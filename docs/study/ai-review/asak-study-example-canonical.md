### 한 줄 결론 예시

관리자 실시간 주문 화면은 주문 목록을 조회해 카드로 보여 주고, 관리자의 상태 변경 또는 취소 요청 뒤에 목록을 다시 조회하여 화면을 최신 상태로 맞추는 구조이다.

이 한 줄은 문서 맨 앞에서 독자가 전체 흐름을 먼저 잡도록 돕는다. 다만 실제 API 연결 여부와 환불 처리 여부는 이 문장만으로 판단하면 안 되며, 아래의 **검증 상태**를 함께 읽어야 한다.

## 1. 먼저 구분할 것: 화면 동작, Mock, API, DB

공부 문서에서는 "된다"는 표현을 하나로 뭉뚱그리지 않는다. 같은 버튼이 보여도 어떤 경로로 동작하는지에 따라 의미가 다르기 때문이다.

| 구분 | 무엇을 확인하는가 | 문서에 쓰는 예시 |
| --- | --- | --- |
| 화면 동작 | 로딩, 목록, 빈 목록, 오류, 버튼 비활성 상태가 보이는가 | `loading`이면 로딩 문구를, 빈 배열이면 Empty 상태를 표시한다. |
| Mock 동작 | 브라우저 안의 임시 데이터로만 화면을 재현하는가 | `sessionStorage`나 mock repository의 데이터를 읽는다. |
| API 연결 | 프론트 요청이 백엔드 엔드포인트까지 실제로 가는가 | `GET /api/admin/orders/live` 호출 경로를 코드와 Network에서 확인한다. |
| DB 반영 | 백엔드 요청이 실제 DB의 어떤 열을 바꾸는가 | 주문 상태, 취소 시각, 결제 환불 필드를 각각 확인한다. |
| 명세 일치 | Bible/Figma/API 문서와 코드의 URL·상태값·문구가 같은가 | 명세의 `/status` 경로와 실제 Controller 경로가 같은지 비교한다. |

### 작성 규칙

- 확인하지 못한 항목은 `미확인`이라고 적는다. 추측을 사실처럼 쓰지 않는다.
- Mock으로 화면이 보인다고 API나 DB까지 연결되었다고 쓰지 않는다.
- Controller가 있어도 결제 환불 처리까지 끝났다고 쓰지 않는다.
- 명세와 코드가 다르면 어느 쪽이 "정답"이라고 단정하기보다, **불일치**로 기록하고 팀이 정할 항목으로 남긴다.

## 2. 이 화면이 사용자에게 제공하는 일

### 사용자 관점

관리자는 새로 들어온 주문을 빠르게 확인하고, 조리 진행 상태를 바꾸거나 주문을 취소할 수 있어야 한다.

### 개발 관점

화면은 다음 네 가지 상태를 모두 가져야 한다.

| 상태 | 사용자에게 보이는 것 | 코드에서 보통 확인할 위치 |
| --- | --- | --- |
| Default | 주문 카드와 상태 변경 버튼 | 화면 컴포넌트의 정상 렌더링 분기 |
| Loading | 주문을 읽는 동안의 로딩 문구/스켈레톤 | `loading` 또는 `isLoading` 분기 |
| Empty | 진행 중 주문이 없다는 안내 | 배열 길이 `0` 분기 |
| Error | 조회 실패 안내와 재시도 수단 | `error` 분기와 재조회 함수 |
| Disabled | 처리 중인 주문 버튼의 중복 클릭 방지 | `pendingOrderId`, `disabled` 속성 |

공부 문서에는 "정상 화면이 보였다"에서 멈추지 않고, 위 상태를 하나씩 코드와 화면 기준으로 확인한다. 그래야 나중에 API가 실패했을 때 어떤 화면이 나와야 하는지도 설명할 수 있다.

## 3. 전체 데이터 흐름 예시

```text
[관리자]
    │ 화면 진입 / 새로고침
    ▼
[LiveOrderPreview]
    │ refresh()
    ▼
[ordersApi.listLiveOrders()]
    │ GET /api/admin/orders/live
    ▼
[AdminOrderController]
    │ Service 호출
    ▼
[AdminOrderService + Mapper]
    │ 조회 SQL
    ▼
[DB 또는 Mock 응답]
    │ 주문 배열 반환
    ▼
[화면 상태 갱신]
    │ loading / ready / empty / error
    ▼
[주문 카드 렌더링]
```

상태 변경은 조회와 흐름이 다르므로 따로 적는다.

```text
[관리자: 상태 변경 버튼]
    ▼
[runOrderAction(orderId, status)]
    ▼
[ordersApi.changeOrderStatus(...)]
    ▼
[PATCH API → Controller → Service → Mapper → DB]
    ▼
[성공하면 refresh()]
    ▼
[변경된 목록을 다시 받아 카드 갱신]
```

### 왜 성공 응답만 믿지 않고 다시 조회할까?

상태 변경 요청의 성공 여부만으로는 화면의 모든 정보가 최신이라는 보장이 없다. 예를 들어 대기 주문 수, 주문 정렬, 다른 관리자가 바꾼 주문 상태가 함께 달라질 수 있다. 그래서 변경 후 목록을 다시 조회하면 서버가 가진 최신 목록을 화면 기준으로 다시 맞출 수 있다.

## 4. 파일을 읽는 순서와 이유

아래 표는 "파일을 많이 읽었다"가 아니라, 각 파일이 흐름에서 맡는 역할을 설명하는 예시다. 실제 파일명과 경로는 그날의 코드에 맞춰 교체한다.

| 읽는 순서 | 파일 예시 | 왜 먼저 읽는가 | 공부할 핵심 |
| --- | --- | --- | --- |
| 1 | `ASAK-Admin/src/components/admin/LiveOrderPreview.jsx` | 화면의 출발점이기 때문 | 상태 변수, `refresh`, 버튼 클릭, 렌더링 분기 |
| 2 | `ASAK-Admin/src/api/ordersApi.js` | 화면이 실제로 어떤 요청을 보내는지 확인 | HTTP method, URL, path parameter, request body |
| 3 | `ASAK-back/.../AdminOrderController.java` | 요청 URL이 백엔드 어디에 도착하는지 확인 | `@GetMapping`, `@PatchMapping`, 요청값 |
| 4 | `ASAK-back/.../AdminOrderService.java` | Controller와 DB 사이의 업무 규칙 확인 | 상태 전이, 예외 조건, 트랜잭션 |
| 5 | `ASAK-back/.../AdminOrderMapper.xml` | 실제 조회/수정 SQL을 확인 | 조회 조건, 상태 코드, 취소/환불 필드 |
| 6 | `ASAK/docs/...Screen Bible...` | 화면 요구사항과 구현을 비교 | Screen ID, 문구, 이동, 상태, API 명세 |
| 7 | Figma Frame/Node | 시각적 상태와 문구를 확인 | Default/Loading/Empty/Error/Disabled |

### 파일별 설명 예시

#### 4-1. 화면 컴포넌트: `LiveOrderPreview.jsx`

이 파일은 "어떤 데이터를 화면에 어떻게 보여 줄지"를 결정한다.

먼저 아래를 찾는다.

```js
const [viewState, setViewState] = useState("loading");
const [orders, setOrders] = useState([]);
const [pendingOrderId, setPendingOrderId] = useState(null);
```

- `viewState`: 지금 화면이 로딩/정상/빈 목록/오류 중 무엇인지 나타낸다.
- `orders`: 카드로 그릴 주문 목록이다.
- `pendingOrderId`: 특정 주문 처리 중 버튼을 잠시 막기 위한 값이다.

그다음 `refresh()`를 찾는다. 이 함수가 API 응답을 받아 `orders`와 `viewState`를 어떤 기준으로 바꾸는지 확인한다.

```js
const refresh = async () => {
  setViewState("loading");
  const response = await ordersApi.listLiveOrders();
  const content = response.content ?? [];
  setOrders(content);
  setViewState(content.length === 0 ? "empty" : "ready");
};
```

이 코드는 **구조 설명용 의사코드**다. 실제 문서에서는 실제 코드와 다르면 그대로 옮겨 적지 말고, "실제 코드는 무엇이며 이 코드가 맡는 역할은 무엇인지"를 분리해서 적는다.

#### 4-2. API 모듈: `ordersApi.js`

화면 컴포넌트에서 URL 문자열을 직접 만들지 않고 API 모듈에 모아 두면, 화면은 "주문을 조회한다"는 역할에 집중할 수 있다.

```js
listLiveOrders: () => apiClient.get("/admin/orders/live")
```

여기서 꼭 확인할 질문은 세 가지다.

1. `apiClient`가 공통 응답 껍질을 풀어서 주는가?
2. 호출하는 쪽은 `response.data`를 써야 하는가, 바로 `response.content`를 써야 하는가?
3. URL 앞의 `/api`는 클라이언트 base URL에 이미 포함되어 있는가?

이 질문을 확인하지 않으면, 화면에서 `undefined`를 읽거나 URL이 중복되는 오류를 이해하기 어렵다.

#### 4-3. Controller: `AdminOrderController.java`

Controller는 프론트의 HTTP 요청을 백엔드 코드로 받는 입구다.

```java
@PatchMapping("/{orderId}/{status}")
public ApiResponse<Void> changeStatus(...) { ... }
```

공부할 때는 "PATCH가 있다"보다 아래를 비교하는 것이 중요하다.

| 비교 대상 | 확인 내용 |
| --- | --- |
| 프론트 호출 | 실제로 `/orders/{orderId}/{status}` 형태인지 |
| Controller | 같은 URL과 HTTP method를 받는지 |
| Bible/API 문서 | 문서의 경로와 코드가 같은지 |
| 상태값 | `PREPARING`, `COMPLETED`, `CANCELED` 등 어떤 문자열을 허용하는지 |

세 곳 중 하나라도 다르면 404, 405 또는 상태 변경 실패가 날 수 있다. 이때 공부 문서의 결론은 "버그다"가 아니라 **경로/상태값 계약을 팀에서 하나로 맞춰야 한다**가 된다.

#### 4-4. Service와 Mapper

Service는 "어떤 상태로 바꿀 수 있는가" 같은 업무 규칙을, Mapper는 "DB에서 실제로 무엇을 읽고 쓰는가"를 담당한다.

예를 들어 취소 API가 주문 상태만 `CANCELED`로 바꾸는지, 결제 테이블의 `approvedAmount`, `approvedAt`, 환불 상태도 함께 바꾸는지는 SQL 또는 결제 서비스 호출까지 확인해야 알 수 있다.

따라서 다음 두 문장은 같은 뜻이 아니다.

- `주문 취소 버튼을 누르면 주문 카드 상태가 바뀐다.`
- `주문 취소와 결제 환불이 모두 처리된다.`

두 번째 문장은 결제 환불 요청/DB 필드/실패 보상 처리까지 증거가 있을 때만 쓴다.

## 5. 데이터 모양을 표로 풀어 쓰기

API 응답 객체를 처음 보는 사람도 이해할 수 있도록 화면에 필요한 필드만 표로 정리한다.

| 화면에서 보이는 것 | 필드 예시 | 왜 필요한가 | 확인 위치 |
| --- | --- | --- | --- |
| 주문 번호 | `orderId` | 어떤 주문을 처리하는지 구분 | 목록 API 응답/DTO |
| 주문 상태 | `orderStatus` | 버튼과 상태 라벨 결정 | DTO, 상태 변환 함수 |
| 주문 시각 | `orderedAt` | 카드 시간 표시와 정렬 | SQL alias/DTO |
| 총 금액 | `totalAmount` | 금액 표시 | 서버 계산값 또는 DB alias |
| 승인 금액 | `approvedAmount` | 결제 완료 금액 확인 | payment 응답/DTO |
| 승인 시각 | `approvedAt` | 결제 시점 확인 | payment 응답/DTO |
| 주문 항목 | `items[]` 또는 화면용 `menus[]` | 메뉴명·수량·옵션 표시 | API 계약/화면 adapter |

### 이름이 비슷해도 역할은 다를 수 있다

`items[]`는 주문 상세의 원본 구조일 수 있고, `menus[]`는 실시간 주문 카드에 맞게 가공된 표시용 구조일 수 있다. 어느 것이 정답이라고 섞어 쓰지 말고, **어느 화면에서 어떤 계약을 쓰는지**를 기록한다.

금액은 가능한 한 다음 이름을 기준으로 통일해서 설명한다.

| 의미 | 권장 이름 |
| --- | --- |
| 주문 총액 | `totalAmount` |
| 결제 승인 금액 | `approvedAmount` |
| 결제 승인 시각 | `approvedAt` |
| 대기 주문 수 | `waitingOrderCount` |

레거시 Mock이나 adapter에 다른 이름이 남아 있다면, 그것도 숨기지 말고 "경계 변환용 이름"으로 적는다.

## 6. 상태 변경과 취소를 분리해서 설명하기

### 일반 상태 변경

```text
WAITING → PREPARING → COMPLETED
```

각 화살표는 업무 규칙이다. 화면 버튼이 보인다는 사실만으로 모든 전이가 허용된다고 판단하지 않는다.

공부 문서에는 다음을 쓴다.

- 시작 상태는 무엇인가?
- 어떤 버튼이 어떤 다음 상태를 요청하는가?
- 서버가 허용하지 않는 전이는 어떻게 처리하는가?
- 요청 중 버튼이 비활성화되는가?
- 성공 후 목록을 다시 읽는가?

### 취소와 환불

```text
[주문 취소 요청]
   ├─ 주문 상태를 CANCELED로 변경
   └─ 결제 환불 처리
        ├─ 환불 승인/실패 기록
        └─ 실패 시 주문 상태와 결제 상태의 정합성 확인
```

취소는 주문 영역, 환불은 결제 영역의 책임일 수 있다. 따라서 취소 엔드포인트가 존재한다고 해서 환불까지 구현됐다고 쓰면 안 된다.

### 문서에 남겨야 할 검증 표 예시

| 항목 | 확인 결과 예시 | 증거 |
| --- | --- | --- |
| 주문 상태 `CANCELED` 변경 | 확인됨 / 미확인 | Mapper update 또는 API 테스트 |
| 취소 시각 기록 | 확인됨 / 미확인 | DB 열 또는 SQL |
| PG 환불 요청 | 확인됨 / 미확인 | 결제 서비스 호출/로그 |
| 환불 실패 처리 | 확인됨 / 미확인 | 예외 처리·테스트 |
| 화면 환불 결과 표시 | 확인됨 / 미확인 | DTO·Figma·컴포넌트 |

## 7. Figma와 코드 매핑 예시

Figma는 "예쁘게 보이는 참고 이미지"가 아니라 화면 상태와 문구의 기준이다.

| 화면 상태 | Figma Frame/Node | 코드의 확인 지점 | 확인 질문 |
| --- | --- | --- |
| Default | 실제 Node ID 기록 | 주문 카드 렌더링 | 상태 라벨, 버튼, 시간, 금액이 맞는가? |
| Loading | 실제 Node ID 기록 | loading 분기 | 요청 중 이전 카드가 남는가, 로딩이 보이는가? |
| Empty | 실제 Node ID 기록 | 빈 배열 분기 | 안내 문구와 CTA가 있는가? |
| Error | 실제 Node ID 기록 | catch/error 분기 | 재시도 동작이 있는가? |
| Disabled | 실제 Node ID 기록 | `disabled`, pending 상태 | 중복 클릭을 막는가? |

### 화면 이동도 적는다

예시:

```text
사이드바 "실시간 주문" 클릭
    → SCR-009 진입
    → 주문 카드 클릭
    → 주문 상세 화면 또는 상세 모달
```

화면 이동이 아직 정해지지 않았거나 구현되지 않았다면 `미정` 또는 `미구현`이라고 기록한다. 예상 흐름을 구현 완료처럼 쓰지 않는다.

공부 문서는 아래처럼 **사실 / 해석 / TODO**를 분리한다.

이 구분은 팀원이 문서를 읽고 "어디까지 끝났고, 무엇을 더 확인해야 하는지" 바로 알 수 있게 한다.

## 9. 검증 기록 예시

| 검증 항목 | 결과 표기 예시 | 왜 하는가 |
| --- | --- | --- |
| 정적 검사 | `npm run lint` 통과 / 경고 n건 | 문법·기본 규칙 확인 |

| DB 조회 | 변경 전/후 레코드 확인 | 상태 값·시각·금액 반영 확인 |
| Figma 대조 | 상태별 문구·버튼 대조 | 화면 요구사항 일치 확인 |

### 실패를 기록하는 방법

검사가 실패했을 때 "실패"만 쓰지 않는다.

```text
결과: 백엔드 compile 실패
원인 위치: 이번에 읽은 주문 기능과 무관한 UserOrderService의 기존 심볼 오류
이번 문서에서 확정 가능한 것: 주문 Controller/Mapper의 코드 구조
이번 문서에서 확정 불가한 것: 현재 브랜치 전체의 백엔드 실행 가능 여부
다음 확인: 해당 기존 오류를 담당자가 해결한 뒤 Spring context와 API 호출 재검증
```

이렇게 쓰면 다른 팀원의 기존 오류를 현재 기능 변경의 오류로 잘못 연결하지 않게 된다.

## 10. 초보자용 점검 질문과 답

### Q1. `response.data`와 `response.content` 중 무엇을 써야 하나요?

Axios가 받는 원본 응답인지, 공통 API client가 이미 바깥 응답을 벗겨 준 값인지에 따라 다르다. `apiClient`의 반환 코드를 먼저 읽고, 실제 응답 한 건을 콘솔 또는 Network에서 확인한 뒤 정한다. 이름만 보고 추측하면 안 된다.

### Q2. Mock 데이터가 보이면 API가 연결된 건가요?

아니다. Mock은 화면 개발을 위해 브라우저 안에서만 데이터를 흉내 낼 수 있다. Network 탭에서 실제 요청이 나가고, Controller 로그 또는 서버 응답을 확인해야 API 연결이라고 말할 수 있다.

### Q3. 주문 취소와 환불은 왜 따로 보나요?

주문 상태 변경은 주문 테이블만 바꿀 수도 있지만, 환불은 결제 승인 취소·환불 금액·실패 보상 같은 별도 책임을 가진다. 둘을 구분해야 "카드가 취소로 보이는 상태"와 "돈이 실제 환불된 상태"를 혼동하지 않는다.

### Q4. 상태값을 프론트에서 마음대로 바꾸면 안 되나요?

화면은 사용자에게 다음 행동을 보여 줄 수 있지만, 실제 허용 여부는 서버가 결정해야 한다. 예를 들어 이미 완료된 주문을 다시 준비 상태로 되돌릴 수 있는지는 서비스 규칙과 DB 상태 전이를 확인해야 한다.

## 11. 직접 해 볼 연습 문제

1. 주문 목록 조회 함수에서 `loading`, `ready`, `empty`, `error`가 되는 조건을 표로 정리해 본다.
2. API client가 공통 응답을 풀어 주는 위치를 찾아, 화면 컴포넌트가 실제로 받는 객체 모양을 한 줄로 적어 본다.
3. 상태 변경 버튼을 연속 두 번 눌렀을 때 어떤 문제가 생길지 쓰고, `disabled` 처리 위치를 찾는다.
4. Screen Bible의 API 경로와 Controller의 매핑을 표로 비교한다.
5. 취소 SQL 또는 결제 서비스에서 `CANCELED`, `approvedAmount`, `approvedAt` 관련 처리를 찾아 "확인됨/미확인" 표를 채운다.
6. Figma의 Empty 상태 문구와 실제 컴포넌트 문구를 비교해 차이가 있으면 기록한다.
