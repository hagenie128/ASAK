# RTOS 공부 메모

> 목적: ASAK 키오스크처럼 **장치(결제·프린터) + 서버(Spring Boot)** 가 나뉜 시스템에서
> **임베디드 / IoT / RTOS** 가 각각 맡는 역할을 정리한다.
> 학습 PC는 Windows + **WSL Ubuntu** 위에서 ARM 펌웨어를 빌드·에뮬한다.

---

## 1. 실행 환경 (한눈에)

| 항목 | 설명 |
| --- | --- |
| 호스트 OS | Windows |
| 개발 리눅스 | **WSL** 안의 Ubuntu |
| 보드 에뮬 | WSL(또는 호스트)에서 **QEMU**로 ARM 보드 가상 실행 |
| 가상화 | WSL2는 가벼운 VM 위에서 리눅스 커널을 돌림 |

일반 OS와 RTOS 비교:

| | 일반 OS (Windows / Linux 등) | RTOS |
| --- | --- | --- |
| 중시 | 처리량, 범용성, 편의성 | **정해진 시간 안에** 중요한 작업 처리 |
| 핵심 | 사용자 편의, 멀티태스킹 유연함 | **우선순위**와 **응답 시간 예측성** |
| 적합 | PC, 서버, 앱 | 임베디드, IoT, 장치 제어 |

## 2. 리눅스(Linux)란? (이게 제일 먼저)

> 한 줄: **리눅스 = 컴퓨터(또는 서버)를 움직이게 하는 운영체제(OS)의 한 종류.**
> Windows, macOS랑 **같은 ‘급’** 이고, 생긴 것만 다르다.

지금 PC에 깔린 건 대부분 **Windows**.
서버·개발·임베디드 도구 세상에서는 **리눅스**를 엄청 많이 쓴다.

### OS가 뭐길래?

```text
[앱]  Chrome, Cursor, Spring Boot, npm …
   ↓  부탁
[OS]  파일 저장, 메모리, 네트워크, 프로세스 관리
   ↓
[하드웨어] CPU, 디스크, 키보드 …
```

OS가 없으면 앱이 하드웨어를 직접 다루기 너무 어렵다.
Windows도 OS, 리눅스도 OS다.

### Windows랑 뭐가 달라?

| | Windows | 리눅스 |
| --- | --- | --- |
| 누가 쓰나 | 일반 PC, 회사 PC | 서버, 클라우드, 개발자, 일부 노트북 |
| 화면 | 아이콘·창이 기본 | 서버는 **검은 터미널(글자)** 이 기본인 경우 많음 |
| 프로그램 설치 | 설치 파일 / Microsoft Store | 터미널에서 `apt install …` 같은 명령 |
| 돈 | 보통 유료(OEM 포함) | 대부분 **무료·오픈소스** |
| 개발 툴 | 됨 | 임베디드·서버 툴이 **원래 여기 친화적** |

둘 다 “컴퓨터 켜면 돌아가는 두뇌”이고,
리눅스가 더 어렵다기보다 **개발·서버 문화가 리눅스 쪽 명령에 익숙한 것**에 가깝다.

### 리눅스 ≠ Ubuntu (헷갈리기 쉬움)

| 말 | 의미 |
| --- | --- |
| **리눅스 커널** | OS의 핵심 엔진 (엔진만) |
| **배포판(distro)** | 엔진 + 도구 + 설치 프로그램을 묶어 낸 **완제품** |
| **Ubuntu** | 배포판 중 하나 (초보자·WSL에서 제일 흔함) |
| 그 외 | Debian, Fedora, Alpine … |

```text
리눅스(커널)
  └─ Ubuntu     ← 우리가 WSL에서 쓰는 것
  └─ Debian
  └─ Fedora
  …
```

그래서 문서에 “리눅스에서 해라” ≈ “Ubuntu 터미널에서 이 명령 쳐라” 인 경우가 많다.

### 우리 공부와의 연결

```text
Windows          ← 평소 쓰는 PC (Cursor, 브라우저, ASAK 프론트)
   └─ WSL
        └─ Ubuntu (리눅스 배포판)
             └─ 여기서 make, gcc, qemu …
```

| 이름 | 초간단 |
| --- | --- |
| Windows | 지금 쓰는 PC OS |
| **리눅스** | Windows랑 다른 종류의 OS |
| Ubuntu | 리눅스를 쓰기 쉽게 포장한 제품 |
| WSL | Windows 안에 Ubuntu를 넣어 두는 통로 |
| RTOS | “실시간”이 중요한 **또 다른** OS (장치용, Windows/리눅스와 목적 다름) |

> 정리: **리눅스를 몰라도 됨 → “Windows 말고 개발용 OS가 하나 더 있는데, 그게 리눅스고, WSL로 빌려 쓴다”** 정도면 충분하다.

## 3. WSL이란?

> **WSL (Windows Subsystem for Linux)**
> Windows 안에서 **리눅스(Ubuntu 등)를 거의 네이티브처럼** 쓰는 기능.

임베디드·RTOS 학습 도구(`gcc`, `make`, `cmake`, `qemu` …)는 원래 리눅스/Unix 환경에서 쓰기 쉽다.
Windows만 있어도 WSL로 그 환경을 바로 쓸 수 있다.

### WSL1 vs WSL2 (느낌만)

| | WSL1 | WSL2 (지금 흔함) |
| --- | --- | --- |
| 방식 | 시스템 호출 번역 | **진짜 리눅스 커널**을 작은 VM에서 실행 |
| 호환성 | 일부 제한 | Docker·QEMU 등에 유리 |
| 파일 속도 | Windows 드라이브 접근이 비교적 단순 | 리눅스 홈(`~/`) 쪽이 빌드에 더 빠름 |

학습할 때는 보통 **WSL2 + Ubuntu** 를 쓴다.

### 왜 RTOS/임베디드 공부에 WSL을 쓰나?

| 이유 | 설명 |
| --- | --- |
| 툴체인 | `arm-none-eabi-gcc`, `cmake`, `make` 설치·사용이 리눅스와 동일 |
| 에뮬 | `qemu-system-arm`으로 보드 없이 펌웨어 실행 연습 |
| Windows와 공존 | Cursor·브라우저·ASAK 프론트는 Windows, 펌웨어 빌드는 WSL |
| 실습 재현성 | 수업·문서의 리눅스 명령을 그대로 따라 하기 좋음 |

```text
[Windows]
  Cursor, Chrome, ASAK Kiosk/Admin (npm) …
       ↕
[WSL2 Ubuntu]
  apt로 도구 설치
  cmake / make / arm-none-eabi-gcc
  qemu-system-arm  ← 가상 ARM 보드
```

### 자주 쓰는 명령 (입문)

```bash
# Windows 터미널 / PowerShell에서 WSL 들어가기
wsl

# 배포판 확인
wsl -l -v

# Ubuntu 안에서
uname -a          # 커널 정보
pwd               # 현재 경로
cd ~              # 리눅스 홈 (빌드 작업은 여기 권장)
```

Windows 파일은 WSL에서 `/mnt/c/...` 로 보인다.

```text
C:\ASAK-workspace  →  /mnt/c/ASAK-workspace
```

> 팁: 펌웨어 소스 빌드는 `/mnt/c`보다 **WSL 홈(`~/projects/...`)** 에 두면 I/O가 빠른 경우가 많다.

### WSL ≠ 임베디드 보드

| | WSL (Ubuntu) | 임베디드 보드 + RTOS |
| --- | --- | --- |
| 정체 | **개발용** 리눅스 환경 | **장치 안**에서 도는 실시간 OS/펌웨어 |
| 목표 | 컴파일·에뮬·실험 | 결제·프린터 등 실제 제어 |
| 실시간성 | 일반 리눅스 (소프트에 가까움) | 하드/소프트 리얼타임 설계 |

WSL은 “보드를 대신하는 OS”가 아니라, **보드용 프로그램을 만들고 QEMU로 돌려 보는 작업장**이다.

### 가상머신(VirtualBox 등)과 비교

| | 전통적 VM | WSL2 |
| --- | --- | --- |
| 무거움 | 창·디스크 할당이 큰 편 | Windows에 더 가볍게 붙음 |
| 통합 | 별도 창에서 리눅스 | 터미널에서 바로 `wsl` |
| 용도 | 완전한 다른 PC처럼 쓸 때 | 개발 툴·서버 연습에 적합 |

메모에 적힌 “가상화머신 + wsl Ubuntu”는 결국 **Windows 위에서 리눅스 개발 환경을 쓰는 것**으로 이해하면 된다.

## 4. RTOS란?

> **Real-Time Operating System**
> 작업이 “언젠가” 끝나는 게 아니라, **마감 시간(deadline) 안에** 끝나도록 설계된 OS.

비즈니스·주문 규칙·DB는 Spring Boot가 담당하고,
**장치 감지·즉시 반응·하드웨어 제어**는 RTOS(또는 장치 쪽 펌웨어)가 담당하는 식으로 역할을 나눈다.

```text
[키오스크 장치 쪽]              [서버 쪽]
결제 리더 / 프린터 / 버튼   →   Spring Boot (상태 저장, 주문 API)
        RTOS가 관리                 비즈니스 로직 관리
```

## 5. 이벤트 처리 흐름

```text
이벤트 발생
  → 감지 (Task가 장치 상태 확인)
  → 우선 처리 (중요도에 따라 Queue + Scheduler)
  → 상태 반영 (다른 Task / 서버로 전달)
```

키오스크에서 자주 나오는 이벤트 예:

- 결제 실패
- 용지 부족
- 카드 승인 완료
- 물리 버튼 입력

## 6. 하드 / 소프트 리얼타임

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| **하드 리얼타임** | 시간 못 지키면 **시스템·안전에 치명적** | 모터 제어, 안전 차단, (키오스크에선) 결제 실패·용지 부족처럼 **즉시 막아야 하는 알림** |
| **소프트 리얼타임** | 늦어도 치명적이진 않지만 **품질이 떨어짐** | 상태 보고, 통계성 로그, 서버 동기화가 조금 늦는 경우 |

> 메모: “결제 실패 / 용지 부족”은 키오스크 UX·운영상 **당장 멈춰야 하는 신호**라서, 학습 맥락에서는 하드 쪽에 가깝게 둔다.
> (산업용 모터 안전과는 급이 다르지만, “절대 놓치면 안 되는 이벤트”로 이해하면 된다.)

## 7. 핵심 구성 요소

| # | 개념 | 쉬운 말 | 역할 |
| --- | --- | --- | --- |
| 1 | **Task** | 독립 실행 작업 단위 (함수에 가까움) | 한 가지 장치/일을 계속 담당 |
| 2 | **Scheduler** | 스케줄러 | 지금 어떤 Task를 돌릴지 결정 |
| 3 | **Priority** | 우선순위 | 중요한 Task를 먼저 실행 |
| 4 | **Queue** | 대기열 / 이벤트 통로 | Task끼리 이벤트를 주고받음 |

### 키오스크 Task 예시

| Task | 담당 장치 | 하는 일 |
| --- | --- | --- |
| `ButtonTask` | 물리 버튼 | 주문 확인 입력 감지 |
| `PaymentTask` | 카드 리더 | 결제 승인·실패 감지 |
| `PrintTask` | 영수증 프린터 | 출력 처리, 용지 부족 감지 |
| `ServerSyncTask` | 통신 모듈 | 이벤트를 Spring Boot로 전송 |

## 8. 큐(Queue)와 연동 예시

**큐 = Task 사이의 이벤트 대기열**

```text
PaymentTask
  결제 승인 감지
    → EventQueue에 이벤트 저장
      → ServerSyncTask가 꺼내서 서버로 전송
        → Spring Boot가 주문/결제 상태 저장
```

같은 방식으로:

```text
PrintTask: 용지 부족 감지
  → EventQueue
    → (높은 우선순위로) UI/서버에 “인쇄 불가” 반영
```

포인트:

- Task는 **자기 장치만** 보고
- Queue로 **느슨하게 연결**
- Scheduler + Priority로 **급한 것부터** 처리

## 9. 역할 분담 한 줄 정리

| 계층 | 담당 |
| --- | --- |
| **RTOS / 장치 펌웨어** | 센서·리더·프린터 감지, 즉시 반응, 이벤트 큐잉 |
| **Spring Boot** | 주문·결제 비즈니스, DB, API, 관리자/키오스크 계약 |

> 비즈니스 계획은 스프링이, 장치 기능 관리는 RTOS가.

## 10. 임베디드(Embedded)란?

> **임베디드 시스템** = 특정 목적만 수행하도록 **기기 안에 심어 둔** 컴퓨터 시스템.

PC처럼 “뭐든지” 하는 게 아니라, **키오스크 결제 모듈·프린터 제어·센서 보드**처럼 역할이 고정된다.

| 특징 | 설명 |
| --- | --- |
| 목적 특화 | 주문 UI PC와 달리, 장치 제어 보드의 할 일이 명확함 |
| 자원 제약 | CPU·RAM·전력이 PC보다 훨씬 작음 |
| 신뢰성 | 장시간 켜 두고, 예측 가능한 동작이 중요 |
| 하드웨어 밀착 | 버튼·UART·SPI·GPIO 등 핀/버스를 직접 다룸 |

### PC / 서버 vs 임베디드

| | PC·서버 | 임베디드 |
| --- | --- | --- |
| CPU | 고성능, 범용 | MCU/SoC, 저전력·저비용 |
| OS | Windows, Linux 등 | 없음(Bare-metal) / RTOS / 경량 Linux |
| 앱 | 여러 프로그램 | 보통 **펌웨어 하나**(또는 소수) |
| 입출력 | 키보드·모니터·네트워크 | 센서, 모터, 리더기, 프린터 |
| 실패 비용 | 앱 재시작 가능 | 장치 멈춤·결제/출력 장애로 직결 |

ASAK 관점:

```text
손님 화면(키오스크 React)     ← 일반 앱/웹에 가까움
결제·프린터 제어 보드         ← 임베디드 (+ RTOS 가능)
Spring Boot 서버              ← 서버(일반 OS)
```

## 11. IoT와의 관계

> **IoT (Internet of Things)** = 센서·장치가 **네트워크로 연결**되어 데이터를 주고받는 구조.

임베디드가 “기기 안의 두뇌”라면, IoT는 그 기기가 **인터넷/서버와 대화**하는 그림까지 포함한 말이다.

```text
임베디드 장치 (센서/리더)
  → 통신 (Wi-Fi, LTE, 시리얼, LAN 등)
    → 서버 / 클라우드 (Spring Boot 등)
      → 모니터링·저장·다른 서비스
```

| 개념 | 한 줄 |
| --- | --- |
| 임베디드 | 장치 **안에서** 제어 |
| IoT | 장치가 **밖(서버)과** 연결 |
| RTOS | 장치 안에서 **실시간으로** 일을 나눔 |

키오스크 예: `ServerSyncTask`가 결제/용지 이벤트를 Spring Boot로 보내는 구간이 IoT식 연결에 해당한다.

## 12. MCU, 펌웨어, Bare-metal

### MCU vs MPU (아주 대충)

| | **MCU** (Microcontroller) | **MPU** (Microprocessor) |
| --- | --- | --- |
| 구성 | CPU + 메모리 + 주변장치가 **한 칩** | CPU 중심, RAM·주변은 외부 |
| 용도 | 센서, 모터, 소형 제어기 | 폰, 라즈베리파이급, 키오스크 메인보드 등 |
| 자원 | 작음 → RTOS·Bare-metal 흔함 | 큼 → Linux 등도 가능 |

학습용 QEMU ARM 보드는 MCU급 임베디드 펌웨어를 돌리는 연습에 가깝다.

### 실제 칩 예: LM3S6965 (TI)

제품 페이지: [TI LM3S6965](https://www.ti.com/product/LM3S6965)
데이터시트(PDF): [LM3S6965 Data Sheet](https://www.ti.com/lit/ds/symlink/lm3s6965.pdf)

> 이건 **보드 전체가 아니라**, 보드 위에 올라가는 **MCU 칩(두뇌 부품)** 의 설명서/판매 페이지다.
> PDF는 그 칩의 **상세 설명서(데이터시트)** — 핀 번호, 메모리 크기, UART·이더넷 사용법 등이 길게 적혀 있다.
> 처음엔 다 읽을 필요 없고, “이 칩 스펙북” 정도로만 알면 된다.

| 페이지에 나오는 말 | 쉬운 말 |
| --- | --- |
| Microcontroller (MCU) | 한 칩에 CPU+메모리+통신이 들어간 **작은 컴퓨터 칩** |
| ARM Cortex-M3 | 그 칩 안의 CPU 설계(종류). “ARM” 계열 |
| 50 MHz | 초당 약 5천만 번 정도 계산할 수 있는 속도 (PC보다 훨씬 느림) |
| Flash 256 KB | 프로그램 저장 공간 (아주 작음) |
| RAM 64 KB | 실행 중 임시 메모리 (아주 작음) |
| UART / SPI / I2C / GPIO | 앞에서 배운 **핀·통신** 주변장치 |
| Ethernet | 유선 랜으로 서버와 이야기할 수 있는 기능 |
| Stellaris | TI가 쓰던 이 MCU 제품군 이름 |

```text
[ 학습/제품 보드 판 ]
     └─ LM3S6965 칩  ← TI 페이지가 설명하는 것
           ├ Cortex-M3 CPU
           ├ Flash / RAM
           └ UART, GPIO, Ethernet …
```

참고:

- **NRND** (Not Recommended for New Designs) = 새 제품에는 비추천, 예전 학습·기존 고객용에 가깝다.
- 후속 예: TI가 안내하는 [TM4C123](https://www.ti.com/product/TM4C123GH6PM) 같은 Cortex-M4 MCU.
- QEMU 실습에서 “lm3s6965evb” 같은 이름이 나오면 = **이 칩이 들어간 평가 보드를 흉내 낸 에뮬**인 경우가 많다.

### 펌웨어(Firmware)

> 하드웨어에 **가깝게 붙어 있는 소프트웨어**. 전원 켜면 바로 돌고, 앱스토어 앱처럼 쉽게 갈아끼우지 않는 편.

- 결제 모듈 안 소프트웨어
- 프린터 컨트롤러 소프트웨어
- 학습용 RTOS 예제 바이너리

### Bare-metal vs RTOS

| | Bare-metal | RTOS |
| --- | --- | --- |
| 의미 | OS 없이 `main` 루프·인터럽트만으로 동작 | Task/스케줄러가 있는 작은 OS |
| 장점 | 단순, overhead 적음 | 여러 장치·우선순위 관리가 쉬움 |
| 단점 | 일이 늘면 `while` 루프가 복잡해짐 | 개념·설정 학습 필요 |

일이 하나면 Bare-metal, **버튼+결제+프린터+통신**처럼 늘면 RTOS가 유리하다.

## 13. 인터럽트와 주변장치 (기초)

임베디드는 “계속 폴링만” 하기보다, 장치가 신호를 주면 **인터럽트(Interrupt)** 로 깨우는 경우가 많다.

```text
카드 리더가 “결제 결과 있음” 신호
  → CPU 인터럽트
    → ISR(인터럽트 서비스 루틴)에서 짧게 처리
      → Queue에 이벤트 put
        → PaymentTask / ServerSyncTask가 이어서 처리
```

| 용어 | 쉬운 말 |
| --- | --- |
| **GPIO** | 핀 on/off (버튼, LED) |
| **UART / 시리얼** | 문자 단위 통신 (많은 모듈 기본) |
| **SPI / I2C** | 칩끼리 짧은 거리 데이터 통신 |
| **ISR** | 인터럽트 직후 **짧게** 실행하는 함수 (길면 안 됨) |

원칙: ISR은 짧게, 무거운 일(서버 전송 등)은 Task + Queue로.

## 18. 에뮬(에뮬레이터)이란?

> **에뮬레이션(emulation)** = 없는 기계를 **소프트웨어로 흉내** 내는 것.
> **에뮬레이터** = 그 흉내를 내는 프로그램.
> 줄여서 그냥 **“에뮬”** 이라고 많이 부른다.

실물 ARM 보드·키오스크 결제 모듈이 없어도,
PC(WSL) 안에서 **“보드인 척하는 프로그램”** 을 돌려 펌웨어를 시험할 수 있다.

### 비유

```text
실물 보드 없이 연습하고 싶다
  → 보드를 산다                    ← 비싸고, 고장·배선 신경 써야 함
  → 에뮬레이터로 보드를 흉내 낸다  ← QEMU 등이 하는 일
```

게임으로 치면 “옛날 게임기를 PC에서 돌리는 것”이 에뮬이고,
우리 공부에서는 “ARM 보드를 PC에서 돌리는 것”이 에뮬이다.

### 우리 도구: QEMU

| 이름 | 역할 |
| --- | --- |
| **QEMU** | 유명한 에뮬레이터 프로그램 |
| **qemu-system-arm** | 그중 **ARM CPU + 보드 전체**를 흉내 내는 실행 파일 |

```text
[내가 만든 펌웨어.elf / .bin]
        ↓ 넣어서 실행
[qemu-system-arm]  ← “가상 ARM 보드”
        ↓
PC 화면에 시리얼 출력, LED 흉내, 동작 확인 …
```

실물 보드에 구워 넣는 대신, QEMU라는 **가짜 보드**에 올려 보는 것이다.

### 에뮬 vs 비슷해 보이는 말

| 말 | 초간단 | 예 |
| --- | --- | --- |
| **에뮬레이터** | 다른 CPU/보드를 **통째로 흉내** | QEMU로 ARM 보드 실행 |
| **시뮬레이터** | 동작을 **수학·모델로 흉내** (하드웨어 1:1이 아닐 수 있음) | 회로·네트워크 시뮬레이션 |
| **가상머신(VM)** | PC 전체를 가상으로 (보통 같은 계열 OS) | VirtualBox에 Ubuntu |
| **WSL** | Windows 안 리눅스 환경 | 개발 작업장 (보드 에뮬 자체는 아님) |

대충 이렇게 기억해도 된다:

- **WSL** = 리눅스 작업장
- **QEMU(에뮬)** = 그 작업장 안에서 돌리는 **가짜 보드**

### 왜 에뮬을 쓰나?

| 이유 | 설명 |
| --- | --- |
| 싸게 | 보드를 안 사도 연습 가능 |
| 빠르게 | 전원·케이블·벽돌(brick) 걱정이 적음 |
| 반복 | 코드 고치고 → 다시 빌드 → 바로 재실행 |
| 한계 | 실제 결제 리더·프린터와 **100% 똑같진 않음** → 나중에 실물 검증 필요 |

```text
학습:  WSL에서 빌드 → QEMU(에뮬)로 확인
제품:  같은 펌웨어를 실물 임베디드 보드에 올려 최종 확인
```

## 19. 시프트(shift)란?

> **시프트** = 비트들을 **옆으로 밀기**.
> 레지스터에서 “몇 번째 스위치를 켜려면?” 할 때 많이 쓴다.

| 기호 | 이름 | 동작 |
| --- | --- | --- |
| `<<` | 왼쪽 시프트 | 비트를 **왼쪽**으로 밀기 (뒤에 0이 채워짐) |
| `>>` | 오른쪽 시프트 | 비트를 **오른쪽**으로 밀기 |

```text
1          =  ...00000001   (bit0만 켜짐)
1 << 0     =  ...00000001   (0칸 밀기 = 그대로, bit0)
1 << 1     =  ...00000010   (왼쪽으로 1칸 → bit1 켜짐)
1 << 3     =  ...00001000   (왼쪽으로 3칸 → bit3 켜짐)
```

그래서 코드에 이런 게 자주 나온다:

```c
// “3번째 비트를 켜라” (0부터 세면 bit3)
값 = (1 << 3);

// 레지스터에 bit3만 켜기 (다른 비트는 유지하는 패턴도 있음)
REG |= (1 << 3);
```

| 표현 | 의미 |
| --- | --- |
| `1 << n` | **n번째 비트만** 1인 값 만들기 |
| `값 << n` | 값 전체를 왼쪽으로 n칸 밀기 |
| `값 >> n` | 오른쪽으로 n칸 밀기 (나누기에 가깝게 쓰이기도 함) |

비유:

```text
스위치 줄:  [7][6][5][4][3][2][1][0]
1 << 3  →  0번째에 있던 불빛을 왼쪽으로 3칸 민 것 → [3]번만 켜짐
```

지금은 **“시프트 = 몇 번째 비트를 가리키려고 옆으로 미는 것”** 정도만 알면 된다.

## 20. day2 `main.c` 의도·의미 (qemu-first-sample)

경로: `/home/administrator/rtos-kiosk-course/day2/qemu-first-sample/src/main.c`

### 이 파일이 하려는 단 한 가지

> “QEMU 가짜 보드가 **살아 있고**, 글자를 **밖으로 보낼 수 있다**”를 보여 주는 것.

- 결제·FreeRTOS·키오스크 로직은 **아직 없음**
- 3일차 전에 **ARM GCC + QEMU가 되는지 확인**하는 bare-metal 샘플
- OS의 `printf`가 아니라 **UART 레지스터에 글자를 직접 써서** 터미널에 로그를 냄

```text
원래 PC 프로그램:  printf("안녕")  → OS가 화면에 그려줌

이 펌웨어:        UART 주소에 글자 쓰기 → QEMU가 터미널에 보여줌
```

### 비유 (아파트 통신함)

| 코드 | 비유 |
| --- | --- |
| `UART0_BASE` | 통신함 건물 주소 |
| `UART_DR` | “넣을 편지” 투입구 |
| `UART_FR` / bit5 | “투입구 꽉 찼음” 램프 |
| `uart_putc` | 램프 꺼질 때까지 기다렸다가 편지 한 장 넣기 |
| `uart_puts` | 문장을 한 글자씩 넣기 |
| `main`의 네 줄 | 부팅됨 / UART 됨 / 보드 돈다 / 다음에 FreeRTOS 확인 메시지 |
| `for (;;)` | 할 일 끝. 끌 OS가 없으니 **여기서 서 있기** |

### 코드 조각별 의도

| 코드 | 의도 |
| --- | --- |
| `UART0_BASE 0x4000C000` | 데이터시트 메모리 맵상의 UART 동네 주소를 이름으로 부르기 |
| `UART_DR` / `UART_FR` | 레지스터 맵의 칸을 변수처럼 읽고/쓰기 |
| `volatile` | 하드웨어가 값을 바꿀 수 있으니 컴파일러가 무시하지 말 것 |
| `1u << 5` (`TXFF`) | “꽉 찼는지”를 알려 주는 **5번째 비트**만 가리키기 |
| `while (UART_FR & TXFF)` | 통이 빌 때까지 대기 (안 그러면 글자 깨짐) |
| `uart_puts` 네 번 | 사람이 읽을 확인 로그 출력 |
| `for (;;)` | `main`이 끝나도 돌아갈 OS가 없어서 **일부러 멈춤** (에러 아님) |

### 실행 흐름

```text
전원/리셋
  → startup.c (벡터 테이블 → Reset_Handler)
    → main()
      → uart_puts("...")
        → uart_putc() 반복
          → UART_FR 확인 → UART_DR에 글자 기록
            → QEMU가 터미널에 표시
      → for(;;) 무한 루프
```

### 머릿속에 남을 한 줄

**의도:** 보드(에뮬)에 “안녕”을 보내서 개발 환경이 되는지 확인한다.
**의미:** 글자 출력 = UART라는 장치의 **레지스터에 값 쓰기**.
