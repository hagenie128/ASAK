## 1. 전체 발표 흐름

발표의 중심 문장:

> ASAK은 옵션 선택이 많은 샐러드 주문을 고객 키오스크와 관리자 운영 화면으로 연결하는 프로젝트이다.

발표 순서:

1. 프로젝트를 시작한 이유
2. 팀별 역할과 수행 방법
3. 기술·데이터 구조
4. Kiosk 화면과 Admin 화면의 구현 결과
5. 수행 단계, 피드백, 결과물
6. 자체 평가와 보완 계획

권장 분량은 22쪽이다. 원본 18쪽의 형식을 복제해 화면·ERD를 분리한다.

### 3쪽 — 프로젝트 개요

**원본 형식 유지:** 다섯 개 세로 카드

#### 1) 주제 및 선정 배경·기획 의도

```text
샐러드 주문은 메뉴 선택 외에도
옵션 선택, 재료 제외, 수량 변경처럼
확인해야 할 항목이 많다.

고객이 주문 과정을 쉽게 이해하고
원하는 조합을 정확히 선택할 수 있는
키오스크 주문 흐름을 만들고자 했다.
```

#### 2) 특화 포인트·차별화 내용

```text
단순 메뉴 주문이 아니라
옵션 정책, 제외 가능한 재료,
품절 여부, 수량 제한을
주문 흐름에 반영한다.

주문 결과는 관리자 화면에서
주문 상태와 메뉴 정보로 확인한다.
```

#### 3) 프로젝트 내용

```text
Kiosk
Home · 메뉴 목록 · 메뉴 상세 · 장바구니 · 결제

Admin
Live 주문 · 주문 관리 · 메뉴 관리 · 품절 · 판매 화면

Backend
메뉴 · 옵션 · 주문 데이터 검증 및 API 처리
```

#### 4) 활용 장비 및 자료

```text
React · React Router · Zustand · Axios
Spring Boot · MyBatis · MySQL
Figma · Bruno · GitHub

Product Bible · Screen Bible · WBS · API 명세
```

#### 5) 활용 방안 및 기대 효과

```text
고객은 복잡한 샐러드 옵션을
화면 흐름에 따라 선택할 수 있다.

운영자는 주문과 메뉴 정보를
관리자 화면에서 확인할 수 있다.

주문 입력 오류를 줄이고
매장 운영 정보를 빠르게 파악하는 것을 목표로 한다.
```

**팀 검토 포인트**

- 실제 구현하지 않은 결제 수단, AI 추천, 하드웨어 제어는 쓰지 않음
- 기대 효과는 수치가 없으면 “시간 단축”, “매출 증가”처럼 단정하지 않음

### 8쪽 — 프로젝트 전체 구조

**원본 형식 유지:** 큰 구조도

**다이어그램에 넣을 요소**

```text
[Kiosk React]                         [Admin React]
Home / Menu / Detail / Cart           Live Orders / Orders / Menus
          │                                      │
          └─────────────── REST API ─────────────┘
                                 │
                    [Spring Boot Backend]
               Kiosk Controller / Admin Controller
                 Service / Validation / MyBatis
                                 │
                           [MySQL Database]
          menu / ing / opt_policy / orders / order_item / payment
```

**표현 규칙**

- Kiosk와 Admin은 좌우로 분리
- API는 가운데 Spring Boot로 모이게 배치
- DB는 오른쪽 또는 하단에 한 번만 배치
- RTOS, 임베디드, 카드리더기, 프린터는 실제 범위가 아니므로 삭제

### 9쪽 — ERD 1: 메뉴·재료·옵션 구조

**원본 형식 유지:** ERD 도식

**넣을 테이블**

```text
category
  └─ menu
       ├─ menu_ing ─ ing
       └─ menu_opt_policy ─ opt_policy ─ opt_policy_item ─ opt_item
                                                    └─ ing
```

**테이블 안에 표시할 최소 필드**

| 테이블 | 표시 필드 |
|---|---|
| category | `id`, `name` |
| menu | `id`, `cat_id`, `name`, `price`, `sold_out` |
| ing | `id`, `name`, `kcal` |
| menu_ing | `menu_id`, `ing_id`, `can_remove` |
| opt_policy | `id`, `opt_group_id`, `min_select`, `max_select` |
| opt_item | `id`, `ing_id`, `name`, `add_price`, `sold_out` |

**하단 설명 문구**

```text
메뉴는 카테고리·기본 재료·옵션 정책으로 구성하며,
옵션 선택 조건과 제외 가능한 재료 정보를 주문 화면에 제공합니다.
```

### 10쪽 — ERD 2: 주문·결제 구조

**추가 페이지 / 9쪽과 같은 ERD 템플릿 복제**

```text
orders
  ├─ order_item ─ menu
  │    ├─ order_item_option ─ opt_item
  │    └─ item_exclusion ─ ing
  └─ payment
```

| 테이블 | 표시 필드 |
|---|---|
| orders | `id`, `order_no`, `order_type_id`, `status_id`, `total_price` |
| order_item | `id`, `order_id`, `menu_id`, `quantity`, `price` |
| order_item_option | `order_item_id`, `opt_item_id`, `quantity`, `price` |
| item_exclusion | `order_item_id`, `ing_id` |
| payment | `order_id`, `status_id` |

**하단 설명 문구**

```text
주문은 메뉴 단위의 주문 항목으로 저장하고,
선택 옵션과 제외 재료를 주문 항목에 연결해 주문 내용을 보존합니다.
```

### 11쪽 — 화면설계서: 키오스크 주문 흐름

**원본 형식 유지:** 메뉴 주문 와이어프레임

**와이어프레임 칸에 넣을 라벨**

```text
상단: 카테고리 선택

1행: 메뉴 목록 / 메뉴 목록 / 메뉴 목록
2행: 메뉴 상세 / 옵션 선택 / 제외 재료·수량

오른쪽 큰 영역: 장바구니
- 선택 메뉴
- 선택 옵션
- 제외 재료
- 수량
- 주문 금액
```

**하단 설명 문구**

```text
고객은 카테고리별 메뉴를 조회하고, 상세 화면에서 옵션·제외 재료·수량을 선택합니다.
선택 결과는 장바구니에 반영되어 주문 금액을 확인할 수 있습니다.
```

### 12쪽 — 핵심 기능 화면: 메뉴 목록

**우측 본문**

카테고리별로 메뉴를 조회하고, 각 메뉴의 이름·가격·이미지·품절 여부를 확인합니다.

메뉴 상세 및 옵션 선택

## 4. PPT 제작 시 금지할 내용

- 실제로 구현·시연하지 않은 AI 추천, 카드 결제 연동, 임베디드, RTOS, 프린터 제어
- 확인하지 않은 성과 수치(주문 시간 단축률, 매출 증가율 등)
- 팀원별 실제 담당 범위를 벗어난 역할 기재
- mock 화면을 완성된 실서비스 연동으로 표현하는 문구
- 원본 템플릿에 남아 있는 예시·작성 안내 문구
