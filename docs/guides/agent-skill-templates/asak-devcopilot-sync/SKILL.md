# ASAK DevCopilot Sync

## 목적

DevCopilot은 ASAK의 보조 협업 도구다.

현재 구현 사실, 승인된 요구사항, API 계약, 화면 설계, 검증 결과를 서로 구분하고, DevCopilot 내용이나 오래된 내보내기로 정본을 덮어쓰지 않는다.

## 사실 종류별 정본 원칙

확인하려는 사실의 종류에 따라 기준을 구분한다.

- 현재 구현 사실: 실제 코드 → 실행·테스트 결과 → Git 이력
- 사용자 경험과 업무 규칙의 의도: Product Bible → Screen Bible → 승인된 결정 기록
- API 계약: 승인된 API 명세 → 실제 Controller·DTO·응답 → 클라이언트 사용 코드
- 화면 디자인: 승인된 Figma Frame/Node → Screen Bible → 현재 UI 구현
- DB 구조와 상태: 실제 DB 조회·DDL·검증된 schema 기록
- DevCopilot, Notion 내보내기, 오래된 문서 복사본: 비교용 보조 자료

정본끼리 충돌하면 어느 하나에 맞춰 조용히 변경하지 않고 `사람 결정 필요`로 기록한다.

## 시작 전 확인

1. 대상 저장소의 Git 상태와 사용자 승인 범위를 확인한다.
2. 소스코드, Product Bible, Screen Bible, Figma, DB는 사용자가 해당 범위의 수정을 명시적으로 승인하지 않으면 수정하지 않는다.
3. 현재 세션에 실제 DevCopilot MCP 도구가 있는지 확인한다.
4. MCP가 없으면 `MCP 미지원`으로 기록하고, 사용자가 허용한 REST 또는 브라우저 수단이 있을 때만 fallback을 사용한다.
5. 작업공간은 기본적으로 `workspace 2`로 하되, URL이나 사용자가 다른 범위를 지정하면 지정 범위만 사용한다.
6. 토큰, 쿠키, Authorization 헤더, 개인 계정 정보, 로그인 세션 정보는 파일·커밋·보고서·채팅에 남기지 않는다.
7. 현재 세션에서 제공되는 MCP 도구 이름과 읽기·쓰기 스키마를 실제로 확인한다. 과거 버전의 기능표를 그대로 가정하지 않는다.

## 전수 점검의 완료 기준

전수 점검을 수행할 때는 목록 API의 pagination, cursor, page, limit, totalCount 또는 이에 준하는 전체 개수 정보를 확인한다.

- 전체 페이지를 읽었는지 확인한다.
- 일부 페이지만 읽었으면 `전수 점검 완료`로 보고하지 않는다.
- 조회 한도나 권한 때문에 전체를 읽지 못하면 `일부 조회` 또는 `조회 범위 제한`으로 기록한다.
- 같은 항목이 여러 페이지에 중복 반환되는 경우 원격 ID 기준으로 중복 제거한다.
- 제목만 같은 항목을 동일 항목으로 단정하지 않는다.

## 전수 점검 범위

다음 여덟 종류를 모두 조회하고, 각 항목을 `동기화`, `변경 없음`, `사람 결정 필요`, `MCP 미지원`, `조회 범위 제한` 중 하나로 분류한다.

| 범위 | 비교 기준 | 주의 사항 |
|---|---|---|
| Wiki | 현재 기준 문서와 정확한 원격 페이지 ID | 제목 검색만으로 새 페이지를 만들지 않는다. |
| 요구사항 | Product Bible 요구사항 ID, 제외 범위 | 상태만 보고 본문을 추정 작성하지 않는다. |
| WBS/작업 | `wbs-v2`의 WBS2 ID와 상태 | `[ARCHIVED DUPLICATE]`, `[SUPERSEDED]`는 보존 레코드다. 정본 WBS와 분리한다. |
| API | 승인된 API 명세, 실제 backend 계약, Bruno, 클라이언트 사용 코드 | 명세만 있고 구현 증거가 없으면 구현 완료로 바꾸지 않는다. |
| 시나리오 | 사용자 시나리오 정본과 Screen ID | 관리자 권한 또는 브라우저 입력 필요 여부를 별도 기록한다. |
| QA | QA Bible, 테스트 케이스, 실제 실행 증거 | 계획과 실행 결과를 혼동하지 않는다. |
| 화면 | Screen Bible, Figma Frame/Node, `screens.json` | SCR ID, 상태, Figma 링크를 함께 확인한다. |
| DB 테이블/뷰 | 실제 DB 조회, DDL, 검증된 schema 동기화 기록 | 오래된 스냅샷으로 원격 ERD를 덮어쓰지 않는다. |

## 안전한 동기화 절차

1. 원격 목록, 전체 개수, 상태, 개별 원격 ID를 읽는다.
2. 각 불일치에 대해 다음을 기록한다.
   - 정본 파일 또는 코드 경로
   - 코드·실행·문서 근거
   - 원격 ID
   - 변경 전 값
   - 변경 제안 값
   - 변경 이유
3. 현재 정본이 명확하고 사용자가 해당 외부 갱신을 승인한 경우에만 **기존 원격 ID 하나씩** 갱신한다.
4. 제목 검색만으로 새 항목을 만들지 않는다.
5. 중복 생성, 삭제, 일괄 초기화, 전체 덮어쓰기는 사용자가 정확한 대상, 영향 범위, 복구 계획을 승인한 경우에만 수행한다.
6. 오래된 `docs/notion` 또는 내보내기 파일을 입력으로 원격 전체를 덮어쓰지 않는다.
7. 갱신 직후 같은 원격 ID를 다시 조회해 제목, 상태, 본문, 관계 필드 반영 여부를 확인한다.
8. 재조회 결과가 다르면 성공으로 보고하지 않는다.
9. 로컬 문서를 갱신했다면 근거와 남은 불일치를 문서에 남긴다.
10. 자동 Git branch, commit, push, merge는 하지 않는다.

## 생성·수정·삭제 원칙

- 기존 ID가 확인되는 항목은 새로 만들지 않고 기존 항목 갱신을 우선한다.
- 원격 ID를 확인할 수 없으면 생성하지 않고 `사람 결정 필요`로 남긴다.
- 삭제는 사용자가 정확한 원격 ID를 승인한 경우에만 수행한다.
- `[ARCHIVED DUPLICATE]`, `[SUPERSEDED]` 같은 보존 레코드는 일반 중복으로 판단해 삭제하지 않는다.
- 관계 필드는 현재 도구가 지원하고, 양쪽 원격 ID가 모두 확인된 경우에만 수정한다.
- 관계를 제목이나 이름 유사도로 추정 생성하지 않는다.

## MCP 미지원 또는 불가 항목 보고

MCP가 없거나 특정 필드·관계 변경을 지원하지 않으면 성공한 것처럼 표현하지 않는다.

| 범위/필드 | 판정 | 근거 | 대안 | 다음 조치 |
|---|---|---|---|---|
| 예: WBS Evidence | MCP 미지원 | 현재 세션 도구 또는 API 스키마에 Evidence 쓰기 없음 | 로컬 `wbs-v2` Evidence 유지 | 기능 제공 시 재점검 |

- REST로 처리했다면 `MCP가 아닌 REST fallback`이라고 명시한다.
- 브라우저로 처리했다면 `브라우저 수동 조작`이라고 명시한다.
- 관리자 로그인, 브라우저 조작, 권한 승인이 필요한 경우 사람 수행 항목으로 남긴다.
- 비밀값, 개인 계정, 로그인 세션은 보고서에 넣지 않는다.

## 현재 세션에서 확인된 DevProject Hub MCP 기능 기준

아래 내용은 고정 기능표가 아니라 과거 확인 기록이다.

작업 시작 시 현재 세션의 실제 MCP 도구와 스키마를 다시 조회하고, 아래 기록과 다르면 현재 세션의 도구 스키마를 우선한다.

과거 확인 기준:

- 요구사항: 조회·생성·수정
- 시나리오: 조회·생성·수정
- 화면: 조회·생성·수정
- WBS: 조회·생성·수정
- API 명세: 조회·생성·수정
- DB 테이블·컬럼: 조회·생성·수정
- QA 테스트케이스: 조회·생성·수정
- 버그: 조회·생성·삭제
- 버그 수정: 과거 확인 기준 미지원

| 항목 | 기본 판정 | 처리 원칙 |
|---|---|---|
| Wiki | 미지원 가능성 높음 | 현재 세션 도구를 확인하고, 정확한 원격 Wiki ID와 사용자 승인이 있을 때만 REST fallback을 사용한다. |
| WBS Evidence/상세 근거 | 미지원 가능성 높음 | 로컬 `wbs-v2` Evidence를 정본으로 보존한다. |
| 요구사항·화면·WBS·API·DB·QA 간 관계 수정 | 미지원 가능성 높음 | 현재 세션 스키마를 확인한다. 미지원이면 관계를 추정 생성하지 않고 로컬 추적성 문서에 근거를 남긴다. |
| 버그 수정 | 과거 확인 기준 미지원 | 현재 세션 스키마를 재확인하고, 미지원이면 REST/API 지원 여부 또는 사람 조치를 보고한다. |
