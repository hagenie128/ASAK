# ASAK 공부

구현된 ASAK 코드를 날짜, 기능, 파일, Screen ID, API 흐름 기준으로 복습할 수 있게 설명한다.

코드를 대신 구현하지 않으며, 초보자도 실제 데이터 흐름을 따라 읽고 직접 확인할 수 있는 학습 경로와 결과 레포트를 남긴다.

## 정본과 결과 파일

기본 설명 정본은 팀 공용 ASAK 문서 저장소의 다음 파일이다.

```text
docs/study/ai-review/ASAK_STUDY_EXAMPLE_CANONICAL.md
```

작업 시작 전 실제 위치를 찾아 읽고, 개인 PC 절대경로를 기준으로 고정하지 않는다.

1. 공부를 시작하기 전에 정본을 읽는다.
2. 정본의 설명 깊이와 구성 방식을 따른다.
3. 정본 속 예시의 기능 완료 여부, API 경로, Figma Node, 데이터는 현재 작업의 사실로 복사하지 않는다.
4. 사용자가 다른 정본 파일을 지정하면 그 파일을 이번 작업의 우선 기준으로 사용한다.
5. 대상 저장소에 다음 형식으로 레포트를 만든다.

```text
docs/study/ai-review/YYYY-MM-DD/asak-study-<짧은-주제>.md
```

6. 폴더가 없으면 만든다.
7. 같은 공부 요청을 이어서 처리하면 기존 레포트를 먼저 읽고 기록을 보존하면서 갱신한다.
8. 현재 요청의 범위나 날짜가 기존 기록과 다르면 새 섹션을 추가하거나 별도 파일을 만든다.
9. 기존 레포트를 통째로 덮어쓰지 않는다.
10. 채팅에는 레포트 전체를 붙이지 않고 완료 결과와 파일 경로만 짧게 알린다.

정본 파일을 읽을 수 없으면 그 사실을 밝히고 아래 필수 목차를 기준으로 레포트를 남긴다.

정본이 없다는 이유로 코드나 문서 내용을 추정하지 않는다.

## 사실 종류별 정본 원칙

- 현재 구현 사실: 실제 코드 → 실행·테스트 결과 → Git 이력
- 사용자 경험과 업무 규칙의 의도: Product Bible → Screen Bible → 승인된 결정 기록
- API 계약: 승인된 API 명세와 실제 서버·클라이언트 구현 비교
- 화면 디자인: 승인된 Figma Frame/Node
- DB 반영: 실제 DB 조회 또는 검증된 실행 기록
- Mock, DevCopilot, 오래된 내보내기: 비교용 보조 자료

명세와 코드가 다르면 어느 한쪽을 자동으로 정답 처리하지 않고 불일치와 확인 담당을 기록한다.

## 시작 전 확인

1. 학습 기준을 확인한다.
   - 날짜
   - 기능
   - 파일
   - 화면
   - API
   - DB
2. 대상 저장소와 사용자의 이해 수준을 확인한다.
3. 지정이 없으면 최근 커밋이나 사용자가 말한 기능을 기준으로 범위를 제안한다.
4. `AGENTS.md`, 현재 Git 상태, 실제 변경 파일, 최근 커밋을 읽는다.
5. 학습 대상과 직접 관련된 문서만 읽는다.
   - UI·화면: Screen Bible, Figma Frame/Node, 상태별 UI
   - API·Backend: API 명세, Controller, Service, DTO, Mapper/Repository
   - DB: DDL, Mapper, 실제 DB 검증 기록
   - 순수 유틸·설정: 관련 코드와 설정 파일
6. 비UI 작업에 Figma 조회를 형식적으로 강제하지 않는다.
7. 구현 완료, Mock 기반, 실제 API 연결, DB 반영, 미검증 상태를 분리한다.
8. 소스코드, DB, Figma, 원격 Git 이력은 수정하지 않는다.
9. 이 스킬이 만드는 파일은 공부 레포트뿐이다.

## 읽는 순서

기능을 실제 구조에 맞춰 아래 흐름으로 역추적한다.

```text
화면/Page
→ Component
→ Hook/상태
→ API 또는 Repository
→ DTO/응답
→ Service
→ Mapper/Repository
→ DB 또는 Mock JSON
```

없는 계층은 억지로 만들지 않고 실제 구조를 표시한다.

### Frontend Mock

```text
Page → Component → Hook → Repository → Mock JSON
```

### 실제 API 연결

```text
화면 요청
→ API client
→ Controller
→ Service
→ Mapper/Repository
→ DB
→ 응답 DTO
→ 화면 표시
```

### Backend 전용 기능

```text
Controller 또는 호출 진입점
→ Service
→ 검증·트랜잭션
→ Mapper/Repository
→ DB
→ 응답 DTO
```

### UI 확인

UI 기능이면 다음을 확인한다.

- Screen ID
- Figma Frame/Node
- Default
- Loading
- Empty
- Error
- Disabled
- 주요 문구
- 이동 경로
- 데이터 필드

## 계약 용어

다음 필드와 상태값은 현재 대상 기능의 실제 코드 또는 승인된 명세에서 확인된 경우에만 사용한다.

- `totalAmount`
- `approvedAmount`
- `approvedAt`
- `waitingOrderCount`
- `CANCELED`
- `APPROVED`

관련 없는 화면이나 API에 특정 필드명 또는 상태값을 강제로 적용하지 않는다.

레거시 Mock 필드는 실제 adapter, mapper, compatibility layer가 확인된 경우에만 호환 경계로 분리한다.

## 레포트 필수 목차

정본의 형식을 바탕으로 현재 작업의 실제 증거로 아래 항목을 작성한다.

1. 문서 기본 정보와 한 줄 결론
2. 기능 또는 화면의 목적과 사용자 관점 동작
3. 학습 범위
4. 확인 파일과 각 파일을 읽은 이유
5. 전체 호출·데이터 흐름 그림
6. 파일별 복습
   - 핵심 함수
   - props
   - 상태
   - 입력 → 처리 → 출력
   - 초보자 주의점
7. 화면 상태
   - Default
   - Loading
   - Empty
   - Error
   - Disabled
   - Figma·Screen Bible 확인 결과
8. 데이터 필드와 Mock·API·DB·명세의 검증 상태
9. 확인한 사실
10. 코드 근거에 따른 해석
11. 미확인 또는 TODO
12. 검증 기록
   - lint
   - build
   - test
   - 브라우저
   - API
   - DB
13. 직접 해 볼 확인 항목
14. 연습문제 3~5개
15. 다음에 읽을 파일 최대 3개

UI가 아닌 기능에서는 화면 상태 목차를 `해당 없음`으로 명시하고 억지로 내용을 만들지 않는다.

## 학습 설명 원칙

- 파일을 열지 않고 함수명, 필드명, 동작을 추정하지 않는다.
- 스크린샷이나 기획 문서를 현재 코드의 증거처럼 쓰지 않는다.
- Mock으로 화면이 보이는 사실, 실제 API 연결, DB 반영, 결제 승인, 결제 취소, 결제 환불을 서로 다른 검증 항목으로 쓴다.
- 취소와 환불을 같은 의미로 단정하지 않는다.
- 결제 환불은 서비스 호출, 외부 결제 결과, DB 기록, 실패 처리 근거가 있을 때만 확인됨으로 쓴다.
- Git 커밋 존재를 기능 완료 또는 테스트 통과로 표현하지 않는다.
- SQL 파일 변경을 실제 DB 반영으로 표현하지 않는다.
- 명세와 코드가 다르면 불일치와 확인 담당 범위를 기록한다.
- 실패한 검증은 실패 위치, 현재 확정 가능한 범위, 다음 확인을 함께 적는다.
- 실행하지 않은 검증을 통과로 쓰지 않는다.
- 비밀값, 토큰, 개인정보, 원본 오류 로그 전체를 기록하지 않는다.
- 초보자 설명은 실제 코드 흐름을 단순화하되 사실을 바꾸지 않는다.

## 레포트 갱신 원칙

같은 주제의 기존 레포트를 갱신할 때:

1. 기존 파일을 먼저 읽는다.
2. 기존 학습 기록을 보존한다.
3. 새로 확인한 범위를 날짜 또는 작업 구간으로 분리한다.
4. 기존 결론이 바뀌면 근거와 변경 이유를 남긴다.
5. 기존 미확인 항목이 해결되면 해결 근거를 연결한다.
6. 내용 전체를 새 결과로 교체하지 않는다.

## 마무리

1. 생성 또는 갱신한 레포트 경로를 확인한다.
2. 레포트를 다시 읽어 코드 근거와 설명이 일치하는지 확인한다.
3. `git diff --check`로 공백 오류를 확인한다.
4. 현재 Git 상태에서 공부 레포트 외 다른 파일이 변경되지 않았는지 확인한다.
5. 자동 commit, push, branch, merge 작업은 하지 않는다.
6. Git 반영은 사용자의 별도 승인 범위만 따른다.
7. 사용자에게는 레포트 파일 경로와 핵심 완료 사실만 짧게 전달한다.
