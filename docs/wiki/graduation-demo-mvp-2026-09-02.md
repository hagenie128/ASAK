## 1. 내일 시연에서 완료로 보는 MVP 범위

### 반드시 시연할 흐름

1. **고객 주문**: 주문 유형 선택 → 메뉴/옵션 → 장바구니 → 결제 → 주문 완료
2. **관리자 운영**: 매장 번호 `0001` 로그인 → 대시보드/주문 목록 → 주문 상태 변경
3. **품절 관리**: 재료 품절 저장 → 고객 메뉴에서 품절 표시/선택 차단 → 복구
4. **결제수단 관리**: 활성/비활성 또는 정렬 변경 → 고객 결제수단에 반영
5. **매출 확인**: 주문/환불 후 일별 매출의 주문 수·취소 금액·순매출 대조

### RTOS 기본 시연 후보

- **환불**: 가상 CARD 환불은 관리자·백엔드 실DB에서 확인했다. 시연 중에는 미리 준비한 테스트 주문만 사용하고, 성공 뒤 주문 `CANCELED`, 결제 `REFUNDED`, 매출 합계를 보여 준다.
- **RTOS/영수증**: `~/ASAK-RTOS`의 FreeRTOS POSIX 클라이언트가 Spring의 pending event를 polling하고, `PRINT_RECEIPT` payload를 콘솔 영수증으로 출력한 뒤 `COMPLETED`를 PATCH하는 기본 흐름을 시연한다. 단, 시연 전 `make`와 전체 흐름이 재현된 경우에만 실행한다.

### 시연 범위에서 제외하고 명시할 기능

- 실제 PG 결제·실제 PG 취소/환불
- 실물 영수증 프린터·보드 펌웨어
- 회원·쿠폰·QR 적립
- WebSocket 실시간 갱신
- 접근성 설정 화면 전체 구현

> 제외 기능을 성공한 기능처럼 말하지 않는다. 현재 환불은 **가상 카드 취소**, RTOS는 **POSIX 콘솔 시연**이며 실물 장비 연동 증거는 없다.

## 2. 오늘 우선순위: 시연 가능 상태 만들기

### P0 — 시연 자체를 막는 항목

- [ ] Kiosk 의존성/lockfile의 `uuid` 문제를 팀원이 해결하고 `npm run build`를 통과시킨다.
- [ ] Admin `npm run build`와 backend `gradlew.bat test --no-daemon -x spotlessApply`을 다시 통과시킨다.
- [ ] Kiosk, Admin, backend를 같은 API/DB 설정으로 실행하고 브라우저 콘솔의 fatal error가 없는지 확인한다.
- [ ] 테스트용 주문·품절 재료·결제수단·환불 대상 주문을 별도로 준비하고 ID/초기 상태를 기록한다.
- [ ] 시연에 쓸 API가 로컬 서버에서 응답하는지 확인한다: 로그인, 메뉴, 주문, 결제, 주문 목록, 품절, 결제수단, 매출.
- [ ] WSL `~/ASAK-RTOS`에서 `make`를 통과시키고, Windows Spring의 실제 호스트 IP로 polling을 시작한다.

### P1 — 시연 신뢰도를 높이는 항목

- [ ] 시연 화면의 Loading, Empty, Error 문구가 깨지지 않는지 확인한다.
- [ ] 메뉴명·가격·금액 합계·주문번호를 고객/관리자 화면과 API 응답에서 대조한다.
- [ ] 브라우저 새로고침 뒤 관리자 로그인과 결제수단/품절 상태가 의도대로 보이는지 확인한다.
- [ ] 백업용 스크린샷과 1~2분 분량의 화면 녹화를 준비한다.

## 2-1. RTOS 기본 시연 준비

### 확인된 구현 경계

- RTOS 저장소: `~/ASAK-RTOS`
- 실행 방식: FreeRTOS `GCC_POSIX` 시뮬레이터
- 흐름: `POST receipt-print` → Spring 메모리 이벤트 큐 → `GET /api/rtos/device-events/pending` → RTOS 콘솔 영수증 → `PATCH /api/rtos/device-events/{eventId}/finish`
- payload: `주문번호|메뉴 요약|금액`의 pipe 문자열
- 한계: 실제 프린터/ARM/QEMU/영구 DB 큐는 범위 밖이며, Spring을 재시작하면 메모리 이벤트 큐가 초기화된다.

### 실행 순서

1. [ ] Windows에서 backend를 실행하고 `Tomcat started on port 8080`을 확인한다.
2. [ ] WSL에서 `cd ~/ASAK-RTOS && make`를 실행해 빌드를 확인한다.
3. [ ] WSL의 Windows 호스트 IP를 확인한다.

   ```bash
   HOST_IP=$(ip route show default | awk '/default/ {print $3}')
   ```

4. [ ] RTOS polling을 시작한다.

   ```bash
   cd ~/ASAK-RTOS
   make run SERVER_URL=http://$HOST_IP:8080
   ```

5. [ ] Kiosk/Admin에서 `PRINT_RECEIPT` 이벤트를 하나 생성하고 RTOS 콘솔의 주문번호·메뉴 요약·금액 출력을 확인한다.
6. [ ] backend의 event 상태가 `COMPLETED`로 변경됐는지 확인하고 캡처한다.

> 같은 Spring 프로세스를 유지한 상태에서 이벤트를 생성·처리한다. WSL에서 `localhost:8080`은 Windows Spring이 아니므로 사용하지 않는다.

## 4. 시연 직전 고정 데이터와 안전 규칙

## 7. 시연 실패 Plan B

1. **Kiosk build 또는 서버가 실패**: 원인을 즉시 고치려 하지 말고, 빌드 성공 로그·준비한 화면 녹화·스크린샷으로 고객 흐름을 설명한다. 실패 사실은 숨기지 않는다.
2. **DB/환불 테스트가 실패**: 환불을 즉석 재시도하지 말고, 이미 기록한 `CANCELED/REFUNDED` 응답과 매출 대조 캡처를 보여 준다.
3. **품절/결제수단 상태가 예상과 다름**: 준비한 원복 API/화면 절차로 복구하고, 고객 주문 데모를 먼저 진행한다.
4. **RTOS가 실패**: 주문·관리자 시연을 계속하고, 빌드 로그와 이벤트 API 흐름을 보여 준 뒤 POSIX 콘솔 시연의 환경 재현 실패로 명확히 설명한다.
5. **네트워크/포트 충돌**: 사전에 확인한 로컬 서버와 동일한 URL만 사용하고, 백업 영상으로 전환한다.
