# ASAK 플랫폼 관리 · 배달 확장 계획

> 상태: **계획 초안 — 구현 전**
> 작성일: 2026-08-14
> 목적: 외부 피드백을 현재 키오스크·매장 Admin 구조에 무리 없이 연결하고, 팀 프로젝트 시연 범위와 이후 포트폴리오 확장 범위를 분리한다.

## 1. 결론과 범위

이번 피드백은 화면을 많이 추가하는 것이 목적이 아니다. ASAK의 기존 주문 흐름에 다음 한 개의 세로 기능 흐름을 추가한다.

```text
고객 배달 주문
→ 매장 조리 상태 변경
→ 배달기사 배정·수거·배달 상태 변경
→ 고객/매장/플랫폼 화면에 같은 상태가 반영
→ 예외(CS) 접수·처리 이력 확인
```

이 흐름에 다건 처리, 종속 검색, 실제 파일 결과(Excel), 상태 이력까지 묶는다. 본사/플랫폼 전체를 한 번에 구현하는 대신, 팀 프로젝트에서는 **배달 주문 1건의 상태 연동**을 우선 구현하고, 다점포·권한 세분화·레시피/신규 메뉴 승인 같은 기능은 다음 버전으로 분리한다.

### 1-1. 팀 프로젝트 v1과 포트폴리오 v2의 경계

| 구분 | ASAK Team Project v1 | ASAK Platform v2 (개인 포트폴리오 확장) |
| --- | --- | --- |
| 한 문장 목표 | 키오스크 주문이 매장 운영 화면까지 안전하게 연결됨을 보여 준다. | 본사·매장·고객·기사·CS가 상태와 데이터를 공유하는 프랜차이즈 운영 플랫폼을 보여 준다. |
| Actor | 고객, 매장 관리자/주방 | 고객, 매장 관리자/주방, 본사 관리자, 배달기사, CS 담당자 |
| 주문/조리 | 주문 상태 이력, Live Order Board, 재조리 카드 | 매장별 주문과 본사 모니터링까지 확장 |
| 품절·재고 | 기존 메뉴·재료·옵션 품절이 Kiosk 주문 가능 여부에 반영 | 매장별 재고 경보·본사 집계·재고 Excel 관리 |
| 다건 처리 | 메뉴 또는 품절의 전체 선택·일괄 상태 변경 1개 | 매장/메뉴/재고의 일괄 반영과 결과 이력 |
| Excel | 주문 목록의 다운로드 1종 | 재고 또는 신규 메뉴 템플릿 업로드·검증·반영 이력 |
| 영수증 전달 | 이메일 1개 채널로 영수증 전송 요청·성공/실패 이력 | 문자·메신저 채널, 발송 템플릿 관리, 재전송 정책 확대 |
| 예외 처리 | CS [재조리] → Live Order Board 재진입 → 해결 처리 | 배송 실패, 환불, 배달 CS 등 예외 유형 확대 |
| 배달 | 설계/시연 여력이 있을 때 최소 상태 연동만 검토 | 기사 배정·픽업·배달중·배달완료와 권한 분리 |
| 본사 기능 | 구현하지 않음 | 매장, 레시피, 신규 메뉴 승인/배포, 운영 Dashboard |

v1의 완료 기준은 “모든 플랫폼 기능을 만들었다”가 아니다. **품절 연동, 주문 상태 이력, 재조리, 다건 처리, Excel 다운로드가 실제 데이터 흐름과 예외 상태까지 보이는가**이다. v2는 v1을 폐기하지 않고 Actor와 상태를 추가하는 버전업으로 진행한다.

### 1-2. 목표 플랫폼 전체 흐름도 (v2)

```text
                         [ASAK Platform / 본사]
              매장 관리 · 메뉴/레시피 · 신규 메뉴 승인 · 운영 모니터링
                                      │
                ┌─────────────────────┼─────────────────────┐
                │                     │                     │
             [매장]                 [CS]                [재고/품절]
     Admin · 주방 · 메뉴 운영    재조리 · 환불 · 이력     영향 메뉴 계산
                │                     │                     │
                └──────────────┬──────┴──────────────┬──────┘
                               │                     │
                           [주문 / 상태 이력]     [Kiosk]
                               │                     │
                       조리완료 │                     └─ 고객 주문/품절 표시
                               ▼
                          [배달 작업]
                    기사배정 → 픽업 → 배달중 → 완료
                               │
                           [배달기사]
```

v1에서는 위 흐름 중 `Kiosk → 주문/상태 이력 → 매장 Admin/주방 → 품절·재조리`를 완성한다. 배달·본사·다점포는 이 구조를 재사용해 v2에서 연결한다.

## 2. 현재 기준과 갭

| 영역 | 현재 확인된 기준 | 이번 계획에서의 처리 |
| --- | --- | --- |
| 주문 유형 | `EAT_IN`, `TAKE_OUT`만 존재 | `DELIVERY` 추가 여부를 계약·DB·Figma에서 함께 확정한다. |
| 주문 상태 | `RECEIVED → PREPARING → COMPLETED`, `CANCELED` | 조리 상태와 배달 상태를 같은 컬럼에 섞지 않는다. |
| 관리자 주문 | 실시간 주문 보드(SCR-009), 주문 관리(SCR-010)가 실연동 | 배달 주문 필터와 배달 진행 요약을 기존 주문 영역에 연결한다. |
| 품절 | SCR-011과 메뉴/재료/옵션 영향 규칙이 존재 | 플랫폼에서 새 기능으로 복제하지 않고 매장 운영 기능으로 유지한다. |
| 메뉴 | SCR-016 메뉴 추가·수정 화면과 재료/옵션 구성 계약이 존재 | 신규 메뉴는 플랫폼 검수/승인 흐름으로 확장하되 기존 메뉴 폼을 재사용한다. |
| 대시보드 | SCR-022는 화면 계약만 있고 프런트 API는 가상 데이터 껍데기 상태 | 배달 핵심 지표는 대시보드 실연동 이후에 추가한다. 현재 값처럼 표시하지 않는다. |

### 반드시 먼저 결정할 점

`COMPLETED`는 현재 조리 완료로도 읽히고 주문 전체 완료로도 읽힐 수 있다. 배달을 넣을 때 주문 상태에 `DELIVERING`, `DELIVERED`를 계속 붙이면 주방과 배송 책임이 섞인다. 따라서 아래처럼 분리한다.

| 책임 | 상태 예시 | 상태를 바꾸는 사람 |
| --- | --- | --- |
| 주문/조리 | `RECEIVED → PREPARING → COMPLETED`, `CANCELED` | 매장 관리자/주방 |
| 배달 | `WAITING_ASSIGNMENT → ASSIGNED → PICKED_UP → DELIVERING → DELIVERED` | 플랫폼 관리자/배달기사 |
| 배달 예외 | `ASSIGNMENT_FAILED`, `DELIVERY_FAILED`, `RETURNED` | 배달기사 요청 후 플랫폼/매장 확인 |
| CS | `OPEN → IN_PROGRESS → RESOLVED` 또는 `REJECTED` | CS 담당자 |

`COMPLETED`가 조리 완료인지 최종 주문 완료인지와 매출 반영 시점은 기존 정책과 충돌할 수 있으므로, 구현 전 팀이 용어를 확정한다. 확정 전에는 enum이나 API를 변경하지 않는다.

## 3. 역할과 페이지 구성

### 3-1. 역할

| 역할 | 책임 | 초기 범위 |
| --- | --- | --- |
| 고객 | 배달 주문·현재 배달 상태 확인·문의 접수 | 배달 상태 조회는 P1 |
| 매장 관리자 | 주문 조리, 재고/품절, 메뉴 초안 작성 | 기존 Admin 확장 |
| 배달기사 | 본인 배정 주문 확인, 수거/이동/완료 처리 | P1의 최소 역할 |
| 플랫폼 관리자 | 매장/배달/CS/신규 메뉴 승인 모니터링 | P2, 우선은 읽기 중심 |
| CS 담당자 | 클레임 접수·처리 상태와 결과 기록 | P2 |

### 3-2. 플랫폼 관리 정보 구조 제안

```text
/platform
├─ /dashboard             운영 요약: 진행 배달, 배정 지연, CS 미처리, 품절 매장 수
├─ /stores                매장 목록·상태·운영시간
├─ /deliveries            배달 목록·상세·기사 배정·상태 이력
├─ /cs                    문의/클레임 목록·처리
├─ /inventory             재고 경보 조회 (매장 데이터 집계)
├─ /sold-out              품절 현황 조회/매장 이동
├─ /menu-approvals        신규 메뉴 초안 검수·승인/반려
├─ /recipes               레시피 조회·버전/사용 메뉴 확인
└─ /imports               Excel 다운로드·업로드 결과 이력
```

처음부터 이 모든 페이지를 만들지 않는다. 팀 프로젝트 P1은 기존 Admin에서 배달 흐름을 완성하고, 플랫폼 페이지는 P2에서 `/platform/dashboard`, `/platform/deliveries`, `/platform/cs`의 읽기/처리 흐름부터 시작한다.

| P3 | 다점포 재고, 레시피 버전, 신규 메뉴 승인 | 플랫폼 고도화 | 매장별 데이터 격리와 승인 이력이 검증된다. |

## 5. P1 화면 설계 카드

### 5-1. 배달 주문 관리 (기존 SCR-010 확장)

- 화면 식별자: **기존 SCR-010 확장**, 새 Figma 프레임/노드는 제작 후 기록한다.
- 목적: 배달 주문을 조건으로 조회하고, 주문·조리·배달 상태와 이력을 확인한다.
- 검색 흐름: `매장 → 주문 유형(DELIVERY) → 주문 상태 → 배달 상태 → 기간/키워드 → [조회]`.
- 표시 필드: `orderNo`, `storeName`, `orderStatus`, `deliveryStatus`, `riderName`, `createdAt`, `assignedAt`, `pickedUpAt`, `deliveredAt`, `totalAmount`.
- 상태: 기본, 불러오는 중, 빈 결과, 오류, 조회 중 비활성화, 상세 패널, 배달 상태 갱신 중, 갱신 실패.
- 재사용 후보: `OrderManagementPage`, `FilterBar`, `OrderTable`, `OrderDetailPanel`, `Pagination`, `OrderStatusBadge`.
- 주의: 자동 조회가 아니라 조건 입력 후 [조회]로 호출한다. 상세를 열어도 목록 필터/선택을 보존한다.

### 5-2. 배달기사 작업 화면 (신규)

- 화면 식별자: 신규 발급 필요.
- 목적: 기사에게 배정된 주문만 보고 `PICKED_UP`, `DELIVERING`, `DELIVERED`로 안전하게 전이한다.
- 화면 이동: 배정 목록 → 주문 상세 → 상태 변경 확인 → 성공/실패 → 목록 갱신.
- 상태: 기본, 불러오는 중, 빈 결과, 오류, 상태 변경 확인, 저장 중 비활성화, 이미 변경됨(409).
- 문구 예시: `주문을 수거했나요?`, `배달 완료로 변경할까요?`, `다른 사용자가 이미 상태를 변경했습니다. 최신 정보를 다시 확인해 주세요.`
- 접근성: 상태는 색상+글자+아이콘/배지로 표시하고, 상태 변경 버튼에는 명확한 이름을 제공한다.

### 5-3. CS/배달 예외·재조리 (신규)

- 화면 식별자: 신규 발급 필요.
- 최소 시나리오 A: 기사 또는 매장 관리자가 `DELIVERY_FAILED`를 요청 → CS 티켓 `OPEN` 생성 → 담당자가 `IN_PROGRESS` → `RESOLVED`로 변경 → 주문/배달 상세에 처리 결과와 시각을 표시한다.
- 최소 시나리오 B: CS 담당자 또는 매장 관리자가 음식 누락/오주문을 확인하고 [재조리]를 누른다 → 원주문에 재조리 요청 이력을 남긴다 → **재조리 작업 카드가 Live Order Board(SCR-009)에 다시 표시**된다 → 매장이 재조리 완료 처리 → CS 티켓이 `RESOLVED`로 바뀐다.
- 재조리는 완료 주문의 `orderStatus`를 억지로 `RECEIVED`로 되돌리지 않는다. 원주문·기존 조리 이력·결제 정보를 보존하고, `reworkOrders`(또는 동등한 재조리 작업 모델)에 `reworkId`, `originalOrderId`, `reasonCode`, `status`, `requestedBy`, `requestedAt`, `completedAt`을 남긴다.
- 실시간 주문 보드에는 일반 주문과 재조리 카드를 배지로 구분한다. 예: `재조리 · #1225 · 누락 재료`. 재조리 카드도 불러오는 중/빈 결과/오류/상태 변경 중 비활성화/동시 변경 충돌 상태를 갖는다.
- 처음에는 배달 실패와 재조리 중 **재조리 1종을 대표 예외로 우선 완성**하고, 환불은 기존 cancel/환불 계약이 확정된 뒤 별도 범위로 둔다.
- 삭제 대신 상태 전이와 처리자/처리 시각/메모를 남긴다.

### 5-4. 메뉴·품절 다건 처리 (기존 SCR-011 또는 SCR-016 확장)

- 화면 식별자: **SCR-011 또는 SCR-016 확장**, 선택한 한 화면의 Figma 상태를 먼저 확정한다.
- 최소 행동: 체크박스, 전체 선택(현재 조회 결과 기준), 선택 `n`건, 일괄 판매중지 또는 일괄 품절, 확인 모달, 요청 중 잠금, 성공 `x`건/실패 `y`건 요약.
- 재사용 후보: 기존 `SoldOutManagementPage`, `SoldOutRow`, `SaveBar` 또는 `MenuListPanel`.
- 안전 규칙: 영향 메뉴와 직접/파생 품절을 하나의 참·거짓 값으로 축소하지 않는다. 실패 항목은 선택 상태와 사유를 유지한다.

### 5-5. 영수증 전달 (기존 주문 완료/상세 화면 확장)

- 화면 식별자: 기존 주문 완료 또는 주문 상세 화면의 확장. Figma Frame/Node와 노출 위치는 구현 전에 확정한다.
- 팀플 v1 채널: **이메일 1개만 실제 연동**한다. 문자·카카오/메신저는 제공사 계정, 비용, 템플릿 승인, 수신 동의 정책이 필요하므로 v2 후보로 둔다.
- 최소 행동: 주문 완료/상세에서 [이메일로 영수증 받기] → 이메일 주소 입력·형식 검증 → 발송 확인 → 요청 중 버튼 잠금 → 성공/실패 안내와 전송 시각 표시.
- 영수증 본문: 주문번호, 주문 시각, 항목/수량, 결제 금액, 매장 정보, 재조리·환불 등 후속 처리 기준. 민감한 결제정보는 포함하지 않는다.
- 상태: 기본, 이메일 입력 오류, 발송 확인, 발송 중 비활성화, 발송 완료, 발송 실패, 재전송 확인, 이미 발송됨.
- 실패는 주문/결제 성공을 되돌리지 않는다. 사용자는 실패 이유를 보고 재시도할 수 있고, 서버는 중복 전송을 방지할 수 있어야 한다.
- 현재 Admin 코드에는 영수증 출력이 TODO-074로만 있으며 API·발급 책임·재시도 규칙이 미확정이다. 이 항목은 **계획**이며 구현 완료가 아니다.

## 6. 데이터와 API 계획

### 6-1. 핵심 데이터 구조 제안

```text
orders
  - 기존 주문 공통 정보
  - orderType: EAT_IN | TAKE_OUT | DELIVERY (결정 후 추가)

deliveries
  - deliveryId, orderId, storeId, riderId
  - deliveryStatus, assignedAt, pickedUpAt, deliveredAt
  - failureReasonCode, failureNote

delivery_status_history
  - historyId, deliveryId, previousStatus, nextStatus
  - changedByActorType, changedById, changedAt, reason

cs_tickets
  - ticketId, orderId, deliveryId, ticketType, ticketStatus
  - requesterActorType, assigneeId, content, resolution, resolvedAt

rework_orders
  - reworkId, originalOrderId, csTicketId, reasonCode
  - reworkStatus, requestedBy, requestedAt, completedAt
  - 원주문 상태를 되돌리는 대신 재조리 작업과 이력을 별도로 보관

receipt_delivery_logs
  - receiptDeliveryId, orderId, channel, recipientMasked
  - deliveryStatus, requestedAt, sentAt, failedAt, providerMessageId, failureCode
  - 재전송 횟수와 멱등성 키는 계약 확정 후 추가
```

재고, 레시피, 매장, 신규 메뉴는 P3까지 기존 테이블/계약을 먼저 조사한 뒤 결정한다. 이름만 보고 새 테이블을 만들지 않는다.

### 6-2. API 초안 (계약 확정 전 구현 금지)

| 목적 | 요청 방식/경로 제안 | 핵심 요청/응답 |
| --- | --- | --- |
| 배달 목록 조회 | `GET /api/admin/deliveries` | `storeId`, `deliveryStatus`, `dateFrom`, `dateTo`, `keyword`, page; 목록+페이지 정보 |
| 배달 상세 조회 | `GET /api/admin/deliveries/{deliveryId}` | 주문 요약, 기사, 현재 상태, 상태 이력, 예외 요약 |
| 배달 상태 변경 | `PATCH /api/admin/deliveries/{deliveryId}/status` | `nextStatus`, `expectedCurrentStatus`, `reason`(예외 시 필수) |
| 기사 내 작업 조회 | `GET /api/rider/deliveries` | 인증된 기사 본인 배정 건만 반환 |
| 기사 상태 변경 | `PATCH /api/rider/deliveries/{deliveryId}/status` | 허용 전이만 적용 |
| CS 티켓 생성/처리 | `POST /api/admin/cs-tickets`, `PATCH /api/admin/cs-tickets/{ticketId}` | 유형, 연결 주문/배달, 처리 상태, 결과 |
| 재조리 작업 생성 | `POST /api/admin/orders/{orderId}/rework` | `reasonCode`, `ticketId`, `expectedOrderVersion`; 재조리 작업 ID와 Live 노출 대상 반환 |
| 재조리 작업 상태 변경 | `PATCH /api/admin/rework-orders/{reworkId}/status` | `PREPARING`, `COMPLETED` 등 허용 전이와 동시성 검증 |
| 영수증 이메일 전송 | `POST /api/orders/{orderId}/receipt-deliveries` | `channel: EMAIL`, `recipient`; 전송 요청 ID와 상태 반환 |
| 영수증 전송 상태 조회 | `GET /api/orders/{orderId}/receipt-deliveries` | 채널, 마스킹 수신자, 성공/실패, 전송 시각, 재전송 가능 여부 |
| Excel 내보내기 | `GET /api/admin/deliveries/export` | 현재 조회 필터, `.xlsx` 파일 응답 |
| Excel 업로드 검증/확정 | `POST /api/admin/imports/.../validate`, `POST /api/admin/imports/.../commit` | 파일 검증 결과 후 사용자 확인 시에만 반영 |

기존 `PATCH /api/admin/orders/{orderId}/{status}`는 조리 상태 전용으로 유지하는 것을 우선안으로 둔다. 배달 상태 변경을 이 API에 추가하지 않는다.

## 7. Excel 업로드·다운로드 정책

### 다운로드

- 대상은 첫 번째로 **배달 주문 목록** 한 종류만 선택한다.
- 현재 화면의 확정된 조회 조건과 정렬 기준을 파일 메타 정보 또는 첫 시트 상단에 남긴다.
- 열 예시: 주문번호, 매장, 조리 상태, 배달 상태, 기사, 배정 시각, 수거 시각, 완료 시각, 금액.
- 파일 생성 성공/실패와 다운로드 파일명이 사용자에게 보여야 한다.

### 업로드

- 업로드는 바로 DB를 덮어쓰지 않는다.
- 순서: 템플릿 다운로드 → 파일 선택 → 서버 검증 → 행별 오류 미리보기 → 오류 행 수정 → 사용자 확인 → 저장 → 성공/실패 행 수와 이력 확인.
- 데이터 종류별 템플릿을 섞지 않는다. 처음에는 **신규 메뉴 초안** 또는 **재고 수량 조정** 중 하나만 선택한다.
- 중복 키, 존재하지 않는 매장/메뉴, 숫자/날짜 형식, 권한 밖 매장, 행 수 제한을 서버에서 검증한다.
- 부분 성공을 허용할지 전체 롤백할지는 업무 데이터 종류별로 사전에 결정한다. 재고·가격처럼 정합성이 중요한 경우에는 전체 롤백이 안전한 기본안이다.

## 8. 구현 순서와 팀 작업 분담

1. **Figma 확정**: 배달 주문 관리, 기사 작업, 고객 지원 예외의 프레임/노드와 기본/불러오는 중/빈 결과/오류/비활성화/충돌 상태를 만든다.
2. **용어·상태 확정**: `COMPLETED`, 배달 상태, 예외/CS 상태, 매출 반영 시점을 팀에서 결정하고 상태 전이표를 승인한다.
3. **Product/Screen/API 문서 갱신**: 새 Screen ID, 문구, 데이터 필드, API 요청/응답/오류/권한을 정본에 기록한다.
4. **DB·백엔드 설계 검토**: delivery와 상태 이력의 관계, 트랜잭션, 동시 변경(`expectedCurrentStatus`)과 권한 검증을 설계한다.
5. **한 세로 흐름 구현**: 배달 주문 생성/조회 → 매장 조리 완료 → 기사 상태 변경 → 고객/관리자 반영을 끝까지 연결한다.
6. **다건 처리와 실제 결과 추가**: 기존 화면 재사용으로 일괄 변경 1개, Excel 다운로드 1개, 영수증 이메일 전송 1개를 완성한다.
7. **예외/고객 지원 1개 추가**: 고객 지원 화면의 [재조리]가 별도 재조리 작업을 만들고 실시간 주문 보드로 다시 들어가는지 검증한다.
8. **P2/P3 확장 판단**: Excel 업로드, 문자/메신저 영수증, 권한 분리, 플랫폼 페이지, 재고·레시피·신규 메뉴 승인으로 넓힌다.

## 9. 발표 시연 시나리오

```text
1. 고객이 DELIVERY 주문을 생성한다.
2. 매장 관리자가 Live Order Board에서 RECEIVED → PREPARING → COMPLETED로 바꾼다.
3. 플랫폼/매장 화면에서 배달 대기 주문을 조회한다.
4. 배달기사가 ASSIGNED → PICKED_UP → DELIVERING → DELIVERED로 바꾼다.
5. 각 화면에서 동일 주문의 상태·시각·담당자가 반영됐음을 보여 준다.
6. 음식 누락 CS 티켓을 열고 [재조리]를 눌러 원주문 이력은 보존한 채 재조리 카드가 Live Order Board로 돌아오는 것을 보여 준다.
7. 매장 관리자가 재조리 카드를 완료 처리하고 CS 티켓이 해결되는 것을 보여 준다.
8. 주문 상세에서 이메일 영수증을 전송하고, 성공/실패와 전송 이력이 표시되는 것을 보여 준다.
9. 배달 목록을 Excel로 내려받아 화면 필터 결과와 행 수를 비교한다.
10. 메뉴/품절 화면에서 다건 선택 후 일괄 상태 변경의 확인·성공/실패 결과를 보여 준다.
```

발표에서는 화면 수를 나열하지 않고, “상태를 분리한 이유”, “동시 변경 충돌을 막는 방식”, “파일 업로드가 즉시 반영되지 않는 이유”를 설명한다.

## 10. 구현 전 체크리스트

- [ ] 배달 주문 화면의 식별자와 Figma 기본/불러오는 중/빈 결과/오류/비활성화/충돌 노드가 확정되었다.
- [ ] `COMPLETED`의 의미와 매출 반영 시점이 결정되었다.
- [ ] 주문 상태와 배달 상태의 전이표·전이 주체·금지 전이가 문서화되었다.
- [ ] 재조리 버튼의 권한, 사유 필수 여부, 원주문/재조리 작업/CS 티켓의 관계와 상태 전이표가 확정되었다.
- [ ] 재조리 카드를 SCR-009 실시간 주문 보드에 표시할 Figma 상태와 일반 주문과의 구분 문구가 확정되었다.
- [ ] 기존 SCR-009/010/011/016 중 재사용 화면과 새 화면의 경계가 결정되었다.
- [ ] 고객·매장·기사·플랫폼·CS의 데이터 접근 범위가 정해졌다.
- [ ] API마다 인증, 요청/응답, 오류 코드, `409` 동시성 처리, 상태 이력이 정의되었다.
- [ ] 영수증의 발급 주체, 이메일 제공사, 수신 동의, 템플릿, 비밀키 보관 위치, 재전송·중복 전송 방지 규칙이 확정되었다.
- [ ] 이메일 실패가 주문/결제 완료를 되돌리지 않으며, 전송 결과가 사용자 화면과 서버 이력에 구분되어 표시된다.
- [ ] Excel 대상 데이터, 템플릿 열, 검증 규칙, 부분 성공/전체 롤백 정책이 결정되었다.
- [ ] 구현/가상 데이터/미연결 항목이 화면에서 명확히 구분된다.

## 11. 근거 및 결정 필요 사항

- 피드백 PDF는 다건 처리, 종속 검색, 상태 전이, 화면 간 연동, 실제 파일 결과, 예외 처리와 하나의 시연 흐름을 우선 권장한다.
- 현재 ASAK 정본에는 주문 상태 `RECEIVED → PREPARING → COMPLETED`, Admin Live/주문 관리/품절/메뉴의 Screen ID와 API 방향이 있다.
- 현재 코드에서 주문 관리자 API는 실연동, 대시보드·품절·매출 일부는 가상 데이터 또는 껍데기 상태다. 따라서 미연결 기능을 구현 완료로 표현하지 않는다.
- 라이브 Figma 파일은 이번 계획 작성 시 직접 열람하지 않았다. 기존 문서의 Figma Node는 기준점이며, 신규 화면은 Figma 확정 후 Node를 이 문서와 Screen Bible에 채워야 한다.
