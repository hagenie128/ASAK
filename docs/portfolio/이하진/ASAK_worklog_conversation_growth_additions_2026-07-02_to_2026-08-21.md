## 0. 이 보강본에서 추가로 기록하려는 것

기존 `worklog/daily/이하진/`과 `worklog/entries/이하진/`은 코드·커밋·검증 근거가 상당히 잘 남아 있다. 다만 Git만 보면 다음 내용이 약하게 보이거나 사라진다.

- 왜 해당 구조를 선택했는지에 대한 **판단 과정**
- 팀원과 API/DB/RTOS 변경 영향 범위를 맞춘 **협업·조율**
- Notion을 단순 메모장이 아니라 정본·View·가이드·업무 공유 도구로 설계한 과정
- 워크로그를 단순 일지가 아니라 **팀 공유 + 포트폴리오 + 성장 기록 + AI 사용 기록**으로 만든 과정
- AI가 만든 초안을 그대로 채택하지 않고, 잘못된 범위·과장·구조를 지적해 다시 시킨 과정
- `커밋됨`, `빌드됨`, `실행 검증됨`, `설계만 됨`을 서로 다른 상태로 관리하게 된 과정
- 발표/시연에서 무엇을 보여줄지, 어떤 기술은 범위 밖으로 미룰지를 정한 과정

이 문서는 이 부분만 보강한다.

### 상태 표기

- **✅ 구현/검증**: 실제 코드·DB·빌드·브라우저·HTTP·시연 등 근거 있음
- **📝 문서/공유**: Notion/Git/가이드/팀 공유까지 수행
- **💡 설계/판단**: 방향·구조·정책을 정했지만 실제 구현은 아직
- **⚠️ 미검증/후속**: 구현 일부가 있더라도 실행 검증이 남음
- **🌱 성장/AI 활용**: 문제 접근법, AI 재지시, 학습 포인트

# 2. 날짜별 붙여넣기용 보강 블록

## 2026-07-02 — 프로젝트 운영 방식과 성장 기록의 시작

### 프로젝트 MVP·역할·완료 기준 정리 — `planning` / `collaboration`

- **작업 목적:** 9주 전체 범위를 한 번에 구현하려 하지 않고, 1차 MVP를 “고객 주문 흐름이 끝까지 동작하는 상태”로 정의해 팀 작업 순서를 고정한다.
- **직접 판단:** React 화면 → Spring Boot/MySQL → API 연동 → 테스트/발표 순으로 통합 단계를 잡고, Day 10 발표에서는 고객 주문 흐름과 관리자 주문 확인을 우선한다. 부가 기능은 기본 동작 이후로 분리한다.
- **협업:** 작업을 사람 이름만으로 나누지 않고 Issue/PR/작업 기록이 이어지도록 기록 구조를 정리했다. 각 작업은 “무엇을 했다”뿐 아니라 **목적·검증·다음 일**을 남기는 방식으로 시작했다.
- **성장 기록:** 이 시점부터 워크로그를 단순 출석 기록이 아니라 이후 포트폴리오에서 “왜 이렇게 설계했는지”를 복원할 수 있는 근거로 사용하기 시작했다.
- **AI 활용:** 계획 초안은 AI로 구조화하되, 발표 범위와 팀원 역할·우선순위는 실제 팀 상황에 맞게 직접 좁혔다.

### AI 활용 메모 추가

- AI에게 “할 일 목록”만 만들게 하지 않고, **MVP / 후순위 / 블로커 / 검증 조건을 나누게 하는 방식**을 사용하기 시작했다.
- 이후 프로젝트 전반에서 `커밋 존재 ≠ 완료`, `UI 존재 ≠ 기능 완료` 같은 증거 중심 기록 방식으로 발전한 출발점이다.

## 2026-07-03 — AI를 생성기가 아니라 Reviewer로 사용

### Cursor/AI 재점검 프롬프트 설계 — `tooling` / `qa`

- **작업 목적:** AI가 코드를 많이 만드는 것보다, 이미 존재하는 Notion·Figma·API·DB·WBS 사이의 불일치를 찾아내도록 역할을 바꾼다.
- **직접 구현/판단:** Cursor 역할을 단순 코딩 도우미가 아니라 **Senior Full-stack Reviewer + 문서 QA**로 두고, 요구사항·화면·API·DB·시나리오·WBS·테스트 사이의 불일치를 찾는 재점검 프롬프트를 설계했다.
- **발표 판단:** Day 10 시연 범위는 고객 주문 흐름과 관리자 주문 확인을 중심으로 두고, 기본 기능과 옵션 기능을 분리해 “다 보여주려다 아무것도 안 되는” 상황을 피하도록 했다.
- **AI 활용:** 1차 AI 결과가 문서 내용을 그대로 요약하는 경우, 실제 산출물과의 불일치를 찾도록 다시 지시하는 방식을 사용했다.

### 성장 포인트

- AI에게 답을 받는 것보다 **검토 기준을 먼저 주는 것**이 결과 품질을 크게 좌우한다는 점을 확인했다.
- 이후 “문서가 아니라 코드부터”, “완료는 증거가 있어야 함” 같은 프로젝트 AI 운영 원칙으로 이어졌다.

## 2026-07-04 — 신규 daily/entry 생성 후보

> 현재 GitHub 이하진 daily에는 07-04 파일이 없지만, 대화 기록상 프로젝트 운영 기여가 있어 별도 기록 가치가 있음.

### Notion 감사 원칙·문서 정합성 점검 — `docs` / `audit`

- **작업 목적:** Notion에 정보가 많아지는 과정에서 AI가 임의로 페이지를 고치거나 옮겨 정본을 훼손하지 않도록 감사 절차를 만든다.
- **직접 판단:** Notion 감사에서는 **즉시 수정 금지 → 문제 목록 작성 → 실제 row 값/링크 검증 → 수정 범위 승인** 순서를 사용하기로 했다.
- **확인 이슈:** WBS-025/API-016 사이 일정·스코프 충돌, DB/링크 전체 검증이 남아 있음을 문제 목록으로 분리했다.
- **협업/문서 운영:** “문서가 있어 보인다”와 “실제로 연결돼 있다”를 구분하고, DB row·링크·정본 위치를 직접 확인하기 전에는 완료로 올리지 않는 기준을 적용했다.
- **AI 활용:** AI에게 정리와 수정 권한을 동시에 주지 않고, **감사(audit)와 변경(change)을 분리**했다.

### 포트폴리오/성장 요약

Notion을 단순 문서 저장소가 아니라 검증 가능한 프로젝트 운영 체계로 다루면서, AI 자동수정의 위험을 줄이기 위한 변경 승인 절차를 설계했다.

## 2026-07-06 — 디자인 자산도 구현 계약으로 관리

### 키오스크 아이콘 프롬프트·Figma 기준 정리 — `design-system` / `ai`

- **작업 목적:** AI 생성 이미지를 임의의 장식물이 아니라 실제 키오스크 UI에서 재사용할 수 있는 일관된 자산으로 만든다.
- **직접 판단:** 아이콘은 **투명 PNG, 배경 없음, 단조롭고 명확한 형태**를 기준으로 잡고, 텍스트·숫자·로고·불필요한 그림자 등 금지 조건을 명시했다.
- **AI 활용:** 1차 이미지 프롬프트를 그대로 사용하지 않고 시각 묘사, 금지 요소, 컬러 팔레트, Figma 컴포넌트 기준, 화면 매핑, 후처리 체크리스트까지 다시 구조화했다.
- **성장 기록:** 생성형 AI 산출물도 “마음에 들면 사용”이 아니라 **디자인 시스템·컴포넌트·화면 역할과 맞는지 검증**하는 방식으로 관리하기 시작했다.

## 2026-07-07 — 신규 daily/entry 생성 후보

### Notion 팀 가이드·학습 리소스 구조화 — `docs` / `knowledge-sharing`

- **작업 목적:** 개인이 알아낸 내용을 대화에서 소모하지 않고, 팀원이 재사용할 수 있는 Notion 하위 페이지와 Markdown 문서로 남긴다.
- **직접 판단:** Markdown 문서를 Notion 페이지로 올리고, 팀이 따라 할 수 있도록 단계별 추천과 사용 목적을 포함한 가이드 구조를 사용하기로 했다.
- **학습 구조:** 코드 학습 자료는 단순 문법 정리가 아니라 **알고리즘 → 문법 → 실제 프로젝트 코드 → 품질/설계 → 디버깅 → SQL** 순으로 묶어 팀 전반에 재사용 가능한 형태로 정리했다.
- **성장 기록:** 워크로그와 학습 문서를 별개로 두지 않고, 프로젝트 작업 중 생긴 문제를 이후 공부 자료로 전환하는 습관을 만들기 시작했다.
- **AI 활용:** AI가 설명한 내용을 그대로 보관하기보다 프로젝트 코드와 연결된 예시·검증 순서를 요구해 팀용 문서로 재가공했다.

### 포트폴리오/성장 요약

프로젝트 중 발생한 질문과 디버깅을 개인 채팅 기록에 남겨두지 않고, Notion/Markdown 기반의 팀 학습 자산으로 전환했다.

## 2026-07-16 — 정본·설계·구현을 분리하는 기준 확립

### 정본 우선순위와 SPEC/IMPLEMENTATION 분리 — `architecture` / `docs`

- **작업 목적:** Notion API/DB 설계와 Figma 화면이 실제 구현처럼 보이는 문제를 막고, 무엇을 근거로 코드를 작성해야 하는지 우선순위를 정한다.
- **직접 판단:** 정본 우선순위를 대체로 **Decision/ADR → Screen Registry → Feature/API 계약 → 최신 Figma → 실제 코드 대조** 흐름으로 관리하고, 문서와 실제 코드가 다르면 구현 evidence를 별도로 확인한다.

- **구현 제약 결정:** SCR-003 메뉴 목록 구현에서는 기존 Kiosk 자산, JavaScript/Axios/Zustand/CSS, Spring Boot/Java 구성은 유지하고, DB migration 없이 인메모리 카탈로그로 우선 구현하는 범위를 정했다.

# 2026-08-21 — RTOS·팀조율·태블릿·IoT 확장 보강

## RTOS 기본 이미지 / 상세 텍스트 영수증 병행 구조 — `feat` / `collaboration`

- **용어 정리:** 기존 `PRINT_RECEIPT`의 `주문번호|메뉴요약|금액` 방식은 앞으로 **기본 이미지**라고 부른다.
- `PRINT_RECEIPT_TEXT`는 옵션·제외·결제·요청사항을 포함한 **상세 텍스트 영수증**으로 구분한다.
- 같은 `main.c`를 사용해도 `eventType`으로 Handler를 나누면 팀원의 기본 이미지와 상세 텍스트 형식을 동시에 지원할 수 있다고 정리했다.

### 팀원 조율 과정

- RTOS 공용 코드를 함께 사용하므로 payload 용량·파서 변경 전에 나연님에게 영향 범위를 설명했다.
- 대화 중 “통메시지로 보낸다”는 표현이 **DB 데이터를 안 쓰는 것처럼 들릴 수 있음**을 확인했다.
- 실제 의미는 주문/결제 데이터는 그대로 사용하되, RTOS가 다시 `|`로 3개 필드만 조립하는 대신 **완성된 출력 문자열을 payload로 받는다**는 것으로 정리했다.
- 나연님이 기본 이미지를 유지하고 싶다면 기존 Handler는 유지하고 새 eventType만 추가하는 방향으로 조정했다.

### 성장 포인트

- 기술적으로 가능한 설계보다 **공용 코드에서 다른 팀원 기능을 깨지 않는 병행 지원**을 우선했다.
- 설명이 모호했을 때 상대가 이해 못했다고 넘기지 않고 데이터 흐름과 출력 포맷의 차이를 다시 정리했다.

## RTOS JSON parser·payload·메모리 개선 — `fix`

- `PAYLOAD_CAPACITY`를 상세 영수증을 수용할 수 있도록 확대.
- JSON 문자열의 `\n`, `\r`, `\t`, `\"`, `\\`, `\/` escape를 복원하도록 `json_string()` 보강.
- `PRINT_RECEIPT_TEXT`는 payload를 다시 분해하지 않고 그대로 출력.
- 큰 로컬 버퍼와 `work_t` 복사로 Task stack이 커지는 문제를 검토해 static buffer, heap pointer 생명주기, Worker/Poll stack size를 정리.
- `vPortFree(work)` 위치와 `worker_running` 생명주기를 확인해 반복 처리 시 누수 가능성을 줄였다.

### 검증 수준

- 실제 상세 영수증이 RTOS 콘솔에 여러 줄로 출력되고 `COMPLETED / receipt text printed`가 Spring으로 보고되는 흐름까지 확인.
- MMS/이미지 영수증은 **아직 설계 단계**이며 구현 완료로 기록하지 않는다.

## 태블릿 LAN 실연결 문제 분석 — `debug` / `frontend`

- **문제:** PC에서는 프론트/백 API가 동작하지만 다른 태블릿에서 열면 백엔드 응답이 오지 않음.
- **원인 후보를 계층별로 분리:**
  - 태블릿의 `localhost`는 개발 PC가 아님.
  - Spring의 `0.0.0.0:8080` 바인딩 여부.
  - Vite `host: 0.0.0.0`.
  - Windows Firewall 8080/5173.
  - CORS.
  - 프론트 `VITE_API_BASE_URL`.
- **개선 방향:** 개발 시 `.env`에 PC IP를 매번 고정하기보다 `VITE_API_BASE_URL=/api` + Vite proxy로 상대경로를 사용하는 방식을 검토했다.
- **UUID 이슈:** PC의 `http://localhost`에서는 `crypto.randomUUID()`가 동작하지만 태블릿이 LAN IP의 HTTP로 접속하면 secure context가 아니어서 브라우저에 따라 제한될 수 있음을 분석했다.
- **성장 포인트:** “태블릿에서 안 됨”을 프론트 버그 하나로 보지 않고 **브라우저 보안 → 네트워크 → 개발서버 바인딩 → API 주소 → CORS** 순서로 범위를 나눴다.

## 영수증 DB 필요성·스냅샷 설계 검토 — `architecture`

- **직접 판단:** 현재 ASAK 시연에서는 별도 `receipt` 테이블이 필수는 아니다.
- 주문/주문상품/옵션/제외/결제 데이터가 원본이고, 영수증은 이 데이터를 조합한 결과물로 본다.
- `DeviceEvent`는 영수증 원본 저장소가 아니라 RTOS 명령의 `PENDING → PROCESSING → COMPLETED/FAILED` 상태를 관리하는 장치 명령 큐 역할로 구분했다.
- **실무 확장:** 실제 상용 환경에서 발행 당시 값을 고정해야 하거나 재발행·취소 영수증·법적 증빙이 필요하면 snapshot 테이블을 추가할 수 있다고 정리했다.
- **성장 포인트:** “실무에서 쓴다”는 이유만으로 현재 프로젝트에 테이블을 추가하지 않고 **현재 요구사항에 필요한 복잡도만 선택**했다.

## 실제 프린터 없는 RTOS/IoT 시연 확장 — `design` / `iot`

### 예쁜 이미지 영수증 방향

- 로고, 매장정보, 영수증번호, 상품/옵션/제외, TOTAL, 이벤트, 바코드, QR이 포함된 **예쁜 이미지 영수증**을 장기 확장안으로 설계했다.
- 이미지 영수증은 Spring이 주문 데이터를 기반으로 PNG를 생성하고, RTOS가 외부 메시징 I/O를 수행하는 역할 분리를 검토했다.

### IoT 성격 유지 결정

단순히 Spring이 SMS/MMS를 직접 보내면 RTOS가 빠지므로 아래 흐름을 후보로 정리했다.

```text
React
  ↓
Spring Boot
  ↓
DeviceEvent: SEND_RECEIPT_MMS
  ↓
FreeRTOS polling
  ↓
WorkerTask
  ↓
외부 SMS/MMS API 호출
  ↓
사용자 휴대폰
  ↓
RTOS → Spring COMPLETED / FAILED
```

- **중요:** `SEND_RECEIPT_MMS`, 영수증 PNG Renderer, 실제 메시징 API는 **2026-08-21 기준 설계/다음 단계**이며 구현 완료가 아니다.
- 실제 프린터가 생기면 동일한 영수증 데이터 계층을 ESC/POS 출력 Adapter로 확장할 수 있는 방향도 검토했다.

### 발표 관점

- “프린터가 없어서 콘솔만 출력했다”보다, **장치 명령을 RTOS가 polling하고 외부 I/O를 수행하며 결과를 서버로 보고하는 구조**를 시연하는 것이 RTOS/IoT 학습 목적을 더 잘 보여준다고 판단했다.

```text
Frontend API URL
↓
Vite host / proxy
↓
CORS / Firewall
↓
Spring binding
↓
RTOS polling / Worker
↓
External I/O
```

### 포트폴리오 문장 후보

> 문제를 화면 증상만 수정하지 않고 데이터·네트워크·런타임 경로 전체로 분해해 추적했습니다. 매출 8초 지연, boolean 직렬화 오류, RTOS JSON escape, 태블릿 LAN 접속처럼 서로 다른 문제도 계층별 가설과 검증으로 범위를 좁혔습니다.

# 6. 최종 기록 원칙

앞으로 daily를 작성할 때 아래 다섯 줄만 꾸준히 남겨도 포트폴리오 품질이 크게 올라간다.

1. **문제:** 무엇이 안 됐거나 왜 바꾸려 했는가
2. **내 판단:** 여러 대안 중 왜 이 방식을 선택했는가
3. **AI 활용:** AI에게 무엇을 시켰고, 무엇을 다시 고치게 했는가
4. **검증:** 커밋/빌드/실행/DB/브라우저 중 어디까지 확인했는가
5. **성장/공유:** 다음에 재사용할 규칙, 팀에 공유한 내용, 배운 점은 무엇인가

이렇게 적으면 단순한 “AI로 많이 개발한 프로젝트”가 아니라, **AI를 검토·통제하면서 실제 근거와 팀 협업을 관리한 프로젝트**로 기록된다.
