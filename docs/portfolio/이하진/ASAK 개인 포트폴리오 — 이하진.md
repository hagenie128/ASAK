# ASAK 개인 포트폴리오 — 이하진

> 프로젝트: **ASAK(A Salad A Kiosk)** — 샐러드 키오스크와 관리자 운영 시스템  
> 기간: **2026.07.01 ~ 2026.08.21**  
> 역할: **Figma·디자인 시스템, React/Vite 관리자 화면, 관리자 도메인 API·DB 계약, 매출·대시보드, 운영 문서와 검증 체계**

---

# 1. 프로젝트 소개

ASAK은 고객이 샐러드의 베이스, 토핑, 옵션을 선택해 주문하는 키오스크와, 매장 직원이 주문·메뉴·품절·결제·매출을 관리하는 관리자 시스템을 함께 만드는 프로젝트이다.

샐러드 주문은 단순히 메뉴 하나를 선택하는 구조가 아니라 재료와 옵션 조합이 많고, 메뉴·재료의 판매 상태가 주문 가능 여부에 직접 영향을 준다. 주문이 발생한 이후에는 결제, 제조 상태, 주문 완료, 취소, 매출 집계, 영수증 출력까지 데이터가 계속 이어진다.

그래서 이 프로젝트를 단순히 **“키오스크 화면과 관리자 페이지를 만드는 작업”​**으로 보지 않았다.

내가 가장 중요하게 생각한 것은 다음이었다.

**고객이 주문할 때 생성된 데이터가 관리자 화면까지 일관되게 이어지고, 매장 직원이 그 데이터를 믿고 실제 업무에 사용할 수 있는가.**

프로젝트 초반에는 Figma 디자인 시스템과 React/Vite 기반 화면 구조를 만드는 데 참여했다. 이후 팀 역할이 정리된 뒤에는 관리자(`admin`) 도메인을 중심으로 주문 Live·상세·상태 변경·취소, 메뉴 CRUD, 영양·재료, 품절, 결제수단, 매출, 대시보드까지 담당했다.

후반으로 갈수록 내 역할도 단순 구현에서 벗어났다.

```text
요구사항 해석
→ 실제 매장 운영 흐름 정리
→ 화면 설계
→ API 계약
→ Service / Mapper
→ DB View와 데이터 확인
→ Front 연결
→ 실 DB 검증
→ 운영 문서와 WBS 반영
```

기능 하나를 만들 때 이 흐름 전체가 맞는지 확인하는 방식으로 프로젝트를 진행했다.

# 2. 내가 이 프로젝트에서 가장 중요하게 생각한 것

## 화면보다 먼저 “운영 흐름”을 봤다

관리자 페이지는 보여주기 위한 서비스가 아니라 **매장에서 계속 열어 두고 사용하는 업무 도구**라고 생각했다.

직원은 관리자 페이지에 들어와 예쁜 UI를 감상하지 않는다.

지금 어떤 주문을 처리해야 하는지, 어떤 메뉴를 판매할 수 없는지, 주문이 제대로 취소됐는지, 오늘 매출이 어떤지를 빠르게 판단해야 한다.

그래서 기능을 설계할 때 항상 화면 다음의 행동을 생각했다.

예를 들어 주문 화면이라면 단순히 주문 목록을 보여주는 데서 끝나지 않는다.

```text
주문 유입
→ 직원 확인
→ 제조 시작
→ 제조 완료
→ 고객 호출
→ 주문 종료
```

각 단계에서 어떤 액션을 보여줄지, 이미 완료된 주문에 다시 잘못된 액션을 할 수 있는지, 취소 상태와 결제 상태를 어떻게 구분할지를 함께 봤다.

품절 역시 단순한 ON/OFF 토글로 보지 않았다.

메뉴가 품절된 것인지, 특정 재료 때문에 판매할 수 없는 것인지, 옵션 항목까지 판매 상태를 관리해야 하는지에 따라 데이터 모델과 화면 정책이 달라진다.

매출도 마찬가지였다.

차트 하나를 그리는 것이 목적이 아니라 **관리자가 어떤 기준으로 매장 상황을 판단할 수 있을지**가 먼저였다.

이 기준은 프로젝트 전체의 설계 방식에 영향을 줬다.

# 3. 프로젝트 초반부터 협업 구조를 먼저 정리했다

## 7월 초 — 코드를 많이 쓰기 전에 “어떻게 같이 일할지”를 만들었다

프로젝트 초반에는 Frontend, Backend, Data Pipeline 역할을 구분하고 여러 저장소를 어떤 방식으로 운영할지 정리했다.

당시 중요하게 본 문제는 프로젝트 규모보다도 **작업 상태가 서로 다르게 해석될 가능성**이었다.

같은 “완료”라는 표현도 사람마다 의미가 달랐다.

누군가는 화면이 만들어지면 완료라고 보고, 누군가는 API가 있으면 완료라고 보고, 또 누군가는 DB까지 연결돼야 완료라고 생각할 수 있었다.

그래서 작업 기록을 `daily`와 상세 `entry`로 나눴다.

### Daily

그날 팀이 빠르게 확인해야 할 내용을 기록했다.

- 오늘 진행한 작업
- 현재 상태
- 블로커
- 다음 작업

### Entry

기능 단위의 상세 근거를 남겼다.

- 왜 변경했는지
- 어떤 파일과 계약이 바뀌었는지
- API·DB에 어떤 영향이 있는지
- 무엇으로 검증했는지
- 아직 확인하지 못한 것은 무엇인지

그리고 Git 이력, WBS, API 문서, 회의록을 연결했다.

이 체계를 만든 이유는 단순히 문서를 많이 남기기 위해서가 아니었다.

팀원이 바뀌거나 며칠 뒤 같은 기능을 다시 확인했을 때

**“왜 이렇게 만들었지?”**

를 다시 처음부터 추측하지 않게 하기 위해서였다.

프로젝트 후반에 팀 규모가 줄어들었을 때도 이 기록 덕분에 현재 구현 상태와 남은 작업을 빠르게 다시 정리할 수 있었다.

# 4. Figma를 단순 시안이 아니라 구현 계약으로 사용했다

## 7월 9일~19일 — 디자인과 개발 사이에 상태와 데이터 기준을 만들었다

초반에는 키오스크와 관리자 화면의 Figma 설계에 참여했다.

키오스크와 관리자 화면은 사용하는 환경 자체가 달랐다.

키오스크는 고객이 서서 짧은 시간 안에 선택해야 하는 세로형 인터페이스이고, 관리자는 직원이 여러 데이터를 동시에 판단해야 하는 데스크톱 환경이었다.

그래서 기준을 분리했다.

- 키오스크: 약 1080px 폭 세로형
- 관리자: 1920×1080 기준 데이터 중심 화면

키오스크에는 홈, 메뉴 목록, 메뉴 상세, 옵션 선택, 장바구니, 결제, 결제 실패, 타임아웃, 주문 완료 흐름을 설계했다.

관리자에는 로그인, 주문, 메뉴, 품절, 매출, 설정 구조를 정리했다.

이때 단순히 화면을 그리는 것으로 끝내지 않고 공통 단위를 정의했다.

Header, CategoryTab, CTA, 주문 요약, Modal, Sidebar, SummaryCard, FilterTab, SectionCard, PageHeader, ExportButton 등을 재사용 단위로 나눴다.

특히 Figma의 Variant와 Property를 React의 props와 상태로 연결했다.

예를 들어 하나의 버튼도 화면에서는 단순히 버튼 하나지만 구현에서는

```text
Default
Loading
Disabled
Error
Sold Out
```

같은 상태가 필요하다.

페이지 역시 정상 데이터만 보지 않았다.

```text
Default
Loading
Empty
Error
Disabled
Payment Failed
Timeout
```

상태를 함께 검토했다.

이 과정을 통해 Figma를 단순한 디자인 결과물이 아니라

**화면 → 상태 → 컴포넌트 → API 데이터**

를 연결하는 사전 계약으로 사용했다.

# 5. Mock을 빠르게 만들되, Mock에 프로젝트가 종속되지 않게 했다

프로젝트 초반에는 서버 구현을 기다리면서 화면을 멈출 수 없었기 때문에 메뉴·옵션·주문·결제 mock 데이터를 사용했다.

하지만 mock 기반 개발에서 가장 위험한 점은 **화면이 잘 돌아가다 보니 실제 기능도 완성됐다고 착각하기 쉽다는 것**이었다.

그래서 mock의 목적을 명확하게 제한했다.

```text
Mock의 역할
= 화면 구조와 상태 흐름을 검증하기 위한 임시 데이터

Mock의 역할이 아닌 것
= 실제 API 계약의 최종 형태
```

React/Vite 구조에서도 데이터 접근 책임을 화면에서 분리했다.

```text
Page / Component
→ Hook
→ API / Repository
→ Data
```

덕분에 mock에서 실제 API로 넘어갈 때 페이지 전체를 다시 만드는 대신 데이터 접근 부분을 교체하는 방향으로 진행할 수 있었다.

이 경험 이후 프로젝트에서도 **화면 컴포넌트가 서버 응답 구조를 직접 너무 많이 알지 않도록 하는 것**을 중요하게 생각하게 됐다.

# 6. 팀 역할이 정리된 뒤 관리자 시스템을 하나의 도메인으로 맡았다

프로젝트 중반 이후 최종 팀은 2인이 되었고, 고객 주문 세션과 관리자 영역을 분리했다.

나는 관리자(`admin`) 도메인을 중심으로 담당했다.

관리자에서 다루는 기능은 다음처럼 많았지만 기능 개수 자체를 목표로 두지는 않았다.

```text
메뉴
↓
재료
↓
품절
↓
고객 주문
↓
결제
↓
관리자 주문 처리
↓
취소
↓
매출
↓
대시보드
↓
영수증 출력
```

각 기능이 서로 다른 페이지에 있어도 실제 매장에서는 같은 데이터 흐름이라는 점을 기준으로 작업했다.

예를 들어 메뉴와 품절을 따로 만들었더라도 품절 상태는 결국 주문 가능 여부와 연결돼야 한다.

주문 취소는 주문 테이블 하나의 상태를 바꾸는 문제로 끝나지 않는다.

결제 상태와 환불 여부까지 영향을 줄 수 있다.

매출도 단순 주문 수가 아니라 취소·환불 데이터를 어떤 방식으로 포함할 것인지 기준이 필요하다.

그래서 관리자 영역을 **페이지 모음이 아니라 하나의 운영 도메인**으로 다루려고 했다.

# 7. API 명세보다 실제 데이터까지 확인했다

프로젝트 중 실제 DB와 API 문서 사이의 차이를 여러 번 경험했다.

문서에는 특정 컬럼이나 응답이 존재하지만 실제 DB에는 없거나, 기존 View가 최신 테이블 구조를 반영하지 않는 경우가 있었다.

이때 문서만 기준으로 화면을 맞추면 결국 실행 단계에서 문제가 발생한다.

그래서 데이터 문제가 생기면 다음 순서로 확인했다.

```text
React 화면
↓
API 요청
↓
Controller
↓
Service
↓
Mapper
↓
SQL
↓
실제 DB 테이블 / View
```

프론트에서 값이 안 보인다고 바로 기본값을 넣거나 이름을 바꿔서 맞추기보다 **데이터가 어느 단계에서 잘못됐는지**를 추적했다.

이 과정에서 `price`, `basePrice`, `unitPrice`처럼 같은 의미처럼 보이지만 실제 책임이 다른 필드도 정리했다.

`orderId`와 사용자에게 보여주는 `orderNo` 역시 분리했다.

주문 상태와 결제 상태도 하나의 상태처럼 처리하지 않았다.

이런 계약을 먼저 정리하면 처음에는 확인할 것이 많지만 이후 기능이 늘어날수록 화면마다 별도 예외 처리가 늘어나는 것을 막을 수 있었다.

# 8. 대표 경험 1 — 모호한 “품절 관리”를 실제 운영 정책으로 바꿨다

초기 요구사항에는 “관리자가 품절 상태를 관리한다” 정도만 있었다.

하지만 실제 구현을 시작하면 바로 여러 질문이 생긴다.

메뉴만 관리할 것인지, 재료까지 관리할 것인지, 옵션도 대상인지, 각 데이터를 별도 API로 만들 것인지, 운영자는 화면에서 어느 수준까지 볼 것인지 결정해야 했다.

처음부터 각 테이블을 화면에 그대로 노출하면 API도 복잡해지고 관리자 입장에서도 관리 단위가 지나치게 많아진다고 판단했다.

그래서 데이터 계층과 화면 정책을 나눴다.

DB에서는 `vw_soldout_catalog` View를 통해 메뉴·재료·옵션 항목을 같은 구조로 조회할 수 있게 만들었다.

```text
관리자 품절 화면
→ soldOutApi / useSoldOutDraft
→ GET·PATCH /api/admin/soldOut
→ AdminSoldOutService
→ AdminSoldOutMapper
→ vw_soldout_catalog
→ menu / ing / opt_item
```

대상 종류, ID, 이름, 분류, 품절 여부, 가격, 이미지 URL을 같은 형태로 제공하게 했다.

반면 현재 관리자 화면에는 실제 운영자가 자주 다룰 **메뉴와 재료만 노출**했다.

`OPTION_ITEM`은 View와 API 구조에는 유지했다.

향후 옵션 품절까지 운영 정책이 확장돼도 데이터 구조를 처음부터 다시 만들지 않기 위해서였다.

이 경험에서 중요했던 것은 “확장성을 위해 모든 걸 화면에 넣는다”가 아니었다.

**데이터 구조는 확장 가능하게 두되, 현재 사용자에게 필요한 화면은 단순하게 유지하는 것​**이었다.

# 9. 대표 경험 2 — 주문 상태를 UI가 아니라 도메인 상태 전이로 다뤘다

관리자 주문 화면에서는 주문이 들어온 뒤 직원이 상태를 변경한다.

처음 보면 버튼 몇 개로 구현할 수 있는 기능처럼 보인다.

하지만 실제로는 주문 상태마다 가능한 다음 행동이 다르다.

예를 들어 이미 완료된 주문에 다시 제조 시작을 누를 수 있어서는 안 된다.

취소된 주문도 정상 주문과 같은 액션을 보여주면 안 된다.

그래서 화면 버튼을 기준으로 상태를 만들기보다 서버의 상태 전이를 먼저 확인했다.

```text
RECEIVED
→ PREPARING
→ COMPLETED
```

같은 흐름과 취소 가능 조건을 기준으로 UI를 연결했다.

Live 주문 조회, 상세 정보, 상태 변경, 취소를 각각 연결했고 READY·완료 상태에서 버튼과 TTS 문구도 관리자 흐름에 맞게 조정했다.

여기서 특히 중요하게 본 것은 **화면 상태와 서버 상태를 따로 놀게 하지 않는 것**이었다.

버튼을 눌렀다는 이유로 먼저 화면 상태만 바꾸는 것이 아니라 서버 응답을 기준으로 상태를 갱신했다.

---

# 10. 대표 경험 3 — 주문 취소를 “취소 버튼”으로 끝내지 않았다

주문 취소 기능을 구현하면서 주문 상태와 결제 상태를 함께 봐야 한다는 문제가 있었다.

사용자가 보기에는 하나의 “취소”지만 시스템에서는

```text
주문 취소
결제 취소
환불 상태
취소 시간
취소 실패 이유
```

가 각각 다른 의미를 가진다.

8월 21일에는 취소 처리 과정에서 실패 사유를 세분화하고 화면에 전달할 수 있도록 정리했다.

단순히

`취소에 실패했습니다.`

라는 메시지를 보여주는 것보다 서버가 판단한 실패 이유를 사용자에게 전달할 수 있게 하는 편이 운영상 유용하다고 판단했다.

또 당시 환불 버튼의 일부 흐름은 실제 결제 서버 환불 API가 아니라 mock에 연결돼 있다는 것도 확인했다.

화면에 버튼이 있고 클릭이 된다는 이유로 **“실제 환불 기능 완료”라고 기록하지 않았다.**

이 부분은 포트폴리오를 정리하면서도 그대로 미완료 또는 추가 검증 항목으로 남겼다.

내가 프로젝트에서 중요하게 생각한 **“보이는 것과 실제로 보장되는 것을 구분한다”​**는 기준이 가장 잘 드러난 사례 중 하나다.

---

# 11. 대표 경험 4 — 메뉴 CRUD보다 메뉴가 운영 데이터가 되는 과정에 집중했다

관리자 메뉴 관리에서는 단순한 이름·가격 수정뿐 아니라 영양 정보와 재료 연결까지 필요했다.

메뉴 생성·수정·삭제 흐름을 정리하면서 삭제 정책도 검토했다.

운영 데이터는 주문 이력이나 다른 참조와 연결될 수 있기 때문에 즉시 물리 삭제하는 것보다 `soft delete`가 적절하다고 판단해 API·문서·DB 방향을 맞췄다.

재료 영양 데이터는 seed와 CSV를 점검하면서 중복 데이터를 정리했다.

이 과정에서 **화면에서 보이는 메뉴 하나가 실제로는 여러 데이터의 조합**이라는 점을 다시 확인했다.

이미지 처리 역시 로컬 정적 파일에 의존하지 않도록 Cloudinary URL 흐름으로 변경했다.

관리자에서는 이미지 미리보기를 제공하고, Front 개발 환경에서는 `/api` 프록시와 환경 변수 기준을 정리했다.

이미지 자체를 화면 코드와 강하게 묶기보다 외부 자산 URL로 관리해 환경이 달라져도 같은 데이터를 사용할 수 있도록 했다.

# 12. 대표 경험 5 — 매출을 “차트 구현”이 아니라 “집계 정책 설계”로 접근했다

매출 기능은 프로젝트 후반에 가장 많이 구조를 다시 본 영역이었다.

처음에는 매출 페이지가 있으니 필요한 데이터를 가져와 차트를 그리면 된다고 생각하기 쉽다.

하지만 실제 운영에서 필요한 질문은 서로 다르다.

```text
오늘 장사가 어떤가?
이번 주는 지난주보다 나은가?
이번 달 누적 매출은 얼마인가?
일별로 언제 매출이 떨어졌는가?
오늘 어느 시간대에 주문이 몰렸는가?
취소가 매출에 얼마나 영향을 줬는가?
```

하나의 API와 하나의 DTO로 모든 질문에 답하려고 하면 응답이 계속 커지고 화면마다 필요 없는 값까지 받게 된다.

그래서 **화면별 DTO가 아니라 조회 책임별 API**로 나눴다.

| 목적 | API |
| --- | --- |
| 매출 요약 | `GET /api/admin/sales/summary` |
| 월별 매출 | `GET /api/admin/sales/monthly` |
| 일별 매출 | `GET /api/admin/sales/daily` |
| 시간대별 매출 | `GET /api/admin/sales/daily/time-slots` |

월별에서는 총매출, 주문 수, 취소 주문, 취소 금액, 평균 주문 금액, 취소율 등 월 단위 지표를 제공했다.

일별에서는 기간 단위의 일별 집계를 제공했다.

시간대 API는 `intervalMinutes=30` 또는 `60`을 받아 차트 단위를 바꿀 수 있게 했다.

이 구분은 화면에 맞춰 API를 잘게 쪼갠 것이 아니라 **데이터 집계의 책임과 변경 이유가 서로 다르기 때문**이었다.

# 13. 없는 데이터는 DB에 만들지 않고 서비스에서 표현했다

시간대별 매출을 실제 DB와 연결하면서 흥미로운 문제가 생겼다.

예를 들어

```text
10:00 주문 있음
10:30 주문 없음
11:00 주문 있음
```

이라면 실제 주문 데이터에는 10:30이라는 행이 존재하지 않는다.

하지만 차트에서 10:30을 통째로 없애면 사용자는

**“매출이 0이었던 것인지 데이터 조회가 빠진 것인지”**

구분할 수 없다.

처음부터 DB에 모든 시간대를 가짜 행으로 저장하는 방법도 있지만, 실제로 발생하지 않은 데이터를 데이터베이스에 넣는 것은 맞지 않다고 판단했다.

그래서 역할을 나눴다.

```text
DB
→ 실제 주문이 발생한 사실 데이터만 저장

Service
→ 영업시간 기준으로 빠진 시간대를 생성

API
→ 연속된 시간축으로 반환

Frontend
→ 그대로 차트 표현
```

영업시간은 `10:00~22:00`을 기준으로 하고, 빈 시간대는 `0`으로 보정했다.

일별 매출에서도 같은 원칙을 적용해 조회 기간 안에 주문이 없는 날짜를 처리했다.

또 현재 날짜 이후의 미래 날짜나 아직 오지 않은 월까지 빈 값으로 계속 표시되지 않도록 범위를 제한했다.

이 과정에서 **DB의 사실과 UI가 필요로 하는 표현은 같은 것이 아니라는 점**을 명확하게 이해하게 됐다.

# 14. 대시보드 8초 문제를 실제로 측정하고 단계적으로 줄였다

관리자 대시보드는 오늘 KPI, 최근 주문, 월 누적, 주간 트렌드, 재고 알림 등 여러 데이터를 한 번에 보여준다.

실 DB와 연결한 뒤 대시보드 조회가 약 **8초** 걸리는 문제가 발생했다.

8초는 로딩 Spinner를 예쁘게 만드는 것으로 해결할 수 있는 시간이 아니었다.

그래서 먼저 어느 부분에서 시간이 발생하는지 확인했다.

대시보드가 필요한 데이터를 다시 나눴다.

```text
반드시 DB에서 집계해야 하는 값
이미 가져온 데이터로 계산할 수 있는 값
화면에서 계산해도 되는 값
중복 조회되고 있는 값
대시보드에서 실제로 필요하지 않은 값
```

첫 번째 개선에서는 DB 조회 횟수를 **10회에서 6회로 줄여 약 3.7~3.9초**까지 낮췄다.

여기서 끝내지 않고 SQL View 구조도 다시 검토했다.

View를 변경하면 더 빨라질 것이라고 예상했던 시도도 있었지만 실제 측정 결과 오히려 느려졌다.

추측대로 밀고 가지 않고 해당 변경은 원복했다.

이후 Mapper를 다시 확인하면서 최근 주문 조회가 복잡한 View를 거칠 필요가 없다고 판단해 **베이스 테이블 직접 조회** 방식으로 변경했다.

최종적으로 실 DB 기준 응답 시간이

**약 8초 → 0.43~0.50초**

수준으로 줄었다.

```text
최초         약 8초
1차 개선     약 3.7~3.9초
최종 개선    약 0.43~0.50초
```

이 과정에서 가장 의미 있었던 것은 단순한 최종 숫자만이 아니었다.

성능 개선 과정에서 실패한 시도도 실제 측정 결과를 기준으로 원복했고, 어떤 변경이 효과가 있었는지를 기록했다.

**성능 최적화를 감이 아니라 측정과 책임 분리로 진행한 경험**이었다.

# 15. 개발 과정에서 나온 문제를 다시 기획에 반영했다

프로젝트를 진행하면서 처음 만든 명세가 항상 정답은 아니었다.

실제 데이터를 연결하면 설계 단계에서는 보이지 않았던 문제가 나타났다.

매출 기능만 해도 다음 문제가 개발 중 발견됐다.

```text
주문 없는 날짜가 차트에서 아예 사라짐
영업시간 중 주문 없는 시간대가 사라짐
미래 날짜까지 출력될 가능성
일별 합계와 시간대 응답 구조가 다름
취소 주문을 어떤 지표에 반영할지 필요
```

이런 문제를 단순한 프론트 버그로 처리하지 않았다.

각 문제를 보고 다시

**“이건 어디서 책임지는 게 맞지?”**

를 결정했다.

DB에서 해결할 문제인지, Service에서 보정할 문제인지, API 계약을 분리해야 하는 문제인지, Front에서 표현해야 하는 문제인지 나눴다.

즉 개발을 **기획 → 구현**의 일방향 과정으로 보지 않았다.

```text
기획
→ 구현
→ 실제 데이터 연결
→ 문제 발견
→ 정책 수정
→ 다시 구현
```

하는 반복 과정으로 운영했다.

# 16. 빌드 성공과 기능 성공을 구분했다

프로젝트에서 자주 마주친 문제가 있었다.

Frontend build는 성공하고 Backend compile도 성공했는데 실제 API 호출은 실패하는 경우였다.

원인은 여러 가지였다.

- 실행 중인 서버가 오래된 코드일 수 있음
- 최신 DB View가 적용되지 않았을 수 있음
- 개발 DB와 운영 DB의 스키마가 다를 수 있음
- 환경 변수나 프록시 설정이 다를 수 있음
- CORS 설정이 실제 실행 환경과 맞지 않을 수 있음

그래서 검증 단계를 다음처럼 분리했다.

```text
코드 작성
↓
Frontend build / Backend compile
↓
애플리케이션 기동
↓
API 호출
↓
실 DB 조회
↓
Bruno 확인
↓
브라우저 확인
↓
장치 또는 운영 환경 확인
```

한 단계가 성공했다고 다음 단계까지 성공한 것으로 기록하지 않았다.

이 기준은 기술적으로도 중요했지만 팀 운영에서도 중요했다.

발표 전 “완료된 줄 알았는데 실제로는 안 된다”는 상황을 줄일 수 있었기 때문이다.

# 17. 팀 규모가 줄었을 때 기능 수보다 흐름 완성을 선택했다

프로젝트 후반에는 최종 인원이 2명이 됐다.

초기 계획의 모든 기능을 같은 수준으로 완성하기는 현실적으로 어려워졌다.

이 시점에서 단순히 각자 더 많은 기능을 가져가는 방식보다 **우선순위를 다시 정하는 것**이 필요했다.

관리자 영역에서는 다음 흐름이 끊기지 않는 것을 우선했다.

```text
메뉴·재료
→ 품절
→ 주문
→ 결제
→ 관리자 주문 처리
→ 취소
→ 매출
→ 대시보드
```

새로운 화면을 계속 추가하기보다 이미 구현한 기능이 실제 API·DB까지 연결되고 서로 같은 데이터를 사용하는지 확인하는 데 더 많은 시간을 사용했다.

기기 출력과 RTOS 연결은 핵심 웹 운영 흐름 이후의 확장 기능으로 배치했다.

이 경험을 통해 프로젝트 관리에서는 기능의 개수보다 **사용자가 끝까지 수행할 수 있는 흐름을 완성하는 것**이 더 중요하다는 것을 배웠다.

---

# 18. 웹 관리자에서 RTOS까지 이어지는 구조를 정리했다

프로젝트 후반에는 주문 완료 이후의 기기 출력 흐름까지 확장했다.

웹 서버가 프린터 장치를 직접 제어하게 만들기보다 `device_event`를 통해 출력 명령을 저장하고 RTOS가 이를 폴링하는 구조로 정리했다.

```text
관리자 영수증 재출력 요청
↓
device_event 생성
↓
RTOS pending event polling
↓
CommandPollTask
↓
WorkerTask
↓
handle_print_receipt
↓
출력
↓
finish / result report
```

Web과 Device가 서로 직접 강하게 결합되지 않게 한 구조다.

관리자에서는 출력 요청을 만들고 상태를 보여 주며, RTOS는 자신이 처리할 이벤트를 가져가 수행한다.

실제 프린터 장치 검증은 별도 검증 대상으로 남겼다.

이 기능 역시 **API가 만들어졌다는 것과 장치에서 실제 출력됐다는 것을 구분**해 기록했다.

---

# 19. PWA와 개발환경 문제도 운영 관점에서 다뤘다

관리자 화면은 단순 웹페이지뿐 아니라 PWA 형태의 운영 가능성도 고려했다.

React/Vite 환경에서 `vite-plugin-pwa`와 관련된 개발 서버 문제, 환경 변수, `/api` 프록시, CORS 등을 확인했다.

이런 문제들은 기능 자체와 직접적인 관계가 없어 보이지만 실제 사용 환경에서는 중요하다.

개발자의 로컬에서는 동작하지만 다른 환경에서 실행되지 않는다면 운영 가능한 기능이 아니기 때문이다.

따라서 코드만 맞추는 것보다

```text
개발 환경
실행 서버
API 주소
브라우저
Backend CORS
DB
```

가 같은 기준을 바라보도록 정리했다.

---

# 20. 실패한 시도를 숨기지 않고 다음 판단 근거로 사용했다

프로젝트에서는 모든 수정이 성공하지 않았다.

대시보드 최적화 과정에서 특정 View 변경은 기대와 달리 성능이 나빠졌다.

DB View 컬럼과 코드가 맞지 않아 API가 실패한 경우도 있었다.

기존 명세와 실제 DB가 달라 다시 계약을 확인해야 했던 경우도 있었다.

이런 일을 단순히 시행착오로 지우기보다 다음 의사결정의 근거로 남겼다.

특히 성능 개선에서는

```text
가설
→ 변경
→ 실측
→ 효과 없음 또는 악화
→ 원복
→ 다른 병목 탐색
```

방식으로 접근했다.

결과적으로 무엇이 맞았는지만큼 **왜 어떤 방법을 버렸는지**도 알 수 있게 했다.

# 21. 문서는 보고서가 아니라 프로젝트 운영 도구로 사용했다

프로젝트의 WBS, daily, 상세 entry, 회의록, Bruno, DB 문서를 서로 연결했다.

기능 상태는 단순한 체크박스로만 관리하지 않았다.

예를 들어

**“매출 API 완료”**

라고 적는 대신

```text
Controller 구현
Service 구현
Mapper 구현
컴파일 확인
실 DB 호출 확인
브라우저 연결 여부
미검증 항목
```

을 나눠 기록했다.

이 기록 방식은 다른 사람에게 보여주기 위한 포트폴리오용 기록이 아니라 실제 프로젝트 진행 중 사용한 방식이었다.

팀원이 해당 기능을 이어받을 때 코드만 열어보고 추측하지 않아도 현재 상태를 파악할 수 있게 하는 것이 목적이었다.

# 23. 내가 보여 준 개발 방식

## 개발자로서

화면에서 발생한 문제를 화면에서만 해결하지 않았다.

API, Service, Mapper, DB까지 따라가 실제 책임이 어디에 있는지 확인했다.

설계가 잘못됐다면 Front에서 우회 코드를 넣기보다 계약을 다시 정리했다.

## 서비스 기획 관점에서

요구사항을 그대로 구현하지 않았다.

“품절 관리”, “매출”, “취소” 같은 기능명을 실제 매장에서 발생하는 상황과 행동 기준으로 다시 구체화했다.

사용자에게 필요하지 않은 복잡도는 화면에서 줄이고, 향후 필요한 확장성은 데이터 구조에 남겼다.

## 팀원으로서

역할을 구분하되 서로 만나는 지점은 먼저 정리했다.

특히 API·DB 계약, WBS, 현재 검증 상태를 문서로 남겨 다른 사람이 이어서 작업할 수 있는 상태를 만들려고 했다.

## 프로젝트 운영 관점에서

팀 규모와 일정이 바뀌면 초기 계획을 그대로 밀지 않았다.

새 기능의 개수보다 사용자가 처음부터 끝까지 수행할 수 있는 핵심 흐름을 우선했다.

## 품질 관점에서

내가 보장할 수 없는 것은 완료라고 표현하지 않았다.

컴파일 성공과 실제 동작을 구분했고, mock과 실 API를 구분했으며, Web API 구현과 실제 RTOS 장치 검증도 분리했다.

# 24. 이 프로젝트에서 배운 점

### 요구사항은 개발하면서 계속 구체화된다

처음부터 완벽한 명세가 주어지는 경우는 드물었다.

실제 데이터와 사용 흐름을 연결하면서 새로운 질문이 생겼고, 그것을 다시 정책과 설계에 반영해야 했다.

### 데이터의 사실과 화면의 표현은 다르다

DB는 실제 발생한 사실을 저장하고, Service와 Frontend는 사용자가 이해할 수 있는 형태로 가공한다.

시간대별 매출의 빈 구간을 처리하면서 이 책임 구분을 명확하게 경험했다.

### API는 단순한 데이터 전달 통로가 아니다

Front와 DB의 책임을 어디에서 나눌지 정하는 계약이다.

계약이 불분명하면 화면마다 예외 코드가 늘어나고 변경 영향 범위가 커진다.

### 성능 개선은 SQL만의 문제가 아니다

대시보드 문제를 해결하면서 어떤 데이터를 왜 조회하는지 다시 정의하는 것 자체가 최적화라는 것을 배웠다.

### 운영 시스템에서는 예외 상태가 정상 상태만큼 중요하다

데이터가 없거나, 주문을 취소할 수 없거나, API가 실패했을 때 사용자가 다음에 무엇을 해야 하는지까지 고려해야 실제 업무 도구가 된다.

### 프로젝트에서는 “완료”의 정의가 중요하다

코드 작성, 빌드, API 호출, DB 반영, 브라우저 검증, 실제 장치 테스트는 서로 다른 단계다.

이를 구분하는 것만으로도 협업 중 많은 오해를 줄일 수 있었다.

# 28. 면접용 1분 소개

ASAK 프로젝트에서는 관리자 시스템을 중심으로 기획부터 화면, API, DB 계약까지 연결했습니다.

제가 이 프로젝트에서 가장 중요하게 생각한 것은 **화면이 보이는 것과 실제 운영 가능한 기능을 구분하는 것**이었습니다.

예를 들어 품절 기능은 단순 토글로 구현하지 않고 메뉴·재료·옵션의 데이터 구조와 실제 운영자가 보는 화면 정책을 분리했습니다. 매출 역시 차트를 먼저 만들기보다 관리자에게 필요한 판단 기준을 정리하고 요약·월별·일별·시간대 API를 역할별로 분리했습니다.

실제 데이터를 연결하면서 없는 날짜와 시간대 처리, 취소 매출, 응답 구조 문제도 발견했고 이를 Front에서 임시 보정하지 않고 DB·Service·API의 책임으로 다시 나눴습니다.

대시보드는 처음 실 DB 조회가 약 8초 걸렸는데 조회 횟수를 줄이고 병목을 측정하면서 개선했고, 효과가 없던 View 변경은 다시 원복했습니다. 이후 최근 주문 조회 구조를 바꿔 최종적으로 약 0.43~0.50초까지 줄였습니다.

프로젝트를 하면서 코드를 작성하는 것뿐 아니라 모호한 요구를 운영 정책으로 바꾸고, 우선순위를 조정하고, 검증 근거를 남기는 방식으로 일했습니다.

# 29. 면접에서 강조할 수 있는 사례

### “직접 기획한 부분이 있나요?”

품절 기능이 대표적입니다. 처음에는 단순히 품절 관리라는 요구만 있었는데 실제 구현을 위해서는 메뉴, 재료, 옵션 중 어디까지 관리할지 정책이 필요했습니다. 데이터 구조는 세 대상을 통합해서 확장 가능하도록 만들고, 실제 관리자 화면에는 현재 사용성이 높은 메뉴와 재료만 노출하는 방식으로 정리했습니다.

### “성능 개선 경험이 있나요?”

관리자 대시보드가 실 DB에서 약 8초 걸렸습니다. 단순히 로딩 UI를 추가하지 않고 실제 DB 호출을 측정했습니다. 처음에는 호출 수를 10회에서 6회로 줄여 3초대로 개선했고, 이후 View 변경도 테스트했지만 더 느려져 원복했습니다. 최종적으로 최근 주문 조회가 병목이라는 것을 확인해 Mapper를 베이스 테이블 직접 조회로 변경했고 약 0.43~0.50초까지 개선했습니다.

### “협업할 때 중요하게 생각한 것이 있나요?”

완료 상태를 모호하게 공유하지 않는 것입니다. UI, mock, API, DB, 브라우저, 실제 장치 검증을 각각 구분했습니다. 그리고 daily에는 진행 상황을, 상세 entry에는 의사결정과 검증 근거를 남겨 다른 사람이 작업을 이어받아도 현재 상태를 알 수 있게 했습니다.

### “기획과 개발이 충돌한 경험이 있나요?”

매출 시간대 차트에서 실제 주문이 없는 시간은 DB에 데이터 자체가 존재하지 않았습니다. 화면만 보면 빠진 데이터처럼 보이기 때문에 처음에는 어디에서 처리할지 고민했습니다. 실제 사실 데이터는 DB에 유지하고, Service가 영업시간을 기준으로 빈 시간대를 0으로 채우도록 책임을 나눴습니다.

# 32. 포트폴리오에서 보여주고 싶은 개발자상

나는 주어진 화면을 그대로 구현하는 개발자보다 **왜 필요한 기능인지 이해하고, 실제 사용 흐름까지 확인하는 개발자​**가 되고 싶다.

요구사항이 모호하면 질문을 구체화하고, 데이터 구조가 맞지 않으면 화면에서 임시로 숨기지 않는다.

문제를 발견하면 어느 계층이 책임져야 하는지 확인하고, 시도한 해결책이 효과가 없으면 측정 결과를 바탕으로 다시 되돌린다.

그리고 내가 만든 코드가 다음 사람에게 넘어갔을 때도 왜 그렇게 만들었는지 이해할 수 있도록 근거를 남긴다.

ASAK은 규모가 큰 상용 프로젝트는 아니었지만, 이 프로젝트를 통해 **기능 구현뿐 아니라 요구사항 해석, 운영 정책, 데이터 계약, 성능, 검증, 협업 기록까지 하나의 개발 과정으로 보는 경험​**을 했다.
