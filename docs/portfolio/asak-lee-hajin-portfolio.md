# ASAK 개인 포트폴리오 — 이하진

> 샐러드 키오스크와 관리자 운영 시스템, ASAK  
> 2026.07.01 ~ 2026.08.21  
> 맡은 영역: 디자인 시스템·Figma, 관리자 화면, 관리자 API·DB 계약, 운영 문서와 검증

## 한 줄 소개

**화면을 만드는 데서 멈추지 않고, 매장 직원이 믿고 사용할 수 있는 운영 흐름인지 끝까지 확인하는 개발자입니다.**

ASAK에서는 Figma와 React 화면 구조를 만드는 단계부터 참여해, 이후 관리자 시스템을 전담했습니다. 주문·메뉴·품절·결제·매출이 각각 따로 보이는 페이지가 아니라 실제 매장에서 하나의 흐름으로 이어진다는 점을 기준으로, 기획·화면 설계·API·DB·검증 기록을 함께 다뤘습니다.

## 내가 일하는 방식

### 사용자의 다음 행동을 먼저 생각합니다

관리자 화면은 예쁜 대시보드가 아니라 바쁜 직원이 주문을 처리하고, 판매 불가 메뉴를 막고, 매출을 판단하는 도구라고 생각했습니다. 그래서 기능을 만들 때 “버튼이 눌리는가”보다 다음을 먼저 확인했습니다.

- 이 정보가 지금 직원의 판단에 필요한가
- 잘못된 상태에서 조작할 수 있지는 않은가
- 데이터가 없거나 오류가 나면 다음 행동을 알 수 있는가
- 앞 단계의 데이터가 다음 화면까지 일관되게 이어지는가

예를 들어 품절은 단순 토글이 아니라 메뉴와 재료의 판매 상태가 주문 가능 여부에 미치는 문제로, 주문 취소는 버튼 하나가 아니라 주문·결제 상태를 함께 바꾸는 문제로 보았습니다.

### “보인다”와 “운영된다”를 구분합니다

프로젝트에서 가장 중요하게 지킨 기준은 UI가 보인다고 기능이 완료된 것은 아니라는 점이었습니다. 정적 UI, mock 연결, API 계약, 백엔드 구현, DB 반영, 실 DB 조회, 브라우저 검증, 장치 검증을 각각 다른 상태로 기록했습니다.

이 기준 덕분에 발표나 협업 중 화면은 있지만 mock인 기능, 컴파일은 되지만 운영 DB에 적용되지 않은 기능을 구분할 수 있었습니다. 환불처럼 실제 API가 준비되지 않은 기능은 화면이 있더라도 완료로 표현하지 않았습니다.

### 문제를 발견하면 책임 계층까지 따라갑니다

데이터가 화면에 보이지 않거나 수치가 다를 때 프론트엔드에서 임시로 맞추지 않았습니다. React 화면 → API → Controller → Service → Mapper → DB View 순으로 원인을 확인하고, 어느 계층이 책임져야 하는지 다시 정했습니다.

이 방식은 단기적으로는 더 많은 확인이 필요하지만, 같은 문제가 다음 화면이나 다음 기능에서 반복되는 것을 줄였습니다.

## 프로젝트에서 맡은 역할

| 시기 | 역할과 기여 |
| --- | --- |
| 프로젝트 초반 | front/back/pipeline 책임 분리, 다중 저장소 운영 방식, daily·상세 entry 작업기록 체계와 온보딩 기준 정리 |
| 디자인 단계 | 키오스크·관리자 Figma 화면과 공통 컴포넌트·디자인 시스템 설계, Figma Variant를 React props·화면 상태로 매핑 |
| 구현 전환 | React/Vite·mock 기반을 API 교체 가능한 구조로 정리하고, mock·실제 API·DB 검증 상태를 분리 |
| 관리자 전담 | Live 주문·상세·상태변경·취소, 메뉴 CRUD·영양·재료·soft delete, 품절·결제수단·매출·대시보드 연결 |
| 운영 확장 | Cloudinary 이미지 흐름, Admin PWA, `device_event` API와 RTOS 영수증 출력 연결 가이드, WBS·API·DB 문서 정합화 |

최종 2인 팀에서 나는 관리자(`admin`) 도메인을 중심으로 책임졌고, 고객(`user`) 주문 세션은 팀원 담당과 구분해 협업했습니다.

## 대표 경험 1 — 요구사항을 운영 정책으로 구체화

“품절 관리”라는 요구는 곧바로 구현할 수 있는 명세가 아니었습니다. 메뉴만 품절인지, 재료도 품절인지, 옵션까지 포함하는지, 화면에는 무엇을 보여 줄지 결정이 필요했습니다.

나는 데이터 모델과 화면 정책을 분리했습니다. `vw_soldout_catalog` View에서 메뉴·재료·옵션 항목을 공통 구조로 조회할 수 있게 했고, 관리자 화면은 실제 사용 빈도가 높은 메뉴·재료만 탭으로 노출했습니다. 옵션은 API와 View에 남겨 확장 가능성을 지키되, 현재 운영 화면은 단순하게 유지했습니다.

```text
관리자 품절 화면
  → soldOutApi / useSoldOutDraft
  → GET·PATCH /api/admin/soldOut
  → AdminSoldOutService / AdminSoldOutMapper
  → vw_soldout_catalog
  → menu · ing · opt_item
```

이 경험을 통해 한 줄 요구사항을 그대로 화면으로 옮기기보다, 사용자에게 필요한 경험과 미래 확장을 함께 설계하는 법을 배웠습니다.

## 대표 경험 2 — 매출을 차트가 아닌 운영 판단의 문제로 설계

매출 화면은 하나의 숫자를 보여주는 일이 아니라, 관리자가 오늘의 상태와 기간별 변화를 판단하도록 돕는 일입니다. 그래서 조회 목적에 따라 API를 분리했습니다.

| 목적 | API |
| --- | --- |
| 매출 요약 | `GET /api/admin/sales/summary` |
| 월별 매출 | `GET /api/admin/sales/monthly` |
| 일별 합계 | `GET /api/admin/sales/daily` |
| 시간대별 매출 | `GET /api/admin/sales/daily/time-slots` |

특히 시간대별 매출은 DB에 실제 주문이 발생한 데이터만 저장하고, 서비스 계층에서 영업 시간 `10:00~22:00`의 빈 구간을 `0`으로 채웠습니다. 데이터베이스의 사실을 훼손하지 않으면서, 차트에서 “값 누락”과 “매출 없음”을 구분하도록 한 선택입니다.

매출 조회를 실제 DB와 연결하면서 발견한 날짜·시간대·응답 형태 문제는 화면에서 임시 처리하지 않고 DB, Service, API, Frontend의 책임으로 나눠 재설계했습니다. 그 결과 기능이 늘어도 화면 코드가 집계 규칙을 과도하게 떠안지 않도록 했습니다.

## 대표 경험 3 — 성능을 로딩 화면으로 감추지 않음

관리자 대시보드의 실제 DB 조회가 약 8초 걸리는 문제를 확인했을 때, 로딩 UI를 추가하는 것으로 끝내지 않았습니다. 화면에서 정말 필요한 값, DB에서 집계할 값, 이미 조회한 값으로 만들 수 있는 정보를 구분해 조회 구조를 다시 설계했습니다.

초기에는 DB 호출을 10회에서 6회로 줄여 약 3.7~3.9초까지 개선했습니다. 이후 View를 바꾸는 시도가 오히려 느려진 것도 측정으로 확인해 즉시 원복했고, 최종적으로 Mapper의 최근 주문 조회를 베이스 테이블 직접 조회로 바꿔 **실 DB 기준 약 8초에서 0.43~0.50초**까지 줄였습니다.

이 경험은 성능 개선이 단순히 쿼리 한 줄을 고치는 일이 아니라, 화면·API·데이터 흐름의 책임을 다시 묻는 일이라는 점을 알려주었습니다. 느려진 시도도 숨기지 않고 원인과 원복 근거를 남긴 점은, 결과뿐 아니라 과정에도 책임지는 개발 방식의 기준이 되었습니다.

## 대표 경험 4 — 팀이 오래 함께 일할 수 있도록 기록을 남김

팀 규모가 줄어든 후에는 모든 기능을 같은 깊이로 만들기보다, 매장 운영 흐름을 끊지 않는 우선순위를 합의했습니다.

```text
메뉴·재료 관리 → 품절 → 고객 주문 → 결제
→ 관리자 주문 처리 → 주문 완료 → 매출 집계 → 영수증·기기 출력
```

daily에는 오늘의 작업·블로커·다음 계획을, 상세 entry에는 변경 이유·구현 범위·API/DB 계약·검증 결과·미검증 항목을 남겼습니다. WBS, Git 이력, Bruno, 회의록을 연결해 팀원이 현재 상태를 다시 확인할 수 있게 했습니다.

문서를 보고서가 아니라 협업 도구로 사용한 덕분에, 팀원이 작업의 배경과 남은 위험을 이해한 상태에서 이어갈 수 있었습니다.

## 개발자·직원·팀원으로서의 강점

| 관점 | 내가 보여 준 태도 |
| --- | --- |
| 개발자 | 화면 문제를 임시 처리하지 않고 데이터 흐름과 책임 계층까지 추적합니다. 실패한 최적화도 원인과 원복 근거를 남깁니다. |
| 직원 | 기능 수보다 실제 사용자의 업무 흐름과 신뢰를 우선합니다. 아직 보장하지 못하는 기능은 완료처럼 말하지 않습니다. |
| 팀원 | 역할 경계를 분명히 하되, API·DB·문서의 접점은 먼저 정리합니다. 작업 상태와 블로커를 남겨 다음 사람이 안전하게 이어갈 수 있게 합니다. |
| 문제 해결자 | 모호한 요구를 운영 정책으로 구체화하고, 발생한 문제를 다음 설계에 반영합니다. |

## 프로젝트를 통해 배운 점

- 좋은 요구사항은 한 줄 기능명이 아니라, 사용자·데이터·예외 상태·검증 기준까지 포함해야 한다.
- API는 프론트와 DB 사이의 단순 통로가 아니라 책임을 나누는 계약이다.
- 운영 시스템에서는 Empty, Error, Disabled 상태가 정상 화면만큼 중요하다.
- 완료는 컴파일 성공이 아니라 구현, 데이터, 브라우저, 운영 환경에서 확인 가능한 기준으로 판단해야 한다.

## 면접에서 말할 수 있는 소개

### 30초 버전

ASAK 샐러드 키오스크 프로젝트에서 관리자 시스템을 전담했습니다. Figma와 React 화면 구조부터 시작해 주문·메뉴·품절·매출·대시보드를 Spring Boot API와 MySQL까지 연결했습니다. 제가 중요하게 생각한 것은 화면 구현보다 실제 매장 운영 흐름이었고, 기능의 구현·실DB·브라우저 검증 상태를 구분해 관리했습니다. 대시보드는 실 DB 기준 약 8초였던 조회를 0.5초 내외로 개선한 경험이 있습니다.

### 1분 버전

ASAK에서 저는 관리자 화면을 만드는 역할을 넘어, 직원이 주문을 처리하고 매출을 판단하는 운영 흐름을 설계했습니다. 요구사항이 모호한 품절·주문 취소·매출 기능은 사용자 화면과 데이터 모델을 분리해 운영 정책으로 구체화했고, 프론트의 임시 보정 대신 API·Service·Mapper·DB View까지 책임을 나눴습니다.

또한 정적 UI, mock, API 구현, DB 반영, 실환경 검증을 구분해 기능 상태를 투명하게 공유했습니다. 대시보드가 느릴 때도 로딩 화면으로 감추지 않고 조회 구조를 재설계해 실 DB 기준 약 8초에서 0.43~0.50초까지 개선했습니다. 문제를 끝까지 확인하고, 다음 팀원이 안전하게 이어갈 수 있게 근거를 남기는 방식으로 일합니다.

## 기술은 문제를 해결하기 위한 도구였습니다

React·Vite, Spring Boot·Java, MyBatis, MySQL·SQL View, Figma, Bruno, Cloudinary, PWA, Git/GitHub를 사용했습니다. 다만 기술 자체보다, 각 도구가 화면·운영 데이터·팀 협업을 어떻게 더 안정적으로 연결하는지에 집중했습니다.
