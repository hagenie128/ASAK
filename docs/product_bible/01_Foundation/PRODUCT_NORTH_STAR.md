## 원문: `PRODUCT_PRINCIPLES.md`

### ASAK Product Principles

> Status: Current

#### 1. Product Before Decoration

화면을 화려하게 만드는 것보다 사용자가 행동을 완료하게 만드는 것이 우선이다.

판단 순서:

1. 사용자 목적
2. 정보 우선순위
3. 오류·복구
4. 데이터 정합성
5. 컴포넌트 재사용
6. 시각적 완성도
7. 모션과 장식

---

#### 2. One Screen, One Decision

각 화면은 사용자가 내려야 하는 하나의 결정에 집중한다.

| Screen | Main Decision |
|---|---|
| Home | 어디에서 먹을 것인가 |
| Menu List | 어떤 메뉴를 고를 것인가 |
| Menu Detail | 어떻게 구성할 것인가 |
| Cart | 이 주문으로 결제할 것인가 |
| Payment | 어떤 방식으로 결제할 것인가 |
| Complete | 주문이 정상 접수되었는가 |
| Dashboard | 지금 매장 상태는 어떤가 |
| Order Board | 어떤 주문을 먼저 처리할 것인가 |
| Sales | 매장 성과가 어떻게 변했는가 |

---

#### 3. State Is Part of the Product

Default 화면만 디자인된 기능은 완료된 기능이 아니다.

주요 화면은 필요에 따라 다음 상태를 가진다.

- default
- loading
- empty
- error
- disabled
- selected
- processing
- success
- validationError

---

#### 4. Recovery Over Blame

오류 메시지는 사용자의 잘못을 지적하지 않는다.

잘못된 예:

- 잘못 입력했습니다.
- 선택이 틀렸습니다.

권장:

- 필수 옵션을 선택해주세요.
- 결제가 완료되지 않았어요. 다시 시도하거나 다른 결제수단을 선택해주세요.

---

#### 5. Server Is the Price Authority

클라이언트가 전달한 금액은 신뢰하지 않는다.

- 화면은 예상 금액을 계산한다.
- 서버는 메뉴·옵션 가격을 다시 계산한다.
- 불일치 시 결제를 진행하지 않는다.
- 사용자에게 변경된 금액을 명확히 안내한다.

---

#### 6. Green Is an Accent

브랜드 초록은 다음에만 사용한다.

- 주요 CTA
- 선택 상태
- 성공 상태
- 핵심 그래프 강조
- 활성 Navigation

사용하지 않는다.

- 모든 KPI 숫자
- 삭제·취소
- 모든 카드 배경
- 라임 glow
- 의미 없는 장식

---

#### 7. Food and Data Are the Heroes

Kiosk에서는 음식이 주인공이다.

Admin에서는 데이터가 주인공이다.

UI는 음식과 데이터의 해석을 돕는 역할만 한다.

---

#### 8. Design Must Survive Implementation

Figma에서만 가능한 표현은 지양한다.

모든 디자인은 다음 질문을 통과해야 한다.

- React 컴포넌트로 분리 가능한가?
- 상태를 props로 표현 가능한가?
- API 응답으로 채울 수 있는가?
- 데이터가 길어져도 깨지지 않는가?
- 모바일이 아니라 고정 Kiosk/Admin 캔버스에서 안정적인가?

---

#### 9. No Hidden Business Logic

정책은 UI 안에 암묵적으로 숨기지 않는다.

예:

- 품절 전파
- 타임아웃
- 결제 실패 시 장바구니 유지
- TTS 중복 호출
- 매출 비교 기준
- 취소·환불 상태 전이

모든 정책은 Feature 문서와 상태 계약에 기록한다.

---

#### 10. Scope Discipline

MVP와 확장 기능을 구분한다.

확장 기능을 화면에 보여줄 경우:

- Mock
- 연결 예정
- 비활성
- 확장 설계

중 하나임을 명확히 한다.

실제 API가 없는 기능을 완성된 기능처럼 표현하지 않는다.

## 원문: `PRODUCT_VISION.md`

### ASAK Product Vision

> Status: Current
> Version: 1.0
> Product: ASAK — A Salad A Kiosk

#### 1. 제품 정의

ASAK는 샐러드 매장의 주문 경험과 운영 경험을 하나로 연결하는 키오스크 기반 주문·운영 플랫폼이다.

고객에게는 복잡한 옵션 주문을 빠르고 직관적으로 제공하고, 관리자에게는 주문·품절·메뉴·결제·매출 상태를 짧은 시간 안에 판단할 수 있는 운영 도구를 제공한다.

ASAK가 해결하려는 핵심 문제는 단순히 “키오스크 화면이 예쁘지 않다”가 아니다.

샐러드 주문은 일반 패스트푸드보다 다음 복잡성이 크다.

- 베이스, 토핑, 드레싱, 제외 재료 등 선택 단계가 많다.
- 필수 옵션과 선택 옵션이 섞이기 쉽다.
- 재료 품절이 메뉴·카테고리·옵션에 연쇄 영향을 준다.
- 가격과 영양정보가 선택에 따라 달라진다.
- 주문 완료 후 고객이 체감할 수 있는 대기 정보가 필요하다.
- 관리자는 실시간 주문과 매장 전체 상태를 동시에 확인해야 한다.

따라서 ASAK의 본질은 **선택이 많은 주문을 실수 없이 끝내게 만드는 제품**이다.

---

#### 2. 제품 비전

> 누구나 설명 없이 주문을 완료하고, 관리자는 3초 안에 매장 상태를 파악할 수 있는 샐러드 주문 운영 플랫폼을 만든다.

---

#### 3. 제품 목표

##### 고객

- 다음 행동을 고민하지 않아도 자연스럽게 주문할 수 있다.
- 옵션을 선택하거나 제외할 때 현재 선택 상태와 가격 변화를 바로 이해한다.
- 결제 실패나 품절 상황에서도 처음부터 다시 시작하지 않는다.
- 주문 완료 후 예상시간 대신 실제 체감에 가까운 대기 주문 수를 확인한다.

##### 관리자

- 로그인 후 매장 상태를 한 화면에서 파악한다.
- 진행 중 주문, 품절, 매출, 인기 메뉴를 빠르게 확인한다.
- 메뉴·재료·옵션의 품절 영향을 이해하고 안전하게 저장한다.
- 데이터가 없거나 불러오기 실패한 상황에서도 다음 행동을 알 수 있다.

---

#### 4. 핵심 사용자

##### Primary

- 샐러드 주문에 익숙하지 않은 첫 방문 고객
- 빠른 주문을 원하는 재방문 고객
- 노년층 및 디지털 기기 사용이 익숙하지 않은 고객
- 여러 옵션을 꼼꼼히 확인하려는 고객

##### Secondary

- 점주
- 매장 관리자
- 조리 담당 직원
- 메뉴·품절·매출을 관리하는 운영 담당자

---

#### 5. 핵심 가치

##### Clear

한 화면에는 하나의 핵심 목적만 둔다.

##### Recoverable

실패를 막는 것뿐 아니라 실패 후 쉽게 복구할 수 있어야 한다.

##### Consistent

가격, 상태, 명칭, 화면 흐름이 Figma·React·API·DB에서 동일해야 한다.

##### Fresh

브랜드의 신선함은 장식보다 색상, 음식 이미지, 여백, 카피에서 표현한다.

##### Operational

관리자 화면은 포트폴리오용 장식이 아니라 실제 운영 판단을 돕는 구조여야 한다.

---

#### 6. 제품 차별점

1. 샐러드 특화 옵션 구조
2. 재료 역할에 따른 품절 전파 정책
3. 장바구니 옵션 수정과 안전한 삭제
4. 대기 주문 수 기반 완료 안내
5. 실시간 주문 보드와 관리자 대시보드 분리
6. 조리 완료 TTS 호출
7. 접근성 모드
8. 메뉴·재료·옵션·영양·알레르기 연결
9. Figma에서 React·API·DB까지 추적 가능한 문서 체계

---

#### 7. MVP 범위

##### Kiosk

- 주문 유형 선택
- 메뉴 탐색
- 메뉴 옵션 선택
- 장바구니
- 결제
- 주문 완료
- 결제 실패
- 타임아웃
- 접근성

##### Admin

- 로그인
- Dashboard
- 실시간 주문 보드
- 주문 관리
- 품절 관리
- 메뉴 관리
- 결제수단 관리
- 매출 요약
- 월별 매출
- 일별 매출

##### MVP 제외 또는 확장

- 실제 PG 결제
- 실물 영수증 프린터 연동
- 멤버십·쿠폰
- WebSocket 자동 동기화
- 외부 AI TTS
- 프랜차이즈 다점포 통합

---

#### 8. 성공 기준

- 고객 핵심 주문 흐름이 끊기지 않는다.
- 화면 간 금액이 모두 일치한다.
- 관리자 Dashboard는 3초 안에 이해 가능하다.
- 주요 관리 액션은 10초 안에 수행 가능하다.
- Default·Loading·Empty·Error 상태가 존재한다.
- Figma와 React 컴포넌트가 중복 없이 매핑된다.
- API 응답과 DB 상태값이 UI와 동일하다.
- P0 이슈가 0건이다.

## 원문: `UX_PHILOSOPHY.md`

### ASAK UX Philosophy

> Status: Current

#### 1. UX 목표

ASAK의 UX는 사용자가 빠르게 누르는 경험보다 **실수 없이 끝내는 경험**을 목표로 한다.

샐러드 주문은 선택지가 많기 때문에 클릭 수만 줄이면 오히려 오류가 커질 수 있다.

따라서 ASAK는 다음을 우선한다.

- 현재 선택 상태를 명확히 보여주기
- 필수와 선택을 구분하기
- 추가와 제외를 구분하기
- 가격 변화를 바로 보여주기
- 실패 시 이전 선택을 유지하기
- 다음 행동을 한 개로 제한하기

---

#### 2. Kiosk UX Rules

##### 터치

- 최소 터치 영역 80 × 80px
- 주요 CTA 높이 100~120px
- 작은 텍스트 링크로 핵심 행동을 제공하지 않는다.

##### 정보

- 메뉴 카드에는 이미지, 메뉴명, 가격, 칼로리, 품절 여부를 제공한다.
- 옵션 선택은 그룹별로 분리한다.
- 필수 여부와 선택 가능한 개수를 항상 표시한다.
- 장바구니에서는 옵션 전체를 과도하게 펼치지 않고 요약한다.

##### 흐름

- 뒤로 가도 선택 상태를 유지한다.
- 결제 실패 시 장바구니를 유지한다.
- 완료 후에는 주문번호와 대기 주문 수를 우선한다.
- 타임아웃 전에 경고와 계속 주문 선택지를 제공한다.

---

#### 3. Admin UX Rules

##### Dashboard

로그인 직후 주문 목록 하나만 보여주지 않는다.

관리자는 다음을 동시에 판단해야 한다.

- 오늘 매출
- 주문 수
- 평균 객단가
- 진행 중 주문
- 품절
- 인기 메뉴

따라서 SCR-022 Dashboard를 별도 화면으로 둔다.

##### Live Order Board

실시간 조리 업무에 집중한다.

- 접수
- 준비 중
- 완료
- TTS 호출

##### Order Management

검색·필터·기간·상세 확인에 집중한다.

실시간 보드와 관리 목록은 목적이 다르므로 같은 화면으로 취급하지 않는다.

---

#### 4. 왜 예상 조리시간 대신 대기 주문 수인가

예상 조리시간은 다음 문제를 가진다.

- 메뉴 구성과 직원 숙련도에 따라 오차가 크다.
- 시스템이 정확한 시간을 계산하기 어렵다.
- 실제보다 늦거나 빠르면 신뢰가 떨어진다.

대기 주문 수는:

- 계산이 단순하다.
- 고객이 현재 혼잡도를 직접 이해할 수 있다.
- 잘못된 시간 약속을 만들지 않는다.

따라서 완료 화면은 `waitingOrderCount`를 사용한다.

---

#### 5. 왜 장바구니에 옵션 수정과 삭제를 분리하는가

두 행동은 결과가 완전히 다르다.

- 옵션 수정: 주문 항목 유지
- 삭제: 주문 항목 제거

한 메뉴나 작은 아이콘에 묶으면 실수 가능성이 높다.

따라서 별도 Action으로 제공하고, 삭제는 ConfirmDialog를 사용한다.

---

#### 6. 왜 TTS를 사용하는가

관리자 화면에서 완료 상태만 바뀌면 고객은 자신의 주문 완료를 알기 어렵다.

TTS는:

- 별도 호출 장비 없이 브라우저에서 구현 가능하다.
- 직원의 반복 호출 부담을 줄인다.
- 주문 완료 흐름을 실제 매장처럼 보여준다.

단, 서버 상태 변경 성공 후에만 호출하며 실패해도 주문 상태는 유지한다.

---

#### 7. 카피 원칙

- 짧다.
- 해결 방법을 포함한다.
- 사용자를 탓하지 않는다.
- 과한 감탄사를 사용하지 않는다.
- 버튼은 행동을 표현한다.

홈 카피:

- 오늘도 아삭아삭
- 당신의 하루를 신선하게

브랜드 톤은 친근하지만 유아적이지 않아야 한다.
