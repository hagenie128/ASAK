# 2026-07-02 ~ 2026-08-21 성장·협업·AI 운영 보강 기록 — 이하진

## 1. 기록 목적

이 entry는 기존 daily와 기능별 entry에 이미 남아 있는 코드·커밋·실행 근거를 대체하지 않는다. Git 이력만으로는 약하게 남는 의사결정, 협업 조율, 문서 운영, AI 사용 기준과 성장 과정을 보강하기 위한 연결 기록이다.

## 2. 프로젝트 운영 기준의 변화

초기에는 기능 목록과 화면 구현을 중심으로 프로젝트를 보았다. 진행하면서 아래 상태가 서로 다르다는 점을 명확히 관리하게 됐다.

```text
정적 UI → Mock 연결 → API 계약 → Backend 구현 → DB 반영
→ 실 DB 조회 → 브라우저 검증 → 실제 운영·장치 검증
```

`커밋됨`, `빌드됨`, `실행 검증됨`, `설계만 됨`을 같은 완료 상태로 묶지 않았다. 이 기준은 품절·매출·환불·RTOS처럼 여러 저장소와 계층이 연결되는 기능의 현재 상태를 팀에 정확히 공유하는 데 사용했다.

## 3. AI를 생성기가 아니라 검토 도구로 사용

초기에는 계획 초안과 문서 구조화에 AI를 사용했다. 이후에는 Figma·문서·API·DB·코드 사이의 불일치를 찾는 Reviewer와 감사 도구로 역할을 바꿨다.

- 문서보다 실제 코드와 실행 근거를 먼저 확인한다.
- 화면 존재와 기능 완료를 구분한다.
- AI가 범위를 넓히면 현재 스프린트 범위로 다시 좁힌다.
- Figma·계약에 없는 UI/상태를 AI가 임의로 추가하지 않도록 한다.
- DB 삭제와 대규모 구조 변경은 AI 제안만으로 실행하지 않는다.
- 검증하지 않은 것은 worklog에 완료로 쓰지 않는다.

이 원칙은 AI를 많이 쓰는 것보다, 결과의 책임을 사람이 갖는 방식이 중요하다는 학습으로 이어졌다.

## 4. 협업 방식

공용 DB·API·자산·RTOS 변경은 내 코드만 확인하고 끝내지 않았다. 변경이 다른 팀원의 주문 흐름이나 출력 흐름을 깨뜨릴 수 있는지 먼저 확인하고, 기존 기능을 보존한 병행 방식을 우선했다.

예를 들어 RTOS 출력은 기본 `PRINT_RECEIPT` 흐름을 유지하면서 상세 영수증을 위한 `PRINT_RECEIPT_TEXT`를 별도 이벤트로 분리했다. 이미지 영수증과 MMS 전송은 장기 확장 설계로만 기록하고, 실제 구현·발송 검증과 구분했다.

daily에는 당일 작업·블로커·다음 계획을, 상세 entry에는 변경 이유·계약·검증 범위를 남겼다. 이는 팀원이 중단된 작업을 이어받을 때 현재 상태와 위험을 다시 찾을 수 있게 하기 위한 방식이다.

## 5. 문제 해결 방식

문제를 화면 증상 하나로 보지 않고 전체 경로로 분해했다.

```text
UI → Hook/Store → API Adapter → Controller → Service → Mapper/SQL → DB/View
```

태블릿과 RTOS 연결도 Browser secure context, API URL, Vite host/proxy, CORS·방화벽, Spring binding, RTOS polling/Worker, 외부 I/O의 계층으로 나눠 확인했다. 이 방식으로 매출 8초 지연, boolean 직렬화 문제, RTOS JSON escape, 태블릿 LAN 접속처럼 성격이 다른 문제에서도 가설과 검증 범위를 좁혔다.

## 6. 일정과 우선순위 판단

최종 2인 체제가 된 뒤에는 모든 기능을 같은 수준으로 만드는 대신, 매장 운영에 필요한 세로 흐름을 우선했다.

```text
메뉴·재료 → 품절 → 고객 주문 → 결제 → 관리자 주문 처리
→ 매출·대시보드 → 영수증·기기 출력
```

실제 운영에 필요한 주문·메뉴·품절·매출 연결을 먼저 확인하고, 고급 통계, 디지털 영수증, MMS 같은 확장 기능은 설계 또는 후속 단계로 분리했다.
