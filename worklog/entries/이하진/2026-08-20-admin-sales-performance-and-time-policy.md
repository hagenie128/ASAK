# 2026-08-20 관리자 매출 성능·시간대 정책 — 이하진

## 1. 작업 목적

관리자 매출을 화면별 임시 DTO가 아닌 책임별 API로 재구성하고, 실제 DB 기준으로 느린 대시보드 조회 원인을 측정해 개선한다.

## 2. 직접 판단과 구현

- 매출 API를 `dashboard`, `summary`, `monthly`, `daily`, `daily/time-slots`로 분리했다. 화면 표현용 필드를 서버 계약에 넣지 않고, 각 API가 제공할 집계 책임을 명확히 했다.
- 과거 영업시간 안에 주문이 없는 시간대는 `0`으로 보정하되, 미래 월·일·시간은 아직 발생하지 않은 데이터이므로 `0`과 구분해 노출하지 않는 정책을 정리했다.
- 대시보드 조회는 KPI 호출을 통합하고, `vw_sales_daily`·`vw_order_live`를 매번 넓게 집계하던 지점을 Mapper의 베이스 테이블 직접 조회로 바꿨다.

## 3. 성능 측정과 실패 기록

```text
8초
→ KPI 호출 통합: 3.7~3.9초
→ 집계 Mapper 직접 조회: 1.6~1.7초
→ 최근 주문 Mapper 직접 조회: 0.43~0.50초
```

`vw_order_list_summary`를 상관 서브쿼리 방식으로 재작성한 시도는 1.3초에서 6.6~6.8초로 오히려 느려져 즉시 원복했다. raw query가 아니라 실제 View 실행 계획에서 MySQL이 TEMPTABLE로 구체화하는 제약이 원인이었다. 성공한 코드뿐 아니라 실패한 시도와 원복 이유도 남겼다.

## 4. 검증 수준

- 실제 DB 기준 KPI·weeklySales·recentOrders 결과가 기존 View 기준과 일치하는지 비교했다.
- 세부 성능 근거는 `ASAK-back/docs/ai-reports/2026-08-20/dashboard-performance-optimization.md`에 남아 있다.
- 시간대 빈 슬롯·미래 구간 정책은 API와 화면에서 일관되게 적용됐는지 추가 브라우저 검증이 필요하다.

## 5. AI 활용과 성장

AI는 DTO·정책 초안을 검토하고 병목 가설을 나누는 보조로 사용했다. 실제 SQL, 실행 시간, 결과 일치는 DB 측정과 Mapper 코드를 기준으로 판단했다. 성능 문제를 로딩 UI로 감추지 않고 데이터 흐름의 책임을 다시 정의한 경험이다.
