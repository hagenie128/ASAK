## 2. 작업 목적

- 매출 조회 API를 화면마다 임시 DTO를 늘리는 방식 대신 `dashboard / summary / monthly / daily / daily/time-slots`로 책임을 분리한다.
- `GET /api/admin/dashboard`의 8초 응답 시간을 실제 DB 기준으로 원인을 좁혀가며 줄인다.
- 주문이 없는 날짜·시간대와, 아직 도래하지 않은 미래 날짜·시간대를 같은 `0`으로 섞지 않는 응답 정책을 정한다.

## 3. 직접 판단과 구현

- 화면에서만 쓰는 `fill`, `barHeight` 같은 표현용 필드를 서버 계약에 넣지 않고, 월별·일별·시간대 집계를 별도 API 책임으로 분리했다. 시간 간격을 향후 파라미터화할 가능성(`30m`/`1h`)도 함께 검토했다.
- 일별 매출은 실제 주문이 있는 시간 슬롯만 DB에서 조회한 뒤 Service/응답 조립 단계에서 영업시간 기준 30분 슬롯을 채우고, 주문이 없는 슬롯은 `0`으로 보정하는 방향으로 정리했다. 24시간 전체를 채우지 않고 **영업시간 범위 내부만** 대상으로 삼았다.
- 현재 월 이후의 미래 월, 오늘 이후의 미래 날짜, (필요 시) 현재 시각 이후의 시간 슬롯은 `0`이 아니라 **아직 발생할 수 없는 데이터**로 보고 응답/화면에서 제외하는 정책을 정리했다. `0원 매출`과 `아직 존재할 수 없음`을 구분해 차트 해석 오류를 줄이는 것이 목적이다.
- 대시보드 응답속도는 4단계로 좁혔다: ① KPI 4개 호출을 `getDashboardKpi(today, yesterday)` 한 번으로 통합(DB 호출 10→6회) ② Mapper별 소요시간을 임시 타이머로 프로파일링해 병목을 특정 ③ `vw_sales_daily`가 `GROUP BY`로 병합되지 않아 매번 orders 전체(약 5.1만 건)를 집계하던 지점을, 뷰는 그대로 두고 `getDashboardKpi`/`getDashboardWeeklySales` Mapper 쿼리만 `orders`/`payment` 베이스 테이블 직접 조회로 교체 ④ `getDashboardRecentOrders`도 같은 방식으로 베이스 테이블 상관 서브쿼리 직접 조회로 교체.

## 4. 성능 측정과 실패한 시도

```text
8초
→ KPI 호출 통합: 3.7~3.9초
→ 집계 Mapper 직접 조회: 1.6~1.7초
→ 최근 주문 Mapper 직접 조회: 0.43~0.50초 (최종, 약 16~18배)
```

- `vw_order_list_summary`를 상관 서브쿼리 방식으로 재작성해 실제 `CREATE OR REPLACE VIEW`까지 적용했으나 **1.3초 → 6.6~6.8초로 오히려 5배 느려져 즉시 원복**했다.
- 원인: SELECT 목록에 상관 서브쿼리가 있는 뷰는 MySQL이 뷰를 병합(merge)하지 않고 TEMPTABLE로 구체화한다는 제약. 사전 검증을 뷰가 아니라 raw 쿼리로만 측정해 이 함정을 놓쳤다.
- 성공한 최종 코드만 남기지 않고, 왜 이 시도가 실패했는지와 raw 쿼리 검증이 실제 View 실행계획과 왜 달랐는지를 문서로 남겨 다음 쿼리 튜닝의 체크리스트로 삼았다.

## 5. AI 도움 영역

- DTO 구조 초안을 여러 차례 대조하며 화면 전용 필드를 서버 계약에서 제외하고 랭킹 필드명을 통일하는 데 AI를 사용했다.
- 병목 가설을 단계별로 나누는 데 ChatGPT를 보조로 썼지만, 실제 SQL 작성·실행 시간 측정·결과 일치 여부(기존 View 기준과 비교)는 DB 조회로 직접 확인했다.

## 6. 검증 내용

- 3단계(뷰 우회) 결과가 기존 뷰 기준과 완전 일치함을 확인(kpi 1,200~1,400ms→80ms, weeklySales 940~970ms→90ms).
- 4단계 원복 후 `vw_order_list_summary`는 2026-08-20 이전과 동일 정의로 복구됨을 확인. `vw_sales_daily`, `vw_order_live`는 미변경.
- 5단계(recentOrders)는 최근 500건 비교로 기존 뷰 기준과 완전 일치 확인(1.3초→90ms).
- 세부 실측 근거: `ASAK-back/docs/ai-reports/2026-08-20/dashboard-performance-optimization.md`.
- 미검증: 빈 슬롯 `0` 보정과 미래 구간 제외 정책은 이 시점에 코드로 반영되지 않았다(설계·논의만). 30분 단위 시간대 조회는 당일 구현 범위에 포함됐으나, 1시간 단위 선택 기능은 검토만 했다.

## 8. 이번 작업에서 배운 점

- 화면이 필요한 데이터를 한 DTO에 다 담지 않고 책임 단위로 나누면, 이후 화면 요구사항이 바뀌어도 API 전체를 다시 설계하지 않아도 된다.
- 쿼리 성능 개선에서 raw 쿼리 측정과 실제 View 실행계획은 다르게 동작할 수 있다는 점을 실패를 통해 확인했다 — 이후 성능 검증은 반드시 실제 사용 경로(뷰/Mapper) 기준으로 측정하는 습관으로 이어졌다.
- `데이터 없음(0)`과 `아직 존재할 수 없음(미래)`을 같은 값으로 섞으면 차트·KPI 해석이 왜곡된다는 점을 API 설계 단계에서 미리 구분해야 한다는 것을 배웠다.

## 9. 포트폴리오용 요약

관리자 매출 API를 화면별 DTO가 아닌 책임 단위로 재설계하고, 대시보드 응답을 8초에서 0.43~0.50초로 줄이는 과정에서 성공한 최적화뿐 아니라 5배 느려진 실패한 시도와 그 원인(뷰 TEMPTABLE 구체화)까지 근거로 남겼다. 동시에 매출 시간대·미래 구간 노출 정책을 `0`과 `아직 없음`으로 구분해 설계했다.
