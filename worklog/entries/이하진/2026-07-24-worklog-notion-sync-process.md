## 2. 작업 목적

- GitHub에는 기술적 근거(커밋·코드·검증)가, Notion에는 팀이 빠르게 읽는 일일 진행 상황이 각각 따로 쌓이면서 같은 하루의 기록이 서로 다른 말로 표현되는 문제를 줄인다.
- daily를 단순 출석 기록이 아니라 이후 본인의 판단 근거를 복원할 수 있는 자료로 쓰기 위한 최소 기준을 정한다.

## 3. 직접 구현 영역 (판단)

- daily는 `worklog/templates/template-daily-auto.md` 형식을 그대로 따르고, Notion 쪽 일일 기록도 같은 항목명(작업 목적/직접 구현/AI 도움/이슈/검증/포트폴리오 요약)과 상태 표현을 쓰도록 맞췄다.
- 그날 작성한 Notion 워크로그에는 DB View/API 계약/DevCopilot 감사, AI 스킬·코드 그래프·Git 규칙, `.gitignore` 조정, 검증·블로커·내일 계획을 GitHub daily와 같은 구조로 함께 정리했다.
- 산출물 나열에 그치지 않고 AI 도움, 직접 수정한 부분, 이슈, 검증 여부, 포트폴리오 요약을 매일 daily에 남기는 것을 이후 작성 기준으로 삼았다.

## 5. AI 도움 영역

- 커밋 메시지만으로 일기를 생성하게 하지 않고, 기존 GitHub daily/entries와 그날 실제 작업 맥락을 먼저 참고해 같은 구조로 작성하도록 요청했다.
- 항목명과 상태 표현이 GitHub daily 관례와 어긋나면 Notion 쪽 표현을 다시 맞추도록 지시했다.

## 8. 이번 작업에서 배운 점

- 일일 기록이 두 곳(GitHub/Notion)에 있으면 형식이 갈라지기 쉽고, 형식이 갈라지면 "오늘 뭘 했는지"는 남아도 "왜 그렇게 했는지"는 한쪽에서만 읽을 수 있게 된다.
- daily에 완료된 산출물뿐 아니라 AI 활용·직접 판단·미검증 범위를 같이 적어야, 나중에 이 기록만으로 그날의 근거를 복원할 수 있다.

## 11. 포트폴리오용 요약

일일 기록을 "오늘 한 일" 나열에서 "증거 기반 성장 로그"로 바꾸기 위해, GitHub daily와 Notion 일일 기록의 항목명·상태 표현을 통일하는 운영 기준을 정하고 그날 작업에 적용했다.
