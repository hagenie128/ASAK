## 2. 작업 목적

프린터가 없는 현재 시연 환경에서, 별도 `receipt` 테이블이 필요한지와 실제 프린터 없이도 RTOS/IoT 프로젝트 성격을 살릴 수 있는 디지털 영수증 확장 방향을 검토한다.

## 3. 직접 판단 영역

- **영수증 DB 필요성:** 현재 ASAK 시연에서는 별도 `receipt` 테이블이 필수는 아니라고 판단했다. 주문/주문상품/옵션/제외/결제 데이터가 원본이며, 영수증은 이 데이터를 조합한 결과물로 본다.
- **`DeviceEvent`의 역할:** 영수증 원본 저장소가 아니라 RTOS 명령의 `PENDING → PROCESSING → COMPLETED/FAILED` 상태를 관리하는 장치 명령 큐로 구분했다.
- **범위 통제:** "실무에서는 필요하다"는 이유만으로 지금 테이블을 추가하지 않고, 현재 요구사항에 맞는 복잡도만 선택했다. 실제 상용 환경에서 발행 당시 값 고정, 재발행, 취소 영수증, 법적 증빙이 필요해지면 별도 snapshot 테이블을 추가할 수 있다고 정리했다.

## 4. 구현 로직 / 적용한 방식 (확장 설계안)

실제 프린터 없이 RTOS/IoT 성격을 유지하기 위해, Spring이 SMS/MMS를 직접 보내 RTOS를 흐름에서 빼는 대신 아래 구조를 후보로 정리했다.

```text
React
  ↓
Spring Boot
  ↓
DeviceEvent: SEND_RECEIPT_MMS
  ↓
FreeRTOS polling
  ↓
WorkerTask
  ↓
외부 SMS/MMS API 호출
  ↓
사용자 휴대폰
  ↓
RTOS → Spring COMPLETED / FAILED
```

- 이미지 영수증 구성안(후보): 로고, 매장정보, 영수증번호, 상품/옵션/제외, TOTAL, 이벤트/쿠폰, 바코드/QR, 감사 문구.
- Spring이 주문 데이터를 기반으로 영수증 PNG를 생성하고, RTOS가 외부 메시징 I/O를 수행하는 역할 분리를 검토했다.
- 실제 프린터가 생기면 같은 영수증 데이터 계층을 ESC/POS 출력 Adapter로 확장할 수 있는 방향도 함께 검토했다.

## 5. AI 도움 영역

- AI로 프린터 없는 환경에서 IoT 성격을 유지하는 대안 구조(Spring 직접 발송 vs RTOS 경유)를 비교했다.
- 최종적으로 어떤 구조를 후보로 택할지("Spring이 직접 SMS를 보내면 RTOS가 프로젝트에서 빠진다")는 프로젝트의 RTOS/IoT 학습 목적을 기준으로 직접 판단했다.

## 6. 이번 작업에서 배운 점

- "실무에서 쓰는 방식이다"라는 이유만으로 현재 필요하지 않은 테이블·구조를 추가하지 않고, 현재 요구사항에 맞는 최소 복잡도를 선택하는 판단 기준을 재확인했다.
- "프린터가 없어서 콘솔만 출력했다"는 설명보다, 장치 명령을 RTOS가 polling하고 외부 I/O를 수행하며 결과를 서버로 보고하는 구조를 시연하는 편이 RTOS/IoT 학습 목적을 더 잘 보여준다고 판단했다.
