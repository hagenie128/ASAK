## 2. 작업 목적

- Notion 페이지가 늘어나면서 정본을 복제하거나 팀원이 기존 페이지를 임의로 옮기는 문제를 막고, 팀이 필요한 정보에 빠르게 접근하게 한다.
- "화면이 있다", "문서가 있다"만으로 기능을 완료로 표시하지 않도록 완료 판정 기준을 명시적으로 정한다.
- 외부 UI 레퍼런스를 참고할 때 ASAK 고유의 상태 모델을 훼손하지 않는 범위를 정한다.

## 3. 직접 구현 영역

- Notion 최상단 4개 영역에 **안내 페이지**만 1단계로 만들고, 기존 페이지·DB의 이동·삭제·통합은 금지하는 원칙을 세웠다. Figma는 참고 전용으로 두고 구현 정본과 혼동하지 않게 분리했다.
- 검토용 DB View 7개와 안내문 11개를 정리하고, 저장소 링크를 당시 실제 구조(`ASAK-Kiosk`, `ASAK-Admin`, `ASAK-back`)에 맞췄다. 기존 회의록은 옮기지 않고 View만 분리해 접근성을 높였다.
- API는 기존 상세 문서를 보관하되 Canonical Contract 링크를 기준 문서로 지정했다.
- 완료(DONE) 기준을 "코드 + 테스트/실행 + 캡처 또는 PR 등 증거"가 있어야 완료로 올리는 원칙으로 재정의했다. 이 기준은 이후 mock 연결, API 구현, 배포, RTOS 작업까지 계속 재사용됐다.
- 외부 UI Kit/레퍼런스는 ASAK 화면의 대체재로 복제하지 않고 시각 위계·선택 피드백·내비게이션만 참고하기로 했다. ASAK 고유의 옵션/제외/품절/수량제한 상태 모델과 한글 업무 용어는 그대로 유지했다.

## 4. 구현 로직 / 적용한 방식

- Notion IA는 "기존 정본을 옮기지 않고 접근 경로만 새로 만든다"는 원칙으로, 재구성이 아니라 안내 레이어 추가로 접근했다. 이렇게 하면 팀원이 기존 링크를 잃어버리는 위험 없이 탐색성만 개선할 수 있다.
- 완료 기준은 상태를 하나의 라벨이 아니라 "설계됨 / 문서화됨 / 코드 작성됨 / 실행 검증됨"의 단계로 나눠 관리해, 화면이 보인다고 바로 완료로 올리지 않게 했다.
- 외부 UI 벤치마킹은 "가져올 것(시각 위계·피드백·내비게이션)"과 "유지할 것(도메인 상태 모델·한글 용어)"을 먼저 나눈 뒤에만 부분 병합안을 검토하도록 순서를 고정했다.

## 5. AI 도움 영역

- 사용한 AI 도구: Codex / ChatGPT
- 어떤 질문/요청을 했는지: Notion 페이지 재구성안, DONE 기준 문구, 외부 UI 참고 시 반영할 요소를 정리해 달라고 요청했다.
- AI가 도움 준 내용: 안내 페이지 구조 초안, View 분류 후보, DONE 기준 체크리스트 문구, 외부 UI에서 참고할 수 있는 패턴 목록을 제안했다.
- 그대로 사용한 부분: 없음 — AI가 제시한 초안은 매번 범위가 넓거나(기존 페이지 이동/통합까지 포함) ASAK 도메인 상태 모델을 그대로 두지 않는 방향이어서 그대로 채택하지 않았다.
- 수정해서 사용한 부분: "기존 페이지는 건드리지 않고 안내 페이지만 추가", "완료는 증거 기반으로만", "외부 UI는 시각 요소만 참고"라는 제약을 직접 추가해 AI 결과를 다시 좁혔다.
- AI 사용 경계: 예쁜 UI를 그대로 가져오거나 Notion 구조를 광범위하게 재편하려는 AI 제안은 채택하지 않고, 현재 도메인 상태 모델을 깨지 않는 범위로 매번 제한했다.

## 6. 발생 이슈

- 이슈 1:
  - 증상: "Figma가 완성됨", "문서가 있음", "코드 파일이 있음"이 실제로는 서로 다른 완료 수준인데 같은 완료로 보일 위험이 있었다.
  - 원인: 완료를 하나의 상태 라벨로만 관리했기 때문.
  - 해결: 코드+테스트/실행+캡처 또는 PR 증거가 있어야 완료로 표시하는 기준을 세우고, 이후 모든 워크로그에 적용했다.
- 이슈 2:
  - 증상: 외부 UI Kit을 참고하다 보면 ASAK 고유의 옵션/제외/품절/수량제한 상태 모델과 한글 업무 용어가 흐려질 위험이 있었다.
  - 원인: 외부 레퍼런스는 일반적인 커머스 UI 기준으로 만들어져 ASAK 도메인 상태와 1:1로 맞지 않음.
  - 해결: 시각 위계·선택 피드백·내비게이션만 부분 참고하고, 상태 모델·용어는 도메인 기준으로 유지하도록 범위를 고정했다.

## 7. 이번 작업에서 배운 점

- Notion, Figma, 코드는 각각 다른 역할을 가진다는 점을 명시하면서, 정보구조(IA)·정본·구현 증거·디자인 참고 범위를 한 번에 관리하는 운영 기준이 생겼다.
- "문서에 있다 = 구현됐다"는 착각을 걷어내고 설계 근거와 실행 근거를 분리하는 습관이, 이후 mock 연결·API 구현·RTOS 검증에도 이어졌다.

## 9. 검증 내용

- 이 항목은 Notion IA·완료 기준·벤치마킹 범위에 대한 **판단·정책 결정**이며, 코드 실행이나 브라우저 검증 대상이 아니다.
- 검증 근거: Notion 안내 페이지·View 구성이 실제로 반영됐는지, 다른 팀원이 기존 링크를 잃지 않았는지는 후속 확인이 필요하다.
- 미검증: DONE 기준이 daily/entries 전체에 일관되게 적용됐는지, 외부 UI 부분 병합안이 실제 화면에 반영됐는지.

## 10. 포트폴리오용 요약

Notion 정보구조를 기존 정본을 건드리지 않는 안내 레이어로 재설계하고, "코드+실행+증거"가 있어야 완료로 인정하는 기준을 세웠다. 외부 UI 레퍼런스는 시각 요소만 참고해 ASAK 고유의 상태 모델과 도메인 용어를 지키는 방식으로 판단 범위를 관리했다.
