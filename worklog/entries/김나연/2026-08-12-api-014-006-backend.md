## 2. 작업 목적

- 이번 작업에서 해결하려고 한 문제: 키오스크 결제 화면에 쓸 **결제수단 목록**과 **PG 승인 후 주문 확정** API가 백엔드에 없었다.
- 기대 결과: `GET /api/kiosk/payment-methods`와 결제 승인 서비스가 DB·명세와 맞고, 이후 Kiosk FE가 붙을 수 있는 계약을 만든다.

## 3. 직접 구현 영역

- **API-014**
  - `UserPayMapper.xml` — `pay_method_cfg` JOIN `common_code`, `media_asset`(이미지)
  - Response: methodCode, name, `active`/`isEnabled`, description, imageAssetId
  - Controller: `GET /api/kiosk/payment-methods`
- **API-006**
  - `UserPayService.approvePayment` — 토스 승인 키·금액 검증
  - `payment` insert, `orders.status` 갱신
  - Idempotency·중복 결제 409 (후일 9/2 QA PASS)

## 4. 구현 로직 / 적용한 방식

- 어떤 로직을 사용했는지:
  - MyBatis mapper alias로 DB `snake_case` → API `camelCase`
  - 결제 승인 시 주문·결제 row를 트랜잭션으로 묶음
- 왜 그 방식을 선택했는지:
  - 기존 `user` 도메인 패턴(UserOrder, UserMenu)과 동일한 Controller/Service/Mapper 구조 유지
- 데이터 흐름 또는 처리 순서:
  - (014) pay_method_cfg 조회 → DTO 목록 반환
  - (006) 승인 요청 → 토스 검증 → payment insert → orders.status 갱신
- 핵심 조건문 / 예외 처리:
  - 중복 승인 키 → 409
  - 당시 `active AS isEnabled` — 8/18 팀 합의로 JSON 필드명 `active` 통일 예정
