### RTOS 영수증 payload 확장 및 출력 방식 분리 — `feat`/`fix` · ASAK-RTOS

- **작업 목적:** 기존 RTOS 영수증 payload가 `주문번호|메뉴요약|금액` 중심의 기본 이미지 출력만 지원해 옵션·제외 재료·요청사항·결제정보가 포함된 상세 영수증을 처리하기 어려운 문제를 개선한다.
- **기존 구조 확인:**
  - `CommandPollTask`가 `GET /api/rtos/device-events/pending`으로 Spring 장치 이벤트를 polling.
  - `WorkerTask`가 `eventType`, `payload`를 기준으로 Handler 실행 후 `PATCH /api/rtos/device-events/{eventId}/finish`로 `COMPLETED/FAILED` 결과를 보고.
  - 기존 `PRINT_RECEIPT`는 payload를 `|` 기준으로 주문번호/메뉴/금액으로 분리해 출력.
- **직접 수정/정리:**
  - 기존 `work_t.payload` 버퍼를 고정 256byte 수준에서 상세 영수증을 수용할 수 있도록 `PAYLOAD_CAPACITY 2048`로 확대.
  - HTTP 응답 버퍼는 `RESPONSE_CAPACITY 4096`으로 확대.
  - 기존 `PRINT_RECEIPT`는 **기본 이미지 출력**으로 그대로 유지.
  - 신규 `PRINT_RECEIPT_TEXT` 이벤트 타입을 추가해, 이미 완성된 상세 영수증 문자열을 RTOS가 별도 분해하지 않고 그대로 출력하도록 Handler 분리.
  - 이에 따라 같은 `main.c`를 공유하더라도 기본 이미지 출력과 상세 텍스트 영수증 출력을 서로 독립적으로 사용할 수 있도록 구조화.
- **JSON 문자열 파서 수정:**
  - 기존 `json_string()`은 JSON escape를 처리하지 않아 `\n`을 실제 줄바꿈이 아닌 문자 그대로 복사하고, payload 내부 `\"`를 문자열 종료로 오인할 수 있었음.
  - 최소 escape 해제 로직을 추가해 `\n`, `\r`, `\t`, `\"`, `\\`, `\/`를 처리하도록 수정.
  - React/JS의 `JSON.stringify()`로 생성된 여러 줄 영수증 payload가 RTOS에서 실제 여러 줄 문자열로 복원될 수 있도록 개선.
- **상세 영수증 출력 예시 확인:**
  - 주문번호, 주문일시, 결제상태, 결제수단, 결제금액을 출력.
  - 주문 상품별 수량·가격 및 옵션 가격 출력.
  - 요청사항 및 총 결제금액 출력.
  - 실제 RTOS 로그에서 `PRINT_RECEIPT_TEXT` 이벤트가 순차 처리되고 `COMPLETED / receipt text printed` 결과가 Spring으로 보고되는 흐름 확인.

### FreeRTOS WorkerTask 메모리·스택 구조 보강 — `fix` · ASAK-RTOS

- **작업 목적:** payload/response 버퍼 확장 후 큰 로컬 배열이 Task stack에 중첩되는 문제를 줄이고 WorkerTask의 메모리 생명주기를 명확히 한다.
- **직접 수정/검토:**
  - `WORKER_TASK_STACK_SIZE 4096`, `POLL_TASK_STACK_SIZE 4096` 상수 추가.
  - `pvPortMalloc()`으로 생성한 `work_t`를 WorkerTask 진입 시 다시 로컬 구조체로 복사하지 않고 포인터 상태로 직접 사용하도록 수정.
  - 이에 따라 `work.event_id` 형태를 `work->event_id`로 변경하고 Handler/결과 보고 함수에는 `work` 포인터를 직접 전달하도록 정리.
  - Worker 종료 시 `vPortFree(work)` 호출 후 `worker_running = pdFALSE`, `vTaskDelete(NULL)` 순으로 정리해 이벤트 처리 반복 시 heap 누수 방지.
  - `report_result()`의 대형 HTTP 응답 버퍼를 `static char response_body[RESPONSE_CAPACITY]`로 이동.
  - `CommandPollTask`의 HTTP body도 `static char body[RESPONSE_CAPACITY]`로 이동해 PollTask stack 사용량 감소.
  - 기존 기본 이미지 Handler가 `strtok()` 사용을 위해 복사하는 payload 버퍼도 `static char payload[PAYLOAD_CAPACITY]`로 이동.
  - Worker가 동시에 하나만 실행되는 현재 `worker_running` 구조에서는 위 static 버퍼 공유가 충돌하지 않음을 확인.
- **추가 검토:**
  - `work_t parsed`까지 static 영역으로 옮기는 최적화도 검토했으나, 현재 `POLL_TASK_STACK_SIZE`와 가독성을 고려해 필수 변경 사항으로 보지 않음.
  - 실제 FreeRTOS 포트별 `xTaskCreate()` stack depth 단위 차이가 있으므로 최종 빌드/실행 시 stack overflow 여부는 추가 확인 필요.

  - `DevicePrintCommand` — `eventType`, `payload`를 String으로 보관.
  - `DeviceEventService#createReceiptPrintEvent()` — `request.eventType()`, `request.payload()`를 별도 변환 없이 그대로 `DevicePrintCommand`에 저장.
  - `AdminDeviceEventController` — RTOS pending claim 및 finish endpoint는 eventType 종류에 종속되지 않고 저장된 이벤트를 그대로 반환/완료 처리.
- **결론:**
  - 신규 `PRINT_RECEIPT_TEXT`를 위해 Spring enum이나 별도 DB 구조를 추가할 필요 없음.
  - 기본 이미지: `eventType = PRINT_RECEIPT`, 상세 텍스트 영수증: `eventType = PRINT_RECEIPT_TEXT` — 두 출력 형식을 같은 DeviceEvent/RTOS pipeline에서 병행 가능.
  - `ConsoleRtosGateway` 역시 개발용 로그 Adapter이므로 필수 수정 대상은 아님.
- **상세 기록:** [`entries/이하진/2026-08-21-rtos-receipt-dual-format-collaboration.md`](../../entries/이하진/2026-08-21-rtos-receipt-dual-format-collaboration.md) (팀원 조율·JSON escape·메모리 구조 포함)

### 태블릿 로컬 실접속 시 Spring/Vite 네트워크 구조 점검 — `debug` · ASAK-Kiosk / ASAK-back

- **작업 목적:** PC에서는 정상 동작하는 Kiosk/Spring 연동이 같은 네트워크의 태블릿에서 접속할 경우 백엔드 응답을 받지 못하는 문제를 분석한다.
- **원인 후보 정리:**
  - 태블릿에서 `localhost:8080`은 개발 PC가 아니라 태블릿 자기 자신을 의미하므로, 프론트 API base URL이 `localhost`로 고정돼 있으면 Spring 접근 불가.
  - Spring은 외부 LAN 접속을 위해 `server.address=0.0.0.0` 및 `server.port=8080` 형태로 바인딩 필요.
  - Vite 개발 서버도 외부 접속을 위해 `host: 0.0.0.0` 또는 `npm run dev -- --host 0.0.0.0` 방식 필요.
  - PC/태블릿 간 동일 네트워크 여부 및 Windows Defender Firewall의 8080/5173 inbound 허용 여부 확인 필요.
  - 직접 IP를 `.env`에 박는 방식보다 `/api` 상대경로 + Vite proxy를 사용하면 개발 PC IP 변경 시 프론트 환경변수 수정 부담을 줄일 수 있음.
- **권장 개발 구조 검토:**

  ```env
  VITE_API_BASE_URL=/api
  ```

  ```js
  server: {
    host: "0.0.0.0",
    proxy: {
      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true
      }
    }
  }
  ```

- **UUID 이슈 분석:**
  - PC의 `http://localhost:*`에서는 `crypto.randomUUID()`가 동작하지만, 태블릿이 `http://192.168.x.x:*` 형태의 일반 HTTP로 접속하면 Secure Context가 아니어서 브라우저에 따라 `crypto.randomUUID()` 사용이 제한될 수 있음을 확인.
  - 대응 방식으로 UUID 라이브러리 사용 또는 fallback UUID 생성 함수 도입 검토.
  - 해당 변경은 오늘 워크로그 기준 실제 반영 여부 별도 확인 필요.
- **상세 기록:** [`entries/이하진/2026-08-21-tablet-lan-connectivity-debug.md`](../../entries/이하진/2026-08-21-tablet-lan-connectivity-debug.md)

### 영수증 데이터 저장 범위 및 디지털 영수증 확장 설계 검토 — `design` · ASAK

- **영수증 DB 필요성 검토:**
  - 현재 ASAK에서는 별도의 `receipt` 테이블이 반드시 필요한 구조는 아님.
  - 주문/주문상품/옵션/제외/결제 데이터를 원본으로 사용해 영수증을 생성할 수 있음.
  - 현재 `DeviceEvent`는 영수증 원본 저장소라기보다 RTOS 명령의 `PENDING → PROCESSING → COMPLETED/FAILED` 상태를 관리하는 장치 명령 큐 역할.
  - 별도 영수증 스냅샷 DB는 실제 서비스에서 법적 증빙, 재발행 이력, 취소 영수증, 발행 당시 값 보존 등이 필요한 단계에서 도입하는 것이 적절하다고 정리.
- **디지털 영수증 방향 논의:**
  - 실제 영수증 프린터가 없는 프로젝트 환경을 고려해, 향후 예쁜 영수증 이미지를 생성하고 휴대폰으로 전달하는 방식 검토.
  - 단순히 Spring이 문자를 직접 발송하는 것보다 RTOS/IoT 시연 목적을 살리기 위해 DeviceEvent를 통해 RTOS가 외부 메시징 작업을 수행하도록 하는 방향 검토.
  - 예정 이벤트 타입 예시:

    ```text
    PRINT_RECEIPT
    → 기본 이미지

    PRINT_RECEIPT_TEXT
    → 상세 텍스트 영수증

    SEND_RECEIPT_MMS
    → 이미지 영수증 전송
    ```

  - 향후 흐름:

    ```text
    React
      ↓
    Spring Boot
      ↓
    DeviceEvent
      ↓
    FreeRTOS polling
      ↓
    WorkerTask
      ↓
    MMS/SMS API
      ↓
    휴대폰 영수증 수신
      ↓
    COMPLETED / FAILED
    ```

  - **오늘은 설계·구현 방향을 정리한 단계이며 MMS API 실제 연동 및 이미지 생성은 미구현.**
- **이미지 영수증 구성안:** ASAK 로고 · 매장명/주소/전화번호/사업자번호 · 영수증번호 · 주문번호/주문일시 · 결제상태/결제수단 · 상품/옵션/제외/가격 · 요청사항 · 소계/할인/TOTAL · 이벤트/쿠폰 · Barcode/QR · 감사 문구.
- **상세 기록:** [`entries/이하진/2026-08-21-digital-receipt-and-receipt-data-design.md`](../../entries/이하진/2026-08-21-digital-receipt-and-receipt-data-design.md)
