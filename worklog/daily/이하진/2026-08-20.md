- **작업 목적:** `GET /api/admin/dashboard`가 8초 걸리던 것을 줄인다.

  4. `vw_order_list_summary`를 상관 서브쿼리 방식으로 재작성해 실제 `CREATE OR REPLACE VIEW`로 적용했으나 **1.3초→6.6~6.8초로 오히려 5배 느려져 즉시 원복**. 원인은 "SELECT 목록에 상관 서브쿼리가 있는 뷰는 MySQL이 병합하지 않고 TEMPTABLE로 구체화"하는 별도 제약이었음(사전 검증을 뷰가 아닌 raw 쿼리로 측정해 이 함정을 놓쳤었다고 문서에 원인 명시).

### 일별 매출 시간대 집계 및 빈 구간 보정 정책 정리 — `design`/`feat review` · ASAK-back / ASAK-Admin

- **작업 목적:** 일별 매출 화면에서 실제 주문이 존재하는 시간대만 반환하는 방식 대신, 영업시간 내 전체 시간 구간을 일정한 간격으로 표시하고 주문이 없는 구간도 `0`으로 표현할 수 있도록 API 응답 정책을 정리한다.
- **요구사항 정리:**
  - 일별 매출 조회 시 주문이 없는 시간도 화면에서 누락되지 않도록 `0`값으로 보정.
  - 단, 하루 24시간 전체를 무조건 반환하는 것이 아니라 **실제 영업시간 범위 내의 시간대만 생성**하는 방향으로 정리.
  - 시간대 조회는 기본적으로 **30분 단위**를 지원하고, 필요 시 **1시간 단위**로도 조회할 수 있도록 확장 가능성을 검토.
  - 예:

    ```text
    10:00  0원
    10:30  12,000원
    11:00  0원
    11:30  8,500원
    ...
    ```

  - 주문이 존재하는 시간 슬롯만 DB에서 조회한 뒤 Service 또는 응답 조립 단계에서 누락 슬롯을 `0`으로 채우는 방식이 화면 안정성 측면에서 적합하다고 정리.
- **API 구조 검토:**
  - 기존 일별 매출 응답에 시간대 데이터를 무리하게 섞기보다 일별 요약과 시간대 집계를 책임별 DTO로 분리하는 현재 구조를 유지.
  - `daily`와 `daily/time-slots` 성격을 구분해 화면별 임시 shape가 아니라 API 책임별 응답 구조를 유지하는 방향으로 정리.
  - 시간 간격을 향후 파라미터화할 경우 `30m`, `1h` 등의 granularity를 명시적으로 받는 구조 검토.
- **상태:** 30분 단위 시간대 조회 훅·화면 연동은 당일 구현 범위에 포함됐으며, 영업시간 기반 빈 슬롯 `0` 보정과 1시간 단위 선택 기능은 추가 정책/구현 대상으로 검토(설계·논의만, 미구현).

### 월별·일별 매출 조회에서 미래 구간 노출 방지 정책 정리 — `design` · ASAK-back / ASAK-Admin

- **작업 목적:** 현재 날짜 이후의 월·일·시간대가 매출 조회 화면에서 의미 없이 `0`으로 노출되는 문제를 방지한다.
- **정리한 동작 원칙:**
  - 현재 연도 조회 시 **현재 월 이후의 미래 월은 응답/화면에서 제외**.
  - 현재 월의 일별 조회 시 **오늘 이후의 미래 날짜는 제외**.
  - 오늘 날짜의 시간대 조회 시에도 필요하면 현재 시각 이후 슬롯을 제외하는 방향으로 확장 가능.
  - 반면 과거 날짜의 영업시간 내 주문 없는 슬롯은 `0`으로 채워 비교 가능한 형태를 유지.
- **예시:**

  ```text
  조회일: 2026-08-20

  월별
  1월 ~ 8월      → 표시
  9월 ~ 12월     → 미표시

  8월 일별
  8/1 ~ 8/20     → 표시
  8/21 이후      → 미표시
  ```

- **목적:** `0원 매출`과 `아직 발생할 수 없는 미래 데이터`를 구분해 차트와 KPI 해석 오류를 줄이는 것.
- **상태:** 설계·논의만, 미구현.

### 관리자 매출 API 응답 책임 분리 재확인 — `refactor review` · ASAK-back

- **작업 배경:** `AdminSalesController` 및 관련 DTO를 정리하면서 dashboard → summary → monthly → daily → daily/time-slots 순으로 API 책임을 구분하는 방향을 재확인.
- **정리한 원칙:**
  - 화면 하나를 그대로 복제한 거대한 DTO를 만들지 않음.
  - `summary`: 기간 기준 KPI/집계. `monthly`: 월 단위 매출 및 월별 랭킹. `daily`: 일 단위 집계. `daily/time-slots`: 하루 내부 시간대별 집계. `dashboard`: 관리자 홈에서 필요한 최소 집계.
  - 시간대 bucket은 `daily` 기본 응답에 무조건 섞지 않고 별도 책임으로 유지.
- **효과:** 이후 화면 요구사항이 바뀌더라도 특정 페이지 DTO 전체를 다시 뜯기보다 필요한 API 단위만 수정할 수 있도록 구조를 명확히 함.

### 매출 집계 SQL의 빈 데이터 처리 방식 검토 — `sql review` · ASAK-back

- **검토 배경:** 기존 `getSalesSummary`가 단순히 `vw_sales_daily`를 조회하는 구조여서 DB에 실제 row가 존재하지 않는 날짜는 결과 자체가 사라지는 문제를 논의.
- **기존 형태:**

  ```xml
  <select
      id="getSalesSummary"
      resultType="com.asak.admin.dto.response.sales.DailySalesSummaryItemResponse"
  >
      SELECT *
      FROM vw_sales_daily
      <if test="dateRange != null">
          WHERE sales_date BETWEEN
              #{dateRange.startDate}
              AND #{dateRange.endDate}
      </if>
  </select>
  ```

- **정리한 방향:**
  - DB 집계 결과가 없는 날을 단순 SQL 결과에만 의존하면 일별 차트에서 날짜가 빠짐.
  - 조회 기간 전체 날짜 sequence와 매출 집계를 조합하거나 Service에서 날짜 sequence를 생성한 뒤 결과를 매핑해 **누락 날짜를 0으로 보정**하는 방식 필요.
  - 시간대 역시 동일하게 `영업시간 × 30분 슬롯` sequence를 생성한 뒤 실제 집계 결과와 병합하는 방식이 일관적.
